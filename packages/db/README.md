# @weddingpick/db

PostgreSQL 스키마와 마이그레이션. 호스팅에 기대지 않는다 — 관리형이든 직접 띄우든 같은 SQL이 돈다.

## 실행

```bash
export DATABASE_URL="postgres://사용자:비밀번호@호스트:5432/데이터베이스"
npm run migrate --workspace @weddingpick/db
npm test --workspace @weddingpick/db
```

`DATABASE_URL`이 없으면 테스트는 건너뛴다. CI는 postgres 서비스를 띄우고 값을 넣어준다.

## 스키마를 셋으로 나눈 이유

사업계획서 28번이 원본·개인정보·구조화 데이터·통계 데이터의 분리 관리를 요구한다. 스키마를
나누면 그 분리를 권한으로 만들 수 있다 — 통계만 읽는 역할에 `originals` 접근을 주지 않는 식.

| 스키마 | 내용 |
|---|---|
| `originals` | 원본 문서의 **메타데이터만**. 파일 본체는 별도 객체 스토리지 버킷에 둔다. 자동삭제 대상 |
| `structured` | 마스킹 후 구조화 데이터. 서비스가 읽고 쓰는 본체 |
| `stats` | 집계 결과. 개별 계약으로 역추적되지 않아야 한다 |

## 스키마가 직접 막는 것

문서에 적힌 규칙 중 애플리케이션이 실수해도 DB에서 걸리는 것들:

- **확인 안 된 문서는 확인 완료가 될 수 없다** — 계약금액·계약일·환불조건이 확인되지 않은 채
  `quotes.confirmed_at`을 채우면 트리거가 막는다. 어떤 필드가 필수인지는
  `extraction_fields.requires_confirmation` 생성 컬럼이 들고 있다 (서비스정책서 1번)
- **L2 미만 데이터로 만든 통계는 저장할 수 없다** — `price_stats`의 CHECK (서비스정책서 2번)
- **집계는 `structured.comparable_quotes` 뷰만 본다** — 등급·확인 여부 조건을 집계 쿼리마다
  다시 쓰면 언젠가 하나가 빠진다
- **표본 수·기준 기간은 중앙값과 한 행에** — 화면에 늘 같이 나가야 하므로 떼어놓을 수 없게 했다
  (사업계획서 9번)
- **원본을 지워도 구조화 데이터는 남는다** — `ON DELETE SET NULL`. 핵심 자산은 원본이 아니다
  (사업계획서 28번)
- 분위수 순서, 기준 기간 순서, 배우자 ≠ 본인, 삭제 상태와 삭제 시각의 일치

## 아직 열린 것

- `quotes.product_key` — "같은 상품"의 판단 기준이 정해지지 않아 컬럼만 두고 생성 규칙은 비워뒀다.
  중앙값의 신뢰도가 여기서 갈린다 (docs/05 7번)
- `raw_documents.retention_until` — 보관 기간 일수가 확정되지 않아 NULL을 허용한다
- 개인정보 자체(이름·연락처)를 어디에 둘지 — 인증 제공자가 정해져야 결정된다.
  지금 `users`에는 식별자만 있다

## 마이그레이션

`migrations/` 안의 `.sql` 파일을 파일명 순서대로 적용하고 `public.schema_migrations`에 기록한다.
각 파일은 한 트랜잭션 안에서 돌기 때문에 중간까지만 적용된 스키마가 남지 않는다.

새 마이그레이션은 다음 번호로 파일을 더한다. 이미 적용된 파일은 고치지 않는다.
