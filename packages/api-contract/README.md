# @weddingpick/api-contract

앱과 서버가 주고받는 것의 정의. 서버는 이대로 구현하고 앱은 이대로 부른다.

타입만이 아니라 **런타임 검증**까지 한다(zod). 서버는 들어온 요청을, 앱은 받은 응답을 같은
스키마로 검사한다.

## 계약이 막는 것

문서에 적힌 규칙 중 응답 모양만으로 막을 수 있는 것들. 서버가 실수해도 계약을 통과하지 못한다.

- **가격만 떼어 보내는 응답이 없다** — `priceStatSchema`가 중앙값과 표본 수·기준 기간을
  한 객체로 묶는다. 사업계획서 9번이 항상 같이 보이라고 한다
- **비교 불가에는 이유가 붙는다** — `comparisonResponse`는 `available` 기준의 union이라,
  가격이 없으면 `reason`이 반드시 있다. 화면이 "표본 부족"을 빈 가격으로 잘못 그릴 수 없다
  (제품 원칙 2)
- **인증 접수 응답에 승인이 없다** — `status`가 `'received'` 리터럴이다. 서버가 즉시 승인을
  내려보내도 통과하지 못한다 (서비스정책서 7번 자동승인 금지)
- **분석 성공에는 문서 id가, 실패에는 이유가 반드시 있다** — 상태별 union
- **추출값에 신뢰도가 없으면 보낼 수 없다** — 낮은 신뢰도를 "확인 필요"로 드러내려면 화면이
  신뢰도를 알아야 한다 (서비스정책서 1번)
- **배우자의 개인정보가 들어갈 자리가 없다** — 웨딩 응답은 역할과 참여 시각만 담는다
  (이용약관 제5조)

## 흐름

```
POST /v1/documents/uploads          서명된 URL 받기 → 파일은 스토리지로 바로
POST /v1/documents/{id}/complete    분석 시작
GET  /v1/analyses/{id}              A-06 진행 상태
GET  /v1/quotes/{id}                A-08 분석 결과
POST /v1/quotes/{id}/confirmations  A-07 핵심 필드 확인
GET  /v1/quotes/{id}/comparison     A-09 실제 가격 비교
POST /v1/quotes/{id}/verification-requests   A-13 인증 신청
```

파일 본체는 API 서버를 거치지 않는다. 서명된 URL이라 스토리지 제공자가 바뀌어도 계약은
그대로다.

## 아직 열린 것

- **토큰 발급 경로** — 인증 제공자가 정해져야 확정된다. 나머지 경로는 모두
  `Authorization: Bearer <token>`을 요구한다
- 업체·플래너 검색(A-16)과 업체 비교는 Phase 2라 아직 없다
