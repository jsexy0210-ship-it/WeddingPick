# WeddingPickl

**WeddingPick | 웨딩픽** — 찍으면, 진짜 가격이 보인다.

결혼 준비의 불투명한 가격과 복잡한 계약조건을 사용자가 직접 비교·검증할 수 있게 돕는 AI 기반 웨딩 견적·계약 검증 모바일 앱.

```
사용자는 찍는다 → AI는 읽는다 → 시스템은 검증한다 → 데이터는 비교한다 → 부부는 결정한다
```

## 구조

```
apps/mobile/       Expo(React Native) 앱 — Primary Product
apps/api/          Fastify + PostgreSQL 서버, AI 분석 워커
apps/web/          웹 랜딩 — 정적 HTML 한 장
packages/domain/   앱·서버·랜딩이 함께 쓰는 도메인 타입·계산 규칙·안내 문구
packages/db/       PostgreSQL 스키마와 마이그레이션
packages/api-contract/  앱과 서버가 주고받는 것의 정의 (타입 + 런타임 검증)
docs/              기획·정책·법률 기준 문서와 제품 명세
```

```bash
npm install

npm run build --workspace @weddingpick/web    # 랜딩 → apps/web/dist/index.html
```

## 현재 상태

**Phase 1 화면(A-01~A-15)이 모두 동작한다.** 촬영 → 분석 → 업체 연결 → 확인 → 실제 계약 중앙값과 비교 → 자료 확인 신청까지 이어지고, 찍은 문서는 기기에 저장돼 앱을 껐다 켜도 남는다. 웹 랜딩도 있다.

Phase 2에서는 업체 검색(A-16)과 업체 상세·비교(A-17)가, Phase 3에서는 배우자 연결(A-18)이 동작한다. 배우자 연결은 양쪽이 각각 동의해야 이뤄지고, 원본 문서 파일과 계정 정보는 연결해도 공유하지 않는다. 별점도 후기도 순위도 없다 — 보여주는 것은 업체가 있다는 사실, 분류와 지역, 확인된 계약이 몇 건 모였는지, 그리고 표본이 충분한 상품의 실제 계약 중앙값뿐이다. 자료가 없으면 없다고 적는다. 최대 3곳까지 나란히 견줄 수 있고, 그 결과에는 "금액만으로는 비교하기 어렵다"는 말이 늘 함께 나간다 — 표만 그리고 그 말을 빼면 우리가 만든 표가 오해를 부추긴다. 플래너도 찾을 수 있지만 **공개 근거가 있는 사람만** 나온다 — 견적서에서 읽어낸 이름은 검색 목록에 오르지 않도록 스키마가 막는다. 화면에는 왜 검색에 나오는지와 원하지 않을 때 어떻게 하는지가 늘 함께 나간다.

남은 것은 코드가 아니라 바깥에서 와야 하는 값이다:

- **원본 문서 보관 일수** — 정해지기 전에는 자동삭제가 돌지 않는다. 임의의 숫자로 남의 계약서를 지우거나 무기한 보관하는 쪽을 조용히 고르지 않으려는 것이다. **실제 사용자 문서를 서버로 보내는 것은 원본 처리에 대한 법률 자문 이후다.**
- **Apple·Kakao 클라이언트 ID** — 나오기 전까지 로그인 화면은 서버가 켜둔 개발용 경로만 보여주고, 그것이 실제 제공자 로그인이 아니라고 화면에 밝힌다.
- **이용약관·개인정보처리방침 확정본** — 없어서 본문을 싣지 않고 상태만 적는다.
- **문의처와 도메인** — 앱 안에는 문의 창구가 있지만 **앱 밖에서 연락할 길이 없다.** 앱을 쓰지 않는 사람이 검색에서 자기 이름을 발견해도 내려달라고 할 방법이 없는 상태다.

- **플래너 공개 근거를 만드는 절차** — 규칙과 스키마 제약은 있지만 넣는 쪽이 없어 지금은 목록이 비어 있다. 공개 자료 수집 경로와 본인·업체의 등록 요청 창구가 필요하다.
- **반론 접수 후 처리 영업일** — 문의 창구는 열렸지만 며칠 안에 답한다는 기준이 없어 기한을 약속하지 못한다.

자세한 것은 [제품·기술 명세 14번 열린 질문](docs/05-product-spec.md).
