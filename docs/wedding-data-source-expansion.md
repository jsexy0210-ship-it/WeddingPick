# 웨딩픽 다중 출처 수집 확장안

작성일: 2026-09-04. 검토 기준: 원격 main `bbc6ce800ab627efdf423d01365a29cd8e72ca00`.
초기 설계 문서다. 후속 구현은 PR #62와 apps/api/src/public-data/README.md를
참조한다. 공공데이터 이천 6개·제천 4개 로컬 수집 완료, 운영 DB 반영과 main
병합은 미실행이다. Actions가 계정 결제/지출 한도 문제로 시작 전에 차단됐다.

사용자 요구는 Google·네이버·카카오 활용 범위 확대, 동일 업체 중복 방지,
가장 최신 정보 채택, 위험 별도 보고다. 기존 수집 구현을 확장하며 새로운
범용 크롤러나 업체 원장을 만들지 않는다. 첨부자료의 코드는 참고 예시다.

## 1. 설계 결론

세 API 응답을 복제해 통합 업체 DB를 만드는 방식은 현재 확인한 공개 조건으로
실행하지 않는다. Google Places의 대량 저장·디렉터리 제한, 네이버 검색 결과의
저장·가공 제한, 카카오 로컬 응답의 저장 제한이 확인되었다.
상세 근거와 미확정 사항은 [별도 위험 보고서](wedding-data-source-risks.md)에 기록했다.

다중 출처 설계는 두 경로로 나눈다.

1. 영구 저장 경로: 개별 이용허락을 확인한 공공데이터, 업체 직접 제공 자료,
   수집·보관이 허용된 공식 웹페이지 또는 계약 데이터. 최신성 판정 후 기존 DB 반영.
2. API 연동 경로: 제공자별 허용 사용 목적·표시 방식·저장 예외를 확인한 경우에만
   활성화한다. 실시간 조회도 사용 목적 전체가 허용되어야 한다.

저장 금지 응답을 임시 DB, 감사 로그, 검색 인덱스, 해시, AI 요약에 옮겨 보관하지 않는다.
공식 홈페이지를 다시 읽었다는 이유만으로 앞선 API 활용의 제한이 없어지는 것으로
취급하지 않는다. 홈페이지의 이용허락과 API의 허용 목적을 각각 확인한다.

## 2. API별 역할과 적용 조건

| 출처 | 검토할 연동 | 현재 설계 상태 |
|---|---|---|
| Google Places API New | 조건에 맞는 장소 조회·공식 링크 제공 | 업체 DB 보강용 일괄 적재 비활성. 저장 예외와 서비스 목적 확인 필요 |
| 네이버 지역·웹 검색 | 허용된 방식의 실시간 검색 결과 제공 | 저장·정규화·통합 목록 생성 비활성. 기존 Search API와 API HUB 구분 필요 |
| 카카오 로컬 | 허용된 실시간 장소 검색·카카오맵 연결 | 저장 목적 호출 비활성. 장소 ID 보관도 별도 확인 필요 |
| 공공데이터 | 인허가 업체 발견·운영 상태 갱신 | 데이터셋별 이용허락 확인 후 기존 임포터 사용 |
| 업체 공식 출처 | 실제 사용하는 업체 필드와 허용 이미지 | 출처별 허용 필드·권리 확인 후 수집 |

네이버 신규 연동은 기존 개발자센터 키가 있다고 가정하지 않는다. 2026-07-31
시행 약관의 API HUB 이관 규정과 실제 신청 계정의 계약을 먼저 확인한다.
소셜 로그인 키가 장소·검색 API 사용 권한을 보장하지 않는다.

## 3. 중복 업체 식별

내부 업체 UUID를 유지한다. 출처 ID는 업체 자체의 영구 불변 ID가 아니며,
보관이 허용된 경우에만 내부 ID와 매핑한다.

판정 순서:

1. 보관 가능한 출처 ID의 기존 매핑 확인.
2. 검증된 공식 지점 URL과 지점 식별 정보 대조.
3. 업체명·지역·허용된 대표번호 등 독립 단서의 일치 여부 확인.
4. 기존 `vendor_aliases`와 상호 변경 이력 대조.
5. 지점·이전·동명이인 업체가 모호하면 기존 행을 덮어쓰거나 신규 생성하지 않고 재검증.

브랜드 공통 홈페이지나 대표번호만으로 지점을 합치지 않는다. 현재
`(normalized_name, region)` 고유키는 지점·동명 업체·복수 업종 사례를 확인하고
필요할 때만 보완한다. 현재 별칭의 전역 고유 제약도 같은 관점에서 점검한다.

## 4. 가장 최신 정보의 정의

동일 업체의 동일 의미·상품·지점·적용기간 필드를 비교한다. 제공자 단위로
행 전체를 덮어쓰지 않는다. 가장 늦게 API를 호출한 결과를 최신 사실로 보지 않는다.

| 시각 | 의미 | 선택 기준으로 사용 |
|---|---|---|
| source_updated_at | 원천이 명시한 해당 값의 수정시각 | 의미·정확도·범위가 검증되었을 때 |
| effective_from / effective_to | 가격·상품·상태의 실제 적용기간 | 현재 유효 여부를 먼저 판단 |
| collected_at | 웨딩픽이 응답을 받은 시각 | 실행 추적. 원천 수정시각 대체 금지 |
| verified_at | 공식 자료 등으로 사실을 검증한 시각 | 검증의 신선도. 사실의 수정시각과 구분 |

이 필드는 저장이 허용된 자료에 한해 보유한다. 시간대는 명시적으로 해석하고
날짜만 있는 근거를 초 단위로 정밀한 것처럼 만들지 않는다. 미래 시행 정보는
예약 상태로 두고 현재 정보에 덮어쓰지 않는다.

선택 규칙:

1. 저장 허용·업체 일치·필드 검증에 실패하면 반영하지 않는다.
2. `admin_locked` 행은 기존 정책대로 자동 갱신하지 않는다.
3. 비교 가능한 원천 시각과 적용기간이 있으면 현재 유효한 최신 값을 채택한다.
4. 수정시각이 없거나 서로 비교할 수 없으면 최신성 불명으로 처리한다.
   공식 변경 공지·업체 직접 확인 등으로 재검증하고, 해결 전에는 기존 검증값을 유지한다.
5. 세 출처 값이 같으면 일치 근거로 사용할 수 있으나 실제 최신성의 증명은 아니다.
6. 동일 시각의 상충 값은 공급자 고정 순위나 단순 다수결로 확정하지 않는다.
7. null·미제공·파싱 실패는 삭제 신호가 아니다. 명시적으로 확인된 삭제만 반영한다.

예: 9월 4일 조회한 A의 수정일이 8월 1일이고, 9월 3일 조회한 B의 수정일이
9월 2일이면 동일 필드·조건에 대해 B를 선택한다. 두 API 모두 수정일이 없으면
조회시각으로 A를 선택하지 않는다. 10월 시행 가격은 9월 현재 가격을 대체하지 않는다.

네이버 `lastBuildDate`는 검색 결과 생성시각이다. 업체 수정시각으로 저장하지 않는다.
검토한 Google Place·카카오 로컬 기본 응답에도 공통으로 비교할 수 있는 업체별
수정시각이 확인되지 않아 세 API만으로 항상 최신값을 판별할 수는 없다.

## 5. 기존 코드 통합 범위

- `apps/api/src/public-data-import.ts`: 실행 경로를 유지하며 공통 검증·반영 함수로 분리.
- `apps/api/src/public-data/localdata.ts`: 신규 영업 업체와 기존 업체의 상태 변경을 구분.
- `structured.vendors`, `vendor_aliases`: 원장과 매칭 재사용.
- `vendor_change_log`: 선택된 변경 필드·원인·실행 ID 기록. 새 감사 테이블 생성 불필요.
- `import_runs/errors/switches`: 실행·실패·중단 기능 확장. 웹 출처별 허용 검사는
  기존의 스위치 미등록 시 허용 동작과 별개로 반드시 통과하도록 설계.
- `vendor_images`, `VendorFact<T>`: 권리·출처·확인일 구조 재사용.
- `expos`, `wedding_info`: 업체 원장에 합치지 않는다.

추가 메타데이터는 출처 설정, 저장 가능한 업체 식별 매핑, 필드별 채택 근거로 한정한다.
불필요한 원문 저장소와 무제한 `specs_json`은 만들지 않는다. 실제 DDL은 구현 단계에서
최신 main의 스키마를 다시 확인한 뒤 정한다.

내용 해시는 허용된 필드만 정규화한 뒤 계산한다. 운영 상태를 포함하고 조회시각은
제외한다. 해시는 빠른 동등성 검사이며 최신성 판정이나 업체 식별 수단이 아니다.
변경 없는 경우 업체 내용 쓰기와 변경 로그를 생략하고 실행 확인 기록만 남긴다.
행 잠금 또는 버전 검사를 사용해 늦게 끝난 과거 작업이 최신값을 되돌리지 않게 한다.

## 6. 최소 수집과 이미지

현재 연결된 업체명·카테고리·지역·출처·확인일을 우선한다. 내부 결제 통계·후기·평점은
외부 검색 결과로 채우지 않는다. 결정사 → 웨딩홀 → 스드메 → 스냅 순으로
화면에 연결되는 필드만 추가한다. 전화번호·주소는 식별 필요성과 저장 권한이
확인된 경우만 처리하고 개인 전화번호를 일반 대표번호로 저장하지 않는다.

이미지는 사용·변경·재배포 허락을 먼저 확인하고 업체 매칭·품질·크롭을 검증한다.
검색 API 사진을 자동 다운로드해 기존 Object Storage에 복제하지 않는다.
안전한 사진이 없으면 웨딩픽 기본 이미지를 사용한다. 원본·파생본의 수와 용량을
제한하고 EXIF를 제거한다. 제공자 권리 조건은 다른 출처의 허락으로 대체하지 않는다.

## 7. 운영 흐름

`허용 출처의 수집 예정 대상 → 권리·스위치·비용 검사 → 필요한 필드 조회 → 정규화
→ 업체 식별 → 필드별 최신성 판정 → 검증 → 변경값과 기존 감사 로그를 트랜잭션 반영
→ 영향받은 캐시 갱신 → 오류 격리·재시도 → 임시 자료 정리`

GitHub Actions와 기존 Node 실행 환경을 사용한다. 일일은 행사·만료·실패 재시도,
주간은 확인기한이 된 기본정보, 월간은 사용 중인 상세 필드로 제한한다.
저장용 사용이 허용되지 않은 지도·검색 API는 이 배치에 등록하지 않는다.

출처별 요청수·동시성·최대 응답 크기·시간 제한·월 비용 한도를 설정한다.
429/일시 장애는 한도 내 재시도하고 인증·권리 오류는 반복 호출하지 않는다.
실제 요금과 할당량은 계정·상품 확인 후 결정하며 무료 운영을 보장하지 않는다.
정기 작업을 한 번 더 만드는 대신 기존 워크플로와 겹치는지 확인하고 독립 수집 작업만 추가한다.

## 8. 구현 시 검증 항목

- 조회가 늦은 구버전 값이 원천 최신값을 덮어쓰지 않는가.
- 원천 시각 미제공·동률 상충·미래 시행 가격을 보류하는가.
- 동일 원본 재실행과 동시 실행이 중복 업체·이력을 만들지 않는가.
- 잠금 행·지점 구분·별칭·명시 삭제·일시 파싱 누락을 구별하는가.
- 폐업 의심은 재검증하고 재개업 시 `closed_at`을 해제하는가.
- 금지 출처의 응답·식별키·파생값이 로그와 캐시에 남지 않는가.
- 실패 출처만 격리되며 비용·저장량 한도에서 중단하는가.

기능 구현, 공급자 허용 확인, 실제 계정 검증은 완료로 표시하지 않았다.
