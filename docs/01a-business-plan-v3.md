# 웨딩픽(Wedding Pick) 사업계획서 (v3 — 올인원 플랫폼 전환)

> 이전 버전은 "결혼정보회사 비교·검증" 단일 서비스였음. 이번 버전부터 **AI 기반 올인원 웨딩 준비 플랫폼**으로 범위가 커짐. 서비스명은 **웨딩픽(Wedding Pick)으로 확정** — 이후 변경 없음.

## 1. 한 줄 정의

> 결혼 준비의 모든 과정을 한곳에서 관리하고, 실제 데이터로 비교하고, 함께 결정하는 AI 웨딩 플랫폼

핵심 획득 메시지: **"찍으면, 진짜 가격이 보인다."**
서비스 경험 흐름: **찾고 → 비교하고 → 제보하고 → 준비하고 → 함께 결정한다.**

핵심 자산은 원본 문서가 아니라 **구조화되고 출처가 구분된 실제 웨딩 가격·결제·이용경험 데이터**다.

---

## 2. 문제 정의 (유지)

| 문제 | 현재 소비자 상황 |
|---|---|
| 가격 | 상담해야 실제 가격을 알 수 있음 |
| 상품 | 소개 횟수·기간·등급 등 구조 복잡 |
| 할인 | 개인별 제안가격이 달라 비교 어려움 |
| 후기 | 블로그·카페·커뮤니티에 파편화 |

2021년~2024년 6월, 한국소비자원 접수 결혼중개업 피해구제 신청 **1,188건**.

---

## 3. 시장성 (유지)

- 업계 대표 사업자 듀오 매출: 2023년 404억원 → 2024년 454억원 → 2025년 483억원
- 2024년 국내 혼인 건수: 약 22만 2천 건 (전년 대비 14.8% 증가)

단일 시장규모 숫자 대신 ① 업체 수 ② 주요 사업자 매출 ③ 이용자 수 ④ 혼인 건수 ⑤ 검색량으로 시장성 입증.

## 4. 경쟁 분석 — 포지셔닝 변경

기존엔 혼톡(결혼정보회사 후기·비교) 대비 "계약 비교·검증"으로 차별화하는 구도였다. **범위가 올인원 플랫폼으로 커지면서 경쟁 구도 자체가 바뀐다.**

| 구분 | 혼톡 | 웨딩북/아이웨딩류 | 웨딩픽 |
|---|---|---|---|
| 결혼정보회사 후기·비교 | O | X | O |
| 웨딩홀·스드메 전체 카테고리 | X | O | O |
| 실제 결제가격 인증(수기 제보 아닌 결제내역 촬영) | 제보 수준 | 거의 없음 | **핵심 기능** |
| 커플 공동 관리(포트폴리오) | X | 부분적 | **핵심 기능** |
| AI 자동완성(입력 최소화) | X | X | **핵심 원칙** |
| 가격 판정(적정가 표시 등) | 일부 | 일부 | **의도적으로 안 함** |

**포지셔닝**: 기존 웨딩플랫폼이 "정보 모음 + 광고"였다면, 웨딩픽은 "실제 결제 데이터 기반 비교 + 준비 자동화"로 간다.

## 5. 핵심 UX 원칙

### Auto-Complete Principle
> 사용자는 최소한만 입력하고, 웨딩픽이 나머지를 자동완성한다.

데이터 확보 우선순위: 기존 데이터 재사용 → 허용된 정보 자동수집 → AI 자동추출 → 데이터 자동연결 → 화면 자동완성 → 선택형 확인 → 직접입력(최후 수단)

### 신뢰도 상태 3단계
- `CONFIRMED` — 신뢰도 높음/사용자 확인 완료
- `AUTO_COMPLETED` — AI/기존데이터 기반 자동완성, 수정 가능
- `NEEDS_CONFIRMATION` — 불확실, 사용자 판단 필요

### 가격 표시 원칙 — "판정 금지"
`+8%`, "비싼 편", "적정가격", "바가지" 같은 평가 문구를 **일체 사용하지 않는다.** 대신:
```
내 결제: 3,120만원
유사조건 실제 결제: 2,650~3,050만원 (최근 12개월 · 결제인증 34건)
```
사실 → 출처 → 표본 → 기간 → 비교까지만 제공, 판단은 사용자 몫.

## 6. 핵심 기능 — 제보(Report)

**법적 리스크 재검토 결과 반영**: 계약서 실물 업로드는 비밀유지 조항(위약벌 최대 계약금의 2배)이 확인돼 P1에서 제외. **결제내역 촬영(결제문자/카드영수증) 기반 "결제인증"으로 전환** — 이 결정이 이번 최종안의 "정상 Flow에서 업로드 금지, 카메라 촬영만 허용" 원칙과 일치한다.

```
제보 → 개인정보/AI처리 안내 → 동의 → 카메라 촬영 → 품질검사
→ AI 분석(업체매칭/금액/날짜 자동추출) → 부족 정보만 선택형 확인
→ 제보 완료 → 결제인증 → 상세 실제가격 Unlock → 웨딩머니 자동반영
```

- **결제인증 제보**(Primary): 결제내역 촬영 → AI 분석 → 최소확인
- **직접 가격 제보**(보조): 증빙 없는 경우, "사용자 제보"로 신뢰수준 구분 표시

필드 단위로 출처를 표시(예: 결제금액 `결제인증` / 총 계약금액 `사용자 입력`) — 레코드 전체를 인증으로 뭉뚱그리지 않는다.

## 7. 이용자 3단계 (신규)

| 단계 | 조건 | 제공 |
|---|---|---|
| Level 1 탐색 | 비로그인 | 검색, 기본정보, 후기 전체, 이용점수 |
| Level 2 결혼 준비 | 로그인 | 내 웨딩, 후보저장, 웨딩머니, 준비리스트, 일정 |
| Level 3 데이터 Unlock | 유효 제보 1건+ | 실제 결제 분포, 조건별 실제가격, 시기별 데이터 |

로그인은 앱 시작 시 강제하지 않고, 저장·개인화가 필요한 시점에만 요청.

## 9. 초기 데이터 확보 전략 (기존 유지 + 확장)

성평등가족부·지자체 공공데이터로 결혼정보회사(결정사) 업체 DB는 개별 등록 없이 시작 가능. 웨딩홀·스드메 등 타 카테고리는 공공데이터가 없어 **제보 기반 데이터 축적**이 더 중요해진다 — 그래서 "제보"가 하단 내비게이션 중앙(Primary Action)에 배치된 것.

### 런칭 데이터 목표 (결정사 카테고리 기준, 유지)
- 업체 기본정보 300~500개 / 상세보강 상위 30~50개 / 실제 견적 50건 / 인증 후기 30건

### 결제인증 제보 이벤트 (기존 견적제보 아이디어를 결제인증으로 전환)
**"결제내역 촬영하고 리워드 받기"** — 100건 × 5,000원 = 50만원 목표

## 18. Claude 구현 공통 규칙 (신규 — 개발 지시용)

1. **입력 최소화**: 폼 만들기 전 자동 확보 방법부터 검토
2. **One Input, Multi Use**: 한 번 확보한 데이터는 관련 기능 전체에서 재사용
3. **AI First, User Confirm**: AI가 먼저 채우고 사용자는 확인
4. **Progressive Input**: 처음부터 모든 정보 요구 안 함
5. **Context Aware**: 현재 상태·후보·일정·결제정보로 화면 자동완성
6. **No Duplicate Input**: 같은 값 재요구 금지
7. **Confidence Based UX**: CONFIRMED/AUTO_COMPLETED/NEEDS_CONFIRMATION 구분
8. **Event Driven Update**: 검색·후보·방문·제보·결제·선택 이벤트 발생 시 관련 기능 자동 갱신
9. **User Has Final Control**: AI 자동완성 정보는 사용자가 확인·수정 가능해야 함
10. **No Price Judgment**: 가격·업체의 좋고 나쁨을 임의 판정하지 않음

→ 안심크루 코드 전환 시 화면 하나 추가할 때마다 이 10개 규칙을 전역 기준으로 적용.

## 19. 법률 리스크 현황 (별도 트래킹 필요)

- 계약서 원본 업로드는 P1에서 제외 확정 (비밀유지 조항 + 위약벌 리스크)
- 결제내역(문자/영수증) 촬영은 계약조건 정보가 없어 해당 리스크 원천 배제 — 단, 가맹점명·카드정보 등 개인정보 비식별화 규칙은 동일 적용
- 개인정보 국외이전, AI 처리사업자, 원본 삭제 시점 등은 미확정 — UI에서 과도한 법적 보장 문구 사용 금지
