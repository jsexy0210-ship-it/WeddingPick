# 프론트–백엔드 연결 전수 검수 (2026-09-16)

2026-09-16 대표 지시 — 「전체적으로 싹다 검수해 기능 동작 프론트와 연결여부 안되는거
싹다 검수해서 고쳐」.

**눈으로 읽지 않고 기계로 셌다.** 화면이 부르는 `/v1/...` 178개와 서버가 등록한 라우트
224개를 맞춰 보고, 라우트 핸들러 본문에서 **DB를 한 번도 안 만지는 것**을 따로 뽑았다.

## 가장 나쁜 것 — 「됐다」고 거짓말하는 넷

**화면에 잠금 표시(`BACKEND_PENDING`)가 없고, 쓰기 단추가 살아 있고, 서버가 성공을
돌려준다.** 운영자가 누르면 아무 일도 안 일어나는데 **성공한 것으로 보인다.**

| 라우트 | 서버가 하는 일 | 화면 |
| --- | --- | --- |
| `POST /v1/admin/ads` | `{ id: randomUUID() }` — **저장 안 함** | `ads.tsx` 잠금 없음 |
| `PATCH /v1/admin/ads/:id` | 204 — **수정 안 함** | 〃 |
| `DELETE /v1/admin/ads/:id` | 204 — **삭제 안 함** | 〃 |
| `PATCH /v1/admin/ads-gate` | 204 — **안 바뀜** | `ads-gate.tsx` 잠금 없음 |
| `PATCH /v1/admin/automation` | 204 — **안 바뀜** | `automation.tsx` 잠금 없음 |
| `POST /v1/admin/campaigns` | `{ id: randomUUID() }` — **저장 안 함** | `campaigns.tsx` 잠금 없음 |

**이것이 CLAUDE.md의 「서버에 없는 동작은 화면에서 잠그고 목록에도 「조회만」으로
표시한다」(2026-09-10 지시)를 정면으로 어긴 자리다.** 잠그지도 않았고, 서버가 실패를
돌려주지도 않는다. **둘 중 하나라도 했으면 운영자가 알았다.**

광고는 특히 위험하다 — 「광고를 껐다」고 믿는데 안 꺼져 있는 상태가 가능하다.

## 라우트가 아예 없는 것 하나

| 화면이 부르는 것 | 서버 |
| --- | --- |
| `POST /v1/admin/biz-queue/:id/approve` · `/reject` | **없다. 404가 난다** |

`admin/biz-queue.tsx:80`의 승인 · 반려 단추다. 그리고 그 화면이 읽는
`GET /v1/admin/biz-queue`도 **`{ items: [], total: 0 }` 고정값**이라 목록이 언제나 비어
있다 — 그래서 단추를 누를 일이 없어 **아무도 404를 못 봤다.**

**같은 일을 하는 진짜 라우트가 이미 있다** — `/v1/admin/inquiries`(`inquiryAdmin.list`) ·
`/v1/admin/inquiries/:id/review` · `/v1/admin/inquiries/:id/answer`. 문의 처리 계통이
**둘로 갈라져 있고 한쪽이 껍데기다.** 새로 만들기 전에 이 둘을 합칠지부터 정해야 한다.

## 빈 값을 돌려주는 조회 셋 — 화면에 잠금 표시는 있다

| 라우트 | 돌려주는 것 | 화면 |
| --- | --- | --- |
| `GET /v1/admin/biz-queue` | `{items:[],total:0}` | `biz-queue.tsx` 잠금 5곳 |
| `GET /v1/admin/revenue` | 전부 0 | `revenue.tsx` 잠금 2곳 |
| `GET /v1/admin/data/email-matching` | 전부 0 | `email-matching.tsx` 잠금 2곳 |

이 셋은 규칙대로 「조회만」이 붙어 있고 **쓰기 단추도 실제로 잠겨 있다.**

**이 자리를 처음에 「단추가 살아 있다」고 잘못 적었다.** `const BACKEND_PENDING = true`
선언만 grep해서 `terms.tsx` 하나만 걸렸는데, 나머지 넷은 `features/admin/pending-backend`
에서 **가져다 쓰고 있었다.** 선언이 아니라 **쓰는 곳**을 세야 했다.

    grep "const BACKEND_PENDING"   →  terms.tsx 하나          ← 틀린 셈
    grep "BACKEND_PENDING"         →  다섯 화면              ← 맞는 셈

`POST .../price-stats/:vendorId/recalc`가 202 `{queued:true}`만 돌려주고 큐에 넣지 않는
것은 사실이지만, **그 단추는 눌리지 않는다.** 거짓말하는 여섯과 성격이 다르다 —
저쪽은 잠기지도 않았고 서버가 성공을 돌려준다.

## 라운지 탭에 서버 계약이 아예 없다

`apps/mobile/src/app/(tabs)/community/index.tsx` — **루트 탭 다섯 중 하나다.**
「리얼후기 · 웨딩피드 · 박람회」 세 탭인데 후기 · 피드 글을 보여줄 API가 없어
**빈 상태만 그린다**(박람회만 `/search/expo`로 넘긴다).

목록을 지어내지 않은 것은 옳다. 다만 **사용자 눈에는 탭 하나가 통째로 비어 있고**,
관리자 화면과 달리 「조회만」 같은 표시를 붙일 자리도 아니다 — 사용자에게 「서버가
아직 없어요」라고 말할 수는 없다. 무엇을 보여줄지가 제품 결정이라 대표님 판단이
필요하다.

## 껍데기가 맞지만 «의도된» 것 — 고치지 않는다

| 라우트 | 왜 |
| --- | --- |
| `POST /v1/admin/terms` · `PUT .../clauses/:id` · `POST .../publish` | `termsUnavailable()`. **약관 · 방침의 정본은 웹사이트**(2026-09-11 대표 지시)라 관리자에서 못 고치게 막은 것이다 |
| `GET /v1/auth/naver/callback` | 네이버 로그인은 뺐다(카카오 + 애플만) |

## 오탐 넷 — 실제로는 제대로 붙어 있다

`GET /v1/me` · `/v1/auth/providers` · `/v1/review-report-reasons` ·
`/v1/me/recommendations`. 검출 정규식이 핸들러 본문을 잘못 잘랐다. 하나씩 열어 확인했다.

## 웨딩피드 — 연결은 됐는데 «설정»이 안 된다

라우트 다섯이 전부 실제로 붙어 있다(목록 · 작성 · 수정 · 삭제 · 자동 작성).
**다만 카테고리가 관리자 화면에서 자유 입력 `TextInput`이다**(`wedding-feed.tsx:335`).
오타나 표기 차이가 나면 그 글은 **어느 탭에도 안 뜨고 「전체」에서만 보인다** — 오류도
안 나고 화면도 멀쩡해서 알아챌 방법이 없다.

탭 넷(`WEDDING_FEED_GROUPS`)도 코드에 박혀 있어 **바꾸려면 배포해야 한다.**
2026-09-16 대표 지시 「웨딩피드는 탭별 카테고리별로 다 설정 가능해야한다」를
아직 만족하지 못한다.

## 세는 방법을 남긴다

이 검수는 다시 돌릴 수 있어야 한다. 한 번 고치고 끝내면 다음에 또 껍데기가 생긴다.
**시험으로 붙이는 것이 목표다** — 「DB를 한 번도 안 만지면서 200 · 204를 돌려주는
라우트」 목록을 세고, 의도된 것(약관 · 네이버)만 예외 목록에 둔다. 글로 적은 규칙은
깨지지만 세는 시험은 안 깨진다.
