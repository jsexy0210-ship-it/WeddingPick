# 947 — 마이그레이션은 들어가고 배포는 안 나갔다 (2026-09-16)

승인은 났고 CI도 초록이었는데 `Deploy → Staging`이 마지막 한 걸음에서 죽었다.

    DB 상태 (적용 전)     성공
    파괴적 구문 확인       성공
    DB Migrate            성공 — 적용: 0420_faq_seed_from_code, 0421_wedding_feed_taxonomy
    이전 호스팅 배포            **실패 (1초)**
    Health check          건너뜀

## 무엇이 죽었나

`scripts/삭제된 이전 호스팅 동기화.py`가 이전 호스팅에 환경변수를 하나씩 올리다가 끊겼다.

      ok GEMINI_MODEL
      !! LEGAL_TERMS_EFFECTIVE_ON 실패 (HTTP 0)

`HTTP 0`은 이전 호스팅이 거절한 것이 **아니다.** 이 스크립트는 응답이 아예 안 오면
(`except Exception → return 0`) 0을 적는다 — 끊긴 것 · 시간 초과다. 바로 앞
`GEMINI_MODEL`이 통과했으니 열쇠도 권한도 멀쩡했다.

## 왜 나쁜가 — 반만 배포됐다

**환경변수가 바뀌면 이전 호스팅은 서비스를 재시작한다.** `ok GEMINI_MODEL`이 찍힌 순간
API는 이미 재시작에 들어갔다. 그 다음 PUT이 끊기면서 스크립트가 `return 1`로 나갔고,
**새 커밋을 올리라는 요청은 한 번도 안 갔다.**

    운영 DB     0420 · 0421 적용됨          ← 새것
    운영 API    bc4d4cea 안 올라감           ← 옛것, 게다가 재시작 중
    헬스체크    건너뜀 — 아무도 확인 안 함

이 파일이 스스로 「반만 배포된 상태가 제일 나쁘다」고 적어 둔 그 자리에, 다른 경로로
다시 들어갔다. 앞서 막아 둔 것은 **서비스 이름을 못 찾았을 때**였고, 이번은 **찾았는데
네트워크가 끊겼을 때**다.

**다행히 두 마이그레이션은 «더하기만» 한다 — 실제로 열어 세어 봤다.** 새 표 둘
(`wedding_feed_categories` · `wedding_feed_groups`)과 널 허용 칸 둘(`faq_items.key` ·
`wedding_feed_posts.category_id`)이 전부다. `UPDATE`는 그 새 칸을 채우기만 한다.
지우는 · 이름을 바꾸는 · `NOT NULL`을 거는 구문이 하나도 없고, 옛 API가 읽던
`category_label`은 그대로 있다. 그래서 옛 코드가 새 DB 위에서 깨지지 않는다.

**이것은 운이었지 설계가 아니다.** 같은 사고가 지우는 마이그레이션에서 나면 옛 코드가
없어진 칸을 읽는다. 배포가 실패하면 **마이그레이션은 이미 들어간 뒤**라는 것이 이
구조의 성질이다 — 순서가 DB 먼저이고 되돌리는 단계가 없다.

## 고친 것

`call()`에 재시도를 붙였다. 끊긴 것(0)과 잠깐 막힌 것(408 · 429 · 5xx)만 2 · 4 · 8초를
두고 세 번 더 부른다.

**POST는 다시 부르지 않는다.** 끊긴 POST는 서버에서 이미 성공했을 수 있고,
`/deploys`를 두 번 부르면 배포가 둘 생겨 `wait_for_live`가 엉뚱한 것을 지켜본다.
GET · PUT · DELETE만 재시도한다.

**응답이 온 4xx는 재시도하지 않는다.** 다시 불러도 같은 답이 온다 — 배포만 늦어진다.

실패를 적을 때 **끊긴 경우에만** 본문을 남긴다. `HTTP 0` 넉 자로는 무엇이 끊겼는지
알 수 없어서 이번에도 로그만 보고는 원인을 못 짚었다. 응답이 온 4xx 본문은 적지
않는다 — 이전 호스팅이 거절 사유에 값을 되비칠 수 있고 이 스크립트의 규칙은
「값은 절대 찍지 않는다」이다.

시험 셋을 붙였다(`scripts/test-삭제된 이전 호스팅 동기화.py`). 끊긴 PUT은 다시 부르는지 ·
4xx는 안 부르는지 · POST는 안 부르는지. 글로 적은 규칙은 깨지지만 세는 시험은 안 깨진다.

## 남는 것

`삭제된 이전 호스팅 선언`은 API 서비스를 아직 `weddingpick-api`로 적고 있는데 실제로 도는 것은
`weddingpickl-sg`다(워크플로의 `API_SERVICE`). 이번 사고의 원인은 아니지만,
이름이 갈린 채로 두면 다음 사람이 `삭제된 이전 호스팅 선언`만 보고 엉뚱한 서비스를 짚는다.

## 그 뒤 — API는 스스로 돌아왔다 (14:37 KST · 14분 만에)

이전 호스팅이 재시작을 끝냈다. 200 · 0.47초. 웹 셋(app-web · web · admin)은 내내 정상이었다.

**헬스 응답이 반만 배포된 상태를 그대로 증명한다.**

    {"ok":true,"database":"ok",
     "schema":{"applied":123,"expected":118,"pending":[],
               "unknown":["0052_mission_draw","0059_wedding_events","0060_vendor_geo",
                          "0420_faq_seed_from_code","0421_wedding_feed_taxonomy"]}}

`pending`은 비었다 — 안 돌아간 마이그레이션이 없다. 그런데 `unknown`에 0420 · 0421이
있다. **DB에는 적용됐는데 돌고 있는 코드가 그 이름을 모른다**는 뜻이고, `expected: 118`이
옛 코드가 아는 개수, `applied: 123`이 DB의 실제 개수다.

**이 `unknown` 목록이 「DB가 코드보다 앞선」 상태의 탐지기다.** 다음에 같은 사고를
의심할 때 여기를 본다 — 배포가 실패했는지를 Actions에서 찾기 전에, 헬스 한 번으로
DB와 코드가 벌어졌는지가 나온다. 나머지 셋(`0052` · `0059` · `0060`)은 전부터 있던
것이라 이번 건이 아니다.

## 복구

947의 **실패한 잡만** 재실행했다(`rerun_failed_jobs`). CI는 앞 실행의 초록을 그대로
쓴다 — 16분을 다시 쓰지 않는다. 마이그레이션은 `schema_migrations`에 이미 있어
다시 돌지 않는다.

**승인은 다시 필요하다.** `environment: production`의 보호는 재실행에도 붙는다.

## 한도가 아니다

멈춘 것을 「파이프라인 한도」로 의심할 자리라 적어 둔다. 이 저장소는 **공개**라
(`visibility: public`) 표준 러너의 Actions는 무료이고 분 한도가 없다. 끝날 한도가
애초에 없다. 947의 `status`는 `waiting` — 기계가 아니라 **사람을 기다리는 중**이다.
