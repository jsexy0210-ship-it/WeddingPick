# Render 빌드 분이 어디로 갔나 (2026-09-16)

대표님이 잔여 **8분**을 알려주셨다. 무엇이 먹고 있었는지 948 로그에서 재서 적는다.

## 배포 한 번에 넷을 전부 다시 빌드하고 있었다

948의 `Render 배포` 단계가 **7분 5초**다. 로그에 넷이 나란히 찍힌다.

    == weddingpickl-sg              재배포 요청 → HTTP 201
    == WeddingPick-관리자 사이트      재배포 요청 → HTTP 201
    == weddingpickl-Preview         재배포 요청 → HTTP 201
    == WeddingPick-웹사이트          재배포 요청 → HTTP 201

**그중 가장 비싼 것이 두 번 돈다.** `관리자 사이트`와 `Preview`가 같은
`npm run export:web`(Expo 정적 export)을 각자 한 번씩 돌린다 — 산출물만 다르게 깎는
구조다(`scripts/split-admin-dist.mjs`).

948이 바꾼 것은 `apps/web` · `packages/domain` · `docs`뿐이었다.

## 규칙은 있었는데 기계가 안 지켰다

`render.yaml` 머리말이 **「바뀐 쪽만 누른다」**고 이미 적고 있었다. 그런데 그것은
**사람에게 하는 말**이었고 자동 배포는 안 지켰다. 이유가 둘이고 **둘 다 항상 참**이었다.

**하나. 조건에 `wait`가 들어 있었다.**

    if redeploy and not dry_run and (changed or wait):

`wait`는 `WAIT_FOR_LIVE`이고 워크플로가 `true`로 넘긴다. 이 한 칸으로 조건이 늘 참이다.

**둘. `changed`도 늘 참이었다.**

    status, body = call('PUT', ...)
    if 200 <= status < 300:
        changed = True          # ← 값이 같아도 여기로 온다

**Render는 같은 값을 PUT해도 200을 돌려준다.** 그래서 「썼다」와 「바뀌었다」가 구별되지
않았고, 948 로그의 `ok GEMINI_MODEL`이 그 증거다 — 그 값은 며칠째 그대로였다.

**`wait`만 고쳤어도 안 됐을 것이다.** 둘째가 남아 있어서 여전히 늘 참이다. 이것이 이
사고의 모양이다 — 늘 참인 조건이 둘 겹쳐 있으면 하나를 고쳐도 아무것도 안 변하고,
고친 사람은 고쳤다고 적는다.

## 고친 것

| 자리 | 전 | 후 |
| --- | --- | --- |
| 환경변수 | 매번 전부 PUT | 현재 값을 읽어 **다른 것만** 쓴다 |
| `changed` | PUT이 200이면 참 | **값이 실제로 달라졌을 때만** 참 |
| 재배포 | 항상 | 그 서비스가 쓰는 파일이 바뀌었을 때만 |
| 모를 때 | — | **누른다** |
| 전부 밀기 | — | `FORCE_REDEPLOY=true` |

경로 목록은 `SERVICE_PATHS`이고 출처는 `render.yaml`의 `buildCommand`다.
`packages/` · `spec/` · 잠금파일은 **모두에게** 들어간다 — 누가 쓰는지 일일이 가르지
않는다. **덜 건너뛰는 쪽이 안전하다.**

**`render.yaml`만은 공용 경로에서 뺐다.** 처음엔 넣었다가 빼면서 근거를 적어 둔다 —
그 파일의 머리말대로 **Blueprint sync가 깨져 있어서(2026-09-07 확인) 저장소의
`render.yaml`은 Render에 닿지 않는다.** 실제 빌드 명령은 대시보드에 있고 이 파일은
그것을 적어 둔 문서다. 문서를 고쳤다고 빌드 결과가 달라지지 않는다.

넣어 둔 채로 두었으면 **이 고침을 올리는 배포 자체가 넷을 전부 다시 빌드했을 것이다**
— 이 커밋이 `render.yaml`의 주석을 고치기 때문이다. 8분 중 7분이 아무것도 바뀌지 않는
데 나갈 뻔했다.

**Blueprint sync가 고쳐지는 날 이 판단을 뒤집어야 한다.** 그때 `render.yaml`은 진짜
설정이 되므로 공용 경로에 들어가야 한다. 시험이 그 자리를 잡고 있어서
(`test_render_yaml_alone_does_not_rebuild_anything`), 고치는 사람이 그 시험을 보고
이 문단에 온다.

**모르면 누른다**가 이 설계의 중심이다. 건너뛰어서 운영이 낡은 코드로 남는 것이, 분을
조금 더 쓰는 것보다 훨씬 나쁘다. 그래서 `git diff`를 못 돌렸을 때도, live 커밋을 못
읽었을 때도, 선언에 없는 서비스 이름도 전부 다시 빌드한다.

시험 일곱을 붙였다(`scripts/test-render-env-sync.py`). 같은 값은 안 쓰는지 · 다른 값은
쓰는지 · 안 바뀐 서비스를 건너뛰는지 · 바뀐 서비스는 누르는지 · 모를 때 누르는지 ·
공용 경로가 전부를 깨우는지 · **선언의 서비스가 `SERVICE_PATHS`에 다 있는지.**
마지막 것이 다음 사람을 위한 자리다 — 서비스를 더하고 목록을 안 채우면 매번 전부
다시 빌드되는데, 그건 조용해서 아무도 모른다.

## 세 번째 「늘 참」이 숨어 있었다 — 얕은 복제

고치고 올리기 직전에 잡았다. **`actions/checkout@v4`의 기본값은 깊이 1이다.**
옛 커밋이 없으니 `git diff base..head`가 `bad revision`으로 죽고, 그러면 이 설계의
「모르면 누른다」로 빠진다.

**안전하지만 조용하다.** 배포는 멀쩡히 되고, 로그에 오류도 안 나고, 넷이 전부 다시
빌드된다 — **고쳤다고 적힌 채로.** 위의 두 「늘 참」과 똑같은 모양이다.

두 자리를 고쳤다.

    워크플로   deploy-staging의 checkout에 fetch-depth: 0
    스크립트   diff가 실패하면 --depth=200으로 받아 보고 다시 잰다

**스크립트 쪽도 고친 이유**는 이 함수를 다른 자리에서 쓰게 될 때 워크플로 설정을
같이 옮긴다는 보장이 없어서다. 받아 와도 안 되면 그때는 `None`이고 전부 배포한다.

시험 둘이 이 자리를 잡는다 — 받아 오는지, 받아 와도 안 될 때 전부 배포하는지.

## 그래도 남는 것 — 줄였지 없애지 않았다

**앱 화면을 고치면 `export:web`이 여전히 두 번 돈다.** `관리자 사이트`와 `Preview`가
같은 빌드를 각자 사는 구조는 그대로다. 한 번만 빌드해 산출물을 둘로 나눠 올리려면
Render 밖에서(예: Actions에서) 빌드해 넣어야 하고, 그건 배포 경로를 통째로 바꾸는 일이라
따로 재서 정할 자리다.

**`weddingpickl-Preview`가 지금도 필요한지 대표님께 여쭤 뒀다.** 안 쓰면 배포 목록에서
빼는 것만으로 앱을 고칠 때마다 export 하나를 통째로 아낀다.
