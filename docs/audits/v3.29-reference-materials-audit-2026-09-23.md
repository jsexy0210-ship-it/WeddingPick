## 1. 웨딩픽 전체 IA — 라우트 대조

### 1-1. 문서 자체의 신뢰도 문제

`웨딩픽 전체 IA.dc.html`은 v3.29의 20개 정본 파일 중 하나지만, **본문 상단 배너가 스스로 "기준 정책 v3.10 · 2026-08-31"이라고 적고 있다** (파일 42행). `docs/design/README.md`가 v3.29 정본 20개 중 하나로 이 파일을 지목했음에도, 내용 자체는 최소 두 버전(v3.10 → v3.29) 갱신되지 않은 것으로 보인다. 아래 두 항목이 그 증거다.

| 항목 | IA 문서 내용 | v3.29 규칙(CLAUDE.md) | 코드 실측 |

### 1-2. 실제 코드에서 발견한 명백한 사실 오류 1건 (수정함)

`apps/mobile/src/features/onboarding/flow.ts:104` (`STEP_DESCRIPTION.budget`)이 실제로 **"예산에 맞춰 웨딩픽이 골라드려요"** 문자열을 그대로 쓰고 있었다 — v3.29 핵심 메시지가 명시적으로 금지한 문구 그대로다. 같은 파일의 주석(93~98행)은 이미 형제 항목(`date`)에서 한 번 같은 종류의 금지어("추천드려요")를 피해 재작성했다고 적어 두었는데, `budget` 항목은 그 작업에서 빠져 있었다. `spec/glossary.json`의 금지어 목록(v3.10)에는 이 문구가 등재돼 있지 않아 `lint-copy.js`가 잡지 못한다.

**조치**: `budget: '예산에 맞춰 웨딩픽이 골라드려요'` → `budget: '예산 구간에 맞춰 좁혀드려요'`로 교체(형제 항목 `region: '선택한 지역으로 좁혀드려요'`와 같은 어투). `flow.test.ts`의 동일 문자열 단언도 함께 갱신하고, 주석을 "1/5"→"2/5" 갱신으로 고쳤다. 이 세션에는 node_modules가 설치돼 있지 않아 `npm run test`를 로컬에서 돌리지 못했다 — 기계적인 리터럴 치환이라 위험은 낮지만, PR 머지 전 CI(or 다음 통합 세션의 로컬 실행)로 재확인이 필요하다.

## 2. 웨딩픽 컴포넌트 시트 — 토큰·컴포넌트 대조

### 2-1. 토큰류

| 항목 | 시트 값 | 코드 실측 | 일치 |

### 2-2. 사용자 노출 용어 표 대조 (섹션 05)

시트의 용어표 자체에 `avoid` 열에 금지어를 예시로 적어두는 구성은 **정상**이다(`lint-copy.js`의 검사 범위가 `apps/` `packages/`이고 시안 파일은 대상 밖이라 예시로 남는 것이 의도된 설계). 다만 아래 항목은 표 자체의 내적 오류이거나 `spec/glossary.json`과 실제로 어긋나는 것으로 판단된다.

1. **표 내부 자기모순 2건** — `use`(권장)와 `avoid`(금지) 열에 같은 단어가 동시에 들어가 있다.
   - `"검증된 정보 전체"` 행: `use: '실 제보'`, `avoid: '실 제보, 가격 데이터'` — "실 제보"가 권장이자 동시에 금지로 적혀 있다.
   - `"정보 체계 · 금액"` 행: `use: '제보 금액'`, `avoid: '실제로 낸 금액, 제보 금액, 실 제보'` — "제보 금액"이 권장이자 금지, "실 제보"는 바로 위 행에서는 권장인데 여기서는 금지로 다시 등장한다.
   이는 시트 파일 자체의 오탈자로 보이며, 디자인 레퍼런스 원본이라 이 세션에서 고치지 않았다. 코드에 영향은 없다(코드가 참조하는 건 `spec/glossary.json`이지 이 표가 아니다).

2. **`spec/glossary.json`(버전 3.10)과의 정책 충돌** — 컴포넌트 시트 자체는 `"선택 주체"` 행에서 `avoid: '웨딩픽이 골랐어요, 웨딩픽이 골라드려요, 웨딩픽 TOP3, AI 추천'`라고 명시해 v3.29 핵심 메시지와 일치한다. 그런데 **같은 저장소의 `spec/glossary.json`은 여전히 `"웨딩픽 TOP3": "상위 3곳"`, `"웨딩픽 추천": "개인화 추천"`, `"추천 이유": "추천 근거"`를 canonical(승인) 용어로 정의하고 있다.** 즉 v3.29 정본 문서와 실제 코드가 참조하는 용어사전이 정면으로 어긋난다.
   - 이는 CLAUDE.md가 이미 인지하고 있는 "후기 별점" 충돌(v3.29 문서 vs 대표님의 별도 확정 결정)과 같은 성격의 **미해결 정책 충돌**이다. `"추천"`이라는 단어 자체가 전면 금지인지("추천 이유"·"웨딩픽 추천 라벨" 등 기존에 승인된 표현까지 포함해서), 아니면 "앱이 대신 결정해준다"는 뉘앙스의 특정 문구(`웨딩픽이 골랐어요`류)만 금지인지가 CLAUDE.md 본문 안에서도 v3.29 블록과 그 아래 남아 있는 v3.24 블록("웨딩픽 추천 라벨"을 홈 코랄 사용처 중 하나로 승인)이 서로 다르게 읽힌다.
   - **이 세션은 이 충돌을 해석·해소하지 않는다.** `spec/glossary.json` 전체를 v3.29 기준으로 다시 쓰는 것은 다수의 화면·카피에 파급되는 정책 판단이라 "명백한 사실 오류 수정" 범위를 넘는다. §1-2에서 고친 1건은 v3.29 텍스트가 글자 그대로 금지한 구절이 코드에 그대로 남아 있던 경우라 예외적으로 처리했을 뿐, "추천"이라는 단어 자체는 건드리지 않았다.

## 3. 웨딩픽 사용자 흐름 — 신뢰도 주의 + 대메뉴 파일 대조

### 3-1. README의 경고가 정량적으로 확인됨

`docs/design/README.md`(76행)는 "`웨딩픽 사용자 흐름`은 옛 파일 링크가 남아 있어 현재 대메뉴 파일 기준으로 재작성 필요"라고 명시한다. 실제로 이 파일의 25개 스테이지(A~X)가 각각 `href`로 가리키는 개별 시안 파일명을 `docs/design/html/`의 실제 16개 파일과 대조한 결과:

- **25개 중 19개**가 더 이상 존재하지 않는 파일명을 가리킨다(예: `웨딩픽 로그인.dc.html`, `웨딩픽 진입 온보딩.dc.html`, `웨딩픽 홈 진행상태.dc.html`, `웨딩픽 검색.dc.html`, `웨딩픽 핵심루프.dc.html`, `웨딩픽 Pick 탭.dc.html`, `웨딩픽 웨딩일정 MY.dc.html`, `웨딩픽 제보 후기.dc.html`, `웨딩픽 MY 하위.dc.html`, `웨딩픽 회원탈퇴.dc.html` 등). 이 화면들은 v3.29에서 대메뉴 5개 파일(`대메뉴_홈`·`대메뉴_검색`·`대메뉴_Pick`·`대메뉴_웨딩노트`·`대메뉴_MY`)로 통합되면서 개별 파일이 사라진 것으로 보인다.
- **6개만** 실제 파일과 일치한다: `웨딩픽 약관 방침.dc.html`(Q), `웨딩픽 랜딩 v4.dc.html`(T), `웨딩픽 랜딩 하위페이지.dc.html`(U), `웨딩픽 관리자.dc.html`(V), `웨딩픽 컴포넌트 시트.dc.html`(W), `웨딩픽 디바이스 대응.dc.html`(X).

→ **지시대로 이 파일의 `href`·개별 파일 구성은 근거로 쓰지 않았다.** 아래 3-2는 화면 ID·순서 정보만 실제 대메뉴 5개 파일과 대조한 결과다.

### 3-2. 화면 순서·Root 구조는 대메뉴 5개 기준과 정합

흐름 문서의 거시 순서(A 로그인 → B 초기설정 → C 홈 → C 검색 → D 업체판단·비교·결정 → F Pick → G 배우자연결 → H 웨딩일정·MY → …)는 실제 Root 탭 순서(`root-tabs.ts`: 홈→검색→Pick→웨딩노트→MY)와 어긋나지 않는다. 흐름 문서가 "비회원 이용은 없다"(A 스테이지 노트), "Pick은 결정 전, 웨딩일정은 결정 후"(F 스테이지), "혼자서도 모든 기능이 열린다"(G 스테이지) 같은 이 저장소의 확정 정책과 부합하는 노트를 달고 있는 점도 코드 쪽 정책(로그인 필수, `capture`/`community` 오프탭 등)과 상충하지 않는다.

개별 화면 ID 208개 전수를 대메뉴 5개 원본 HTML과 1:1 대조하는 것은 이 세션 범위를 벗어난다(대메뉴 파일 5개 자체가 각각 대형 문서다). 이번 감사는 **파일 구조 신뢰도 확인**까지만 수행했고, 화면 ID별 내용 대조는 각 대메뉴 파일을 실제로 구현하는 화면군 세션의 몫으로 남긴다.
