## 1. 먼저 읽을 내용

사용자 최신 지시:

> 홈 뿐만 아니라 전체 페이지 대상이야
>
> 클로드가 실 작업 이어갈수 있게해주고 너는 개선점과 기타 등등을 md에 남겨줘 디자인 정본에

추가 확정 지시:

> 상담 예약은 최종 Pick 완료 -> 그 다음 이어지는 구조로 변경이 필요하다

- 홈만 수정한 뒤 종료하지 않는다. 정본의 **208개 고유 화면 ID** 전체를 추적한다. 이 숫자는 라우트 수가 아니며 시트·공통 상태·폐기 화면을 포함한다.
- 실제 모바일 앱 소스의 화면 파일은 **143개**다. 그룹 폴더와 `index`를 URL 규칙으로 정규화하고 `_layout`, `+*`를 제외한 수다. 관리자 36개, 리다이렉트·별칭도 포함한다.
- `apps/web`는 앱웹과 별도 제품이다. WEB 화면군도 연결·정책·문구의 대조 대상에 넣되, 기존 보존 지시를 무시한 전면 재디자인은 하지 않는다.
- 원본 ZIP과 해시 고정된 `handoff/`, `figma-export/` **99개 파일을 덮어쓰지 않는다.** 이 문서는 최신 사용자 요청과 수정 제안을 덧붙이는 실행 문서이지, 전달 원본의 대체 시안이 아니다.
- 본문에서 **확정 요청 / 확인된 현상 / 코드 근거 / 개선 제안 / 미확인**을 구별한다. 제안은 승인된 디자인으로 오독하지 않는다.
- 전수 대상과 출발점은 [PAGE_STATE_AUDIT.md](PAGE_STATE_AUDIT.md)를 사용한다. 파일 검색 결과는 시각 검수 완료가 아니다.

### 읽는 순서

1. 루트 `AGENTS.md`, `AI_START_HERE.md`, `CLAUDE.md`의 최신 지시.
2. [README.md](README.md), [canonical-manifest.json](canonical-manifest.json).
3. 해당 화면의 `figma-export/*.dc.html` 및 `handoff/SPEC.md`, `tokens.json`, `screens.json`, `CHANGELOG.md`.
4. 본 문서 → 전수 대장 → `docs/sync/design-screen-map.json`.
5. 최신 main과 열린 PR을 다시 확인한 뒤 소유 파일 배정.

## 3. 증거 범위와 현재 상태

### 확인한 것

- 로그인 후 공개 앱웹의 홈·준비 현황·Pick 추천 동선, 복귀 시 추천 영역이 비었다가 다시 보이는 현상.
- main 코드의 로딩 분기, 공통 스켈레톤, 주요 화면의 실제 스타일, 추천 파라미터 처리, 상담 일정 저장 코드.
- 정본 208개 ID의 기존 매핑 분류: route 123 / component 34 / state 1 / system 1 / excluded 19 / unmapped 30.
- 143개 화면 파일 중 스켈레톤 계열 직접 참조 29개, `DelayedLoadingView` 직접 참조 31개. 이는 호출부 검색 수이지 시각 결함 수나 전체 로더 수가 아니다.
- 공통 컴포넌트 안에 숨은 로딩·리다이렉트 대상의 로딩은 이 수에 별도로 포함되지 않는다.

### 아직 확인하지 않은 것

- 208개 ID의 동일 상태 390×844 전수 시각 대조.
- iOS/Android 실기기, 스크린리더, 키보드·동적 글자 크기의 전수 검증.
- 이번에 본 운영 화면과 분석 main의 배포 SHA 일치 여부.
- 모든 API의 운영 데이터·실제 네트워크 요청 횟수·상담 외부 전송 여부.
- 문서 작성 시점 이후 병합된 PR과 운영 배포 상태.

**대장에 파일이 있거나 과거 PR 검사가 초록이었다는 이유로 현재 화면을 완료 처리하지 않는다.**

### 로더 원인을 과장하지 말 것

`apps/mobile/src/api/client.ts`에는 이미 읽기 캐시·`inFlightReads`·쓰기/인증 변경 후 캐시 무효화가 있다.

`useMyCandidates`의 mount/focus 호출이 겹쳐도 **곧바로 동일 네트워크 요청이 두 번 나간다고 결론 내릴 수 없다.** 화면 상태를 초기화하는 문제와 실제 API 중복을 분리 측정한다. 개발 Strict Mode나 서버 지연으로 단정하지 않는다.

## 5. 전체 페이지의 정보 역할

아래는 중복을 줄이기 위한 **설계 제안**이다. 승인 없이 대규모 섹션 삭제나 탭 변경으로 바꾸지 않는다.

| 위치 | 주 역할 | 피할 중복 |
| --- | --- | --- |
| 홈 | 지금 상태, 다음 행동, 예산 요약, 웨딩 준비 팁 | 추천 업체 전체 목록·비교함·상담관리까지 모두 복제 |
| Pick 추천 보기 | 업종별 추천·추천 이유·조건에 맞는 후보 찾기 | 준비 현황이라는 이름의 동일 업종 목록을 또 만듦 |
| 나의 Pick | 담은 후보 관리와 최종 결정 | ‘담음’과 ‘결정’을 같은 상태로 표현 |
| 비교함/비교 상세 | 선택 후보의 차이와 결정에 필요한 정보 | 업체 탐색 목록을 그대로 한 번 더 나열 |
| 웨딩노트 | 일정·지출·기록·결정 결과 | 추천 탐색과 후보 담기의 두 번째 진입 허브 |
| MY | 개인 설정·내 기록·혜택·지원 | 준비 진행 상황을 또 하나의 대시보드로 복제 |
| 웨딩 준비 팁 | 편집 콘텐츠와 정보 습득 | 추천 업체/광고를 일반 팁인 것처럼 섞음 |

홈 추천 영역은 아직 최종 콘텐츠가 확정되지 않았다. 임시로 상담 카드를 새로 만들지 않는다.

- 권장 검토안: 추천 탐색·비교는 Pick에서만 수행하고 홈은 해당 작업으로 연결한다.
- 홈의 기존 추천 영역을 유지해야 한다면, 동일 업체 카드+Pick+비교 CTA를 그대로 반복하지 않는 대체 내용을 사용자에게 확인한다.
- 중복 해소를 이유로 예산현황이나 웨딩 준비 팁을 삭제하지 않는다.
- 제목을 바꾸는 것만으로 두 화면의 같은 기능이 통합됐다고 하지 않는다.

| 홈 웨딩홀 일정 카드 | `/pick?section=recommendations&category=hall` | 웨딩홀 추천이 첫 화면에서 열림 |
| 홈 스튜디오 일정 카드 | `/pick?section=recommendations&category=studio` | 스튜디오 추천이 첫 화면에서 열림 |
| 다른 홈 업종 카드 | 같은 route + 해당 category | 선택 업종 유지 |
| 옛 `/recommendations?category=...` | 통합 Pick 추천 | query 유실 없이 redirect |
| 준비 현황의 결정 완료/후보 행 | 해당 업종의 Pick 후보/결정 보기 | 미시작 업종 추천과 같은 동작으로 뭉개지 않음 |
| 업체 상세에서 닫기/복귀 | 현재 Back 정책에 따른 상위/명시적 history 예외 | 업종·탭·필터·스크롤 복원 기준 테스트 |

- 허용 category는 `VENDOR_CATEGORIES`를 사용한다. 누락·잘못된 값·배열형 query도 처리한다.
- `useOpenCategory`는 요청 업종과 사용자의 이후 토글을 구별해야 한다.
- 이미 최종 결정돼 추천 목록에서 빠진 업종은 “다른 업종을 조용히 열기”로 대신하지 않는다. 완료/추천 없음 상태와 후보/결정 보기 경로를 정의한다.
- 딥링크·알림 링크·로그인 복귀·탭 재진입을 포함한다.
- `features/navigation/depth-back-rules.ts`와 테스트가 현재 Back 정책의 단일 기준이다. UX 개선 명목으로 모든 화면을 history back으로 바꾸지 않는다.
- 준비 현황 route의 삭제 여부는 별도 승인 전까지 보류한다. 통합 진입점 변경만으로 오래된 링크를 404로 만들지 않는다.

## 7. 확정 흐름: 최종 Pick 완료 → 상담 예약

### 사용자 확정 순서

**업체 확인·비교 → 최종 Pick 확인 → 최종 결정 저장 성공 → 상담 예약 화면 → 예약 내용 확인·제출**

- 최종 Pick 이전에 상세·추천·비교에서 상담 예약으로 바로 건너뛰는 CTA를 제공하지 않는다.
- 최종 Pick 전 주 행동은 `최종 Pick하기`, 완료 후 후속 행동은 `상담 예약하기`로 연결하는 방향이다. 기존 확인 시트를 거쳐 최종 결정 저장이 성공해야 다음 행동을 연다.
- 완료 화면에 상담 예약으로 이어지는 명확한 다음 행동을 둔다. **최종 Pick만으로 상담이 자동 접수되거나 예약이 확정되지는 않는다.** 예약 내용 확인과 제출은 별도다.
- 사용자가 나갔다 돌아와도 서버에 저장된 최종 Pick 상태에 따라 예약을 이어갈 수 있어야 한다.
- 후보 담기(하트)만으로 다음 단계가 열려서는 안 된다. 기존 후보 모델과 최종 결정 모델을 혼합하지 않는다.
- 상세·Pick 완료·나의 Pick 등 모든 진입점과 `consult`/`booking` 직접 링크에 같은 조건을 적용한다.
- 이 순서 변경은 더 이상 미확정 제안이 아니다. 다만 아래 실제 예약 기능의 전송·확정 계약은 별도로 명확히 해야 한다.

### 현재 코드에서 확인한 사실

- 저장/하트 Pick은 **후보 담기**다. 최종 결정은 별도 `decideCategory`/결정 확인 화면이다.
- 업체 상세에 상담 CTA가 있으며 `/search/[vendorId]/consult`를 연다.
- consult는 상세 화면 위 시트이고 `booking`은 같은 구현의 별칭이다.
- 확인 시 `addWeddingEvent`로 개인 웨딩 일정을 추가한다. 이것만으로 업체에 요청이 전송되거나 예약이 확정됐다고 말할 수 없다.
- 시트의 시간 목록은 `TIMES` 고정값이다. 업체의 실제 예약 가능 시간표라고 표시하면 안 된다.
- `consultation_records` 및 업로드/확인 API는 상담 기록 자료 처리다. 이름이 비슷하다는 이유로 예약 중개 API로 재사용하지 않는다.
- Pick Root의 “상담 구현 대기” 주석과 상세의 상담 CTA도 함께 정리해야 한다.

### 권장 권한 조건

화면 잠금과 서버 검증을 함께 둔다. 아래는 개념 조건이며 실제 필드/동시성은 현재 계약에 맞춘다.

```text
현재 웨딩에 접근 가능한 회원
AND 해당 업종의 최종 결정 vendorId == 요청 대상 vendorId
AND 해당 업체/채널이 상담 연결을 지원
```

하트, 후보 목록 포함 여부, 클라이언트 전달 `isPicked`만으로 허용하지 않는다.

### 상태별 권장 UX

| 상태 | 행동 |
| --- | --- |
| 아직 후보 아님 | 후보 담기/업체 정보 보기. 상담 예약은 선행 제공하지 않음 |
| 후보에만 담김 | 비교/최종 Pick으로 안내. 상담 예약 불가 |
| 최종 결정 저장 중/실패 | 다음 단계로 이동하지 않음. 중복 클릭 방지·재시도 |
| 최종 결정 저장 성공 | 완료 상태에서 `상담 예약하기`로 다음 단계 연결 |
| 상담 연결 미지원 | 개인 일정 기록임을 명시; 예약 확정처럼 표현 금지 |
| 요청 접수 | 접수와 예약 확정을 구별해 표시 |
| 업체 확인 완료 | 서버에서 확정한 일정만 예약 확정으로 표시 |
| 결정 취소/변경 | 새 요청 차단 여부·기존 요청 처리 정책 정의. 기존 일정 자동 삭제 금지 |

### 구현 전에 확인할 선택

1. 기존 최종 결정 저장을 선행조건으로 연결한다. 새로 `상담용 Pick` 같은 중간 상태를 임의로 추가하지 않는다.
2. 상담 예약의 실제 기능은 업체 요청 전달인가, 외부 예약 채널 연결인가, 내 일정 기록인가? 현재 코드만으로 업체 예약 확정 기능이 있다고 간주하지 않는다.
3. 개인정보 전송 동의·수신 업체·채널·재시도·취소를 어느 계약에서 관리하는가?
4. 배우자의 동시 결정 변경과 중복 클릭을 서버에서 어떻게 처리하는가?

### 필수 회귀 시나리오

- 미Pick·후보만 Pick한 업체: CTA·직접 URL·예약 요청에서 차단.
- 최종 Pick 저장 실패: 완료 화면/상담 예약 진입 금지.
- 최종 Pick 저장 성공: 같은 업체의 상담 예약으로 연결, 업체 ID 유지.
- 앱 재실행·다른 기기: 서버 최종 결정으로 예약 가능 여부 복원.
- 예약 입력 중 최종 결정 해제/다른 업체로 변경: 제출 시 재검증, 입력을 조용히 버리지 않고 안내.
- 동일 업체 연속 탭/재시도: 중복 접수 방지. 이미 접수한 경우 상태 확인으로 연결하는 정책 정의.
- 최종 결정 취소는 기존 예약의 자동 취소와 다르다. 자동 삭제/취소하지 않는다.
- 일반 일정 등록 API 전체를 막지 않는다. 예약 도메인/해당 진입 경로에 필요한 서버 계약을 구분한다.

지금 시트를 실제 예약 기능처럼 확대하지 않는다. 별도 승인이 필요한 외부 메시지 전송·개인정보 전달은 실행하지 않는다. 직접 URL/API 접근, 결정 해제 직후, 다른 웨딩 접근, 중복 요청을 실패 사례로 시험한다.

## 8. 화면별 스켈레톤 규칙

### 공통 원칙

1. 스켈레톤은 “자료가 들어갈 실제 자리”다. 모든 화면에 같은 카드 3개를 붙이는 방식은 금지한다.
2. 실제 컴포넌트와 **shell·폭·safe area·패딩·행/열·이미지 비율**을 공유한다. 별도로 비슷하게 베껴 만든 수치가 다시 어긋나지 않게 한다.
3. 제목·Back·탭·필터처럼 이미 아는 UI는 그대로 둔다. 개인정보·실제 금액·완료 상태는 조회 전 가짜로 표시하지 않는다.
4. 초기 조회만 skeleton. 재조회는 기존 내용 유지+작은 갱신 표시, 더 보기는 아래쪽, 저장은 해당 CTA에 진행 표시.
5. 초기 실패는 skeleton 종료+재시도. 부분 실패는 해당 영역만 실패. 데이터가 없는 성공 응답은 empty이지 loading이 아니다.
6. 로딩 중 뒤로가기·취소가 필요한 화면의 행동을 없애지 않는다. 완료·삭제 같은 데이터 의존 CTA는 활성화하지 않는다.
7. 읽기 도구는 영역당 한 번만 로딩을 안내하도록 검토한다. 애니메이션 감소 설정도 검증한다.
8. 700ms 처리 로더 규칙과 화면 뼈대 표시를 혼동하지 않는다. 표시를 위한 강제 지연은 두지 않는 방향으로 검토하되 기존 정책과 테스트 변경을 함께 기록한다.
9. 인증 미확정 동안 이전 사용자의 캐시를 노출하면 안 된다. 세션/사용자/웨딩/필터별 캐시 구분과 무효화를 유지한다.
10. 높이가 가변인 본문을 픽셀 고정으로 속이지 않는다. 동일 fixture에서 주요 앵커의 이동량과 사유를 기록한다.

## 10. Claude 작업 순서와 소유 범위

### 착수 전

- main과 열린 PR을 다시 조회한다. 이 문서 기준 SHA를 현재 운영 SHA로 가정하지 않는다.
- 분석 당시 #473은 `features/onboarding/flow.ts` 및 테스트, #475는 MY profile/wedding-settings/notification-settings, `features/settings/my-kit.tsx` 및 app-journey 테스트를 수정 중이었다. 최신 상태 확인 후 파일 소유권을 조정한다.
- Codex가 요청 전환 전에 시작한 로컬 구현 초안은 **미커밋·미검증·미배포**다. 이번 전달 브랜치는 문서만 포함한다. 해당 초안을 정본/완료 구현으로 가져오지 않는다.
- 초안은 타입검사에서 상세 skeleton의 잘못된 스타일 참조가 확인된 미완성 상태여서 로컬 stash에 보존하고 작업 트리에서 분리했다. 제품 코드 커밋/PR에는 포함하지 않는다. Claude는 최신 main을 기준으로 구현한다.
- 사용자 데이터·운영 DB·로그인 토큰·외부 메시지를 검수 편의로 변경하지 않는다.

### 권장 작업 묶음

| 순서 | 범위 | 주의 |
| --- | --- | --- |
| A | 전수 매핑과 공통 상태 규칙, tokens/shell/접근성 | 공통 파일 소유자는 한 명. 범용 뼈대를 새 이름으로 복제하지 않음 |
| B | 인증·진입·로딩 전환 | #473 등 최신 PR 확인. 기존 테스트의 낡은 문자열 단정도 근거와 함께 변경 |
| C | 검색·업체 상세·사진·후기·비교 | 실제 카드/표/이미지 구조 공유 |
| D | Pick·홈·추천 통합 동선·준비 현황 | §2 확정 요청과 §5 미확정 정보구조를 구별 |
| E | 웨딩노트·일정·지출·메모·커플 | 화면마다 초기/갱신/편집 저장 상태 분리 |
| F | MY·알림·혜택·콘텐츠·박람회·정보·업체 관계자 | #475 소유 파일과 겹치지 않게 조정 |
| G | 업로드·검증·공통 시트·관리자·WEB 연결 감사 | 외부 작업·예약·정책 변경은 별도 승인 경계 유지 |
| H | 전체 회귀와 미매핑/제외 항목 재검토 | 처음부터 끝까지 사용자 여정 검수. 홈만 통과하고 종료 금지 |

구현 담당은 변경 단위마다 ID, route, 기준 시안 위치, 상태, 코드 파일, 테스트와 캡처 증거를 전수 대장 또는 `design-screen-map.json`에 연결한다. 기존 기록을 삭제하지 말고 기준 SHA와 상태를 갱신한다.

## 11. 검증과 완료 기준

### 상태 행렬

각 활성 화면은 아래 상태를 확인한다. 적용 안 되는 경우 “N/A + 근거”를 남긴다.

| 상태 | 확인 |
| --- | --- |
| 초기 loading | shell 유지, skeleton 정합, 취소/Back, 가짜 데이터 없음 |
| ready | 원본과 최신 사용자 예외의 일치 |
| empty | 로딩 종료, “미설정/없음/조건불일치/미지원” 구별, 다음 행동 하나 |
| error | 초기/부분/재조회 실패 구분, retry 유효, 입력/기존 자료 보존 |
| refreshing | 전체 화면 제거 없음, 선택·스크롤·탭 유지 |
| submitting | 중복 제출 방지, 해당 CTA 진행, 성공 전 완료 표시 금지 |
| 권한/세션 | 미인증·만료·권한 없음, 타인 데이터/캐시 노출 없음 |
| 복귀/딥링크 | category/query 유지, 부모/닫기 정책, 오래된 링크 |
| 환경 | 390×844 기준, 넓은 웹, 키보드·큰 글자·스크린리더·reduce motion |

### 실행할 검사

```bash
node scripts/verify-design-canonical.mjs
npm run typecheck --workspace @weddingpick/mobile
npm run typecheck --workspace @weddingpick/ui
npm run test --workspace @weddingpick/mobile -- --runInBand
npm run lint --workspace @weddingpick/mobile
node lint-copy.js spec/strings.ko.json apps packages
node scripts/sync-seed-tokens.mjs --check
```

API/도메인/계약 변경 시 해당 workspace 검사와 통합 검사를 추가한다. 위 명령은 **Claude 실행 지침**이며 이번 문서 작업에서 모두 통과했다는 뜻이 아니다.

- 기존 `scripts/screenshot-screens.mjs`, `scripts/screenshot-figma.mjs`, `scripts/fixtures/api.cjs`는 사용할 환경의 권한과 실행 방식을 먼저 확인한다. 운영 인증 우회를 만들지 않는다.
- 캡처 fixture는 loading 지연·실패·empty·최소/최대 데이터·긴 이름을 포함한다. 사용자 실제 데이터를 fixture로 복제하지 않는다.
- 동일 화면/상태의 정본과 실제 390×844 비교를 남긴다. 캡처 생성 성공만으로 검수 통과가 아니다.
- 웹 검증을 네이티브 검증으로 적지 않는다.
- 원본 변경이 필요한 정책은 승인 근거와 원본 보존 방법을 먼저 기록한다. 해시만 바꿔 검증을 통과시키지 않는다.
