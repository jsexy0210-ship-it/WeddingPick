# v3 전환 분석 — 지금 코드에 무엇이 맞고 무엇이 어긋나는가

사업계획서 v3(올인원 전환)과 화면·데이터 구조 스펙을 받아, 화면스펙 9번이 요구한
일곱 가지를 지금 코드 기준으로 정리한다. **코드는 아직 손대지 않았다** — 9번이
"승인 전 전체 코드 일괄 수정 금지"라고 못박았고, 아래 4번의 충돌들은 승인 없이
고를 수 있는 것이 아니다.

기준 시점의 코드: API 212 · 도메인 146 · 스키마 18 테스트 통과, 마이그레이션 0021까지.

> **2026-08-28 결정 반영.** 아래 0번·4-1·4-2·4-4가 정해졌고, ①~④가 구현됐다.

## 0. 먼저 물어야 하는 것 — 두 문서가 서로 다른 범위를 말한다

| | 사업계획서 v3 | 화면·데이터 구조 스펙 |
| --- | --- | --- |
| 1번 정의 | 결혼 준비 전체(웨딩홀·스드메·…·결정사) | **"결혼정보회사가 공식 안내한 조건과…"** — 결정사 단일 |
| 이용점수 | 전 카테고리 공통 기능(7번 Level 1) | 결정사 항목만(5.5: 가격설명/계약일치/매칭이행/과도권유…) |
| 비교표 | — | 공식가격·소개 횟수·해지점수 — 전부 결정사 항목(4번) |

스펙 문서는 스스로 "이전 버전은 결혼정보회사 단일 서비스였음"이라고 적은 그 **이전
버전 기준으로 쓰여 있다.** 그래서 아래 3번·4번의 판단이 갈린다:

- **스펙이 결정사 전용이라면** — 이용점수는 카테고리마다 다른 두 벌(결정사=체크리스트,
  웨딩홀·스드메=항목별 평가)이 되고, 지금 만든 것은 후자로 살아남는다
- **스펙이 전 카테고리 기준이라면** — 지금 만든 별점 후기를 체크리스트로 갈아엎어야 한다

**결정: 별점을 유지한다.** 표본 기준만 스펙 5.5의 5건을 따르고, 항목별 평가는
지금 구조(업종·역할별 별점)를 그대로 쓴다. 05a의 체크리스트 항목이 전부 결정사
전용이라 웨딩홀 음식·주차에는 쓸 수 없기 때문이다.

스펙 5.5의 나머지 반쪽 — "기준 미달이면 확정 비율 노출 금지" — 은 그대로 지킨다.
기준에 못 미치면 `average` 키 자체가 응답에 없다. 4건에서 계산한 4.5점을 회색으로
흐려 보여주는 것도 안 된다. 흐린 숫자도 숫자고, 사람들은 숫자를 읽는다.

## 4. 정책·기술 충돌 (승인 필요)

### 🔴 4-1. 원본 파기 — 30일 vs 24시간

2026-08-28에 "검증 완료 후 30일"로 정하고 마이그레이션 0018까지 넣었다. 스펙 8.3은
"분석 완료 후 24시간"이다.

둘은 **서로 다른 것을 재고 있다.** 30일은 인증 심사가 원본을 다시 볼 수 있어야 해서
잡은 값이고, 24시간은 카드정보가 찍힌 이미지를 오래 들고 있지 않겠다는 값이다.
계약서가 P1에서 빠지면 남는 원본은 결제내역뿐이니 **24시간이 이긴다** — 다만 그러면
사람이 심사할 때 원본이 이미 없다. 심사를 24시간 안에 끝내거나, 심사를 접수 시점의
자동 판정으로 바꿔야 하는데 후자는 서비스정책서 7번(자동승인 금지)과 부딪친다.

**결정: 제보는 심사가 아니라 등록이다.** 그러면 이 충돌이 사라진다 — 사람이
원본을 붙들 이유가 없으니 24시간이 그대로 맞다.

그래서 보관 기간은 **종류별로** 갈렸다(0022). 결제내역 24시간, 계약서 30일. 두
값이 다른 것은 두 가지가 다른 것을 재기 때문이고, 하나로 합치면 둘 중 하나가
틀린 값이 된다. 종류는 등록할 때가 아니라 **올릴 때** 받는다 — 나중에 정하게
두면 찍어만 두고 등록하지 않은 결제내역이 30일짜리 문서로 남는다.

등록이 심사가 아니라는 것은 결과에서도 지켜진다: 문서 등급이 오르지 않고
(`verification_requests`가 만들어지지 않는다), 시장 대표가격에도 들어가지 않는다.
서비스정책서 7번의 자동승인 금지는 등록 경로가 생겼다고 느슨해지지 않는다.

### 🔴 4-2. 이용점수 — 별점 vs 체크리스트

바로 앞 작업에서 별점(1~5) 기반 후기를 만들어 넣었다. 스펙 5.5는 **"예/아니오/모름
체크리스트 자동환산, 별점 아님"**이라고 명시한다. 표본 기준도 우리 3건 vs 스펙 5건이다.

체크리스트가 더 나은 이유가 스펙에 적혀 있다 — **"모름"은 분모에서 빠진다.** 별점은
모르는 것도 3점쯤으로 찍히고 그게 평균에 들어간다. 우리 구조는 "답하지 않은 항목은
넣지 않는다"로 그걸 피하지만, 사용자가 모르면서 답하는 것까지는 못 막는다.

다만 5.5의 항목(가격설명/계약일치/매칭이행/과도권유…)은 전부 결정사 항목이라
웨딩홀 음식·주차에는 쓸 수 없다. **0번이 먼저 정해져야 한다.**

**결정: 별점 유지.** 0번을 보라. 기준만 5건으로 올렸다.

곁가지로 0020의 버그를 하나 찾았다. `receipt`(영수증 확인)가 L1(견적인증)에 붙어
있었다. L1은 "실제 견적자료 확인"이지 영수증이 아니고, 견적서를 받은 것과 그
업체를 이용한 것은 다른 일이다 — **상담만 받고 계약하지 않은 사람의 후기에 확인
배지가 붙고 있었다.** 그 자리를 결제인증(`payment`)이 가져갔다.

### ✅ 4-3. 비로그인 = 익명 제보 아님 (구현됨)

읽기만 열었다. 후기 **쓰기**·신고·제보는 로그인이 계속 필요하다 — 한 사람이 한
업체에 하나라는 제한이 사용자 식별에 기대고 있고, 그게 없으면 점수를 밀어 올릴
수 있다.

**틀린 토큰은 여전히 401이다.** 조용히 비로그인으로 떨어뜨리지 않는다 — 만료된
토큰을 든 사람에게 남의 화면을 보여주면 그 사람은 자기가 로그인한 줄 안다.
토큰이 아예 없는 것과 틀린 것은 다른 일이다.

### ✅ 4-4. 캡처 허용 (결정됨)

결제문자는 **이미 찍혀 있는 화면 캡처**인 경우가 대부분이라, 캡처를 막으면
제보가 거의 안 들어온다. 앨범 불러오기를 그대로 둔다.

### 🟡 4-5. "AI" 표기

새 문서는 AI를 앞세우지만, 화면 문구에서 AI를 쓰지 않는 규칙은 그대로 두는 것으로
읽었다. 사업 문서와 화면 문구는 다른 것이고, 5번의 "판정 금지"도 같은 방향이다.

### ⚪ 4-6. 계약서 P1 제외는 우리가 찾은 것이다

6번이 근거로 든 "비밀유지 조항 위약벌 계약금 2배"는 실제 계약서 제12조에서 확인한
것이다(2026-08-28). 계약서 관련 코드(문서 종류 7종, 계약 기반 L2 인증, 계약서 촬영
화면)는 **지우지 말고 남겨두기를 권한다** — 법률 확인이 끝나면 되살릴 것이고,
지우면 다시 만드는 값이 훨씬 크다. P1 범위에서 빼되 코드는 둔다.

## 5. DB 스키마 변경안 (초안)

| 마이그레이션 | 내용 | 상태 |
| --- | --- | --- |
| 0022 | `payment_proofs`, `masked_identifier_kind` enum, 종류별 보관 기간 | ✅ |
| 0023 | 후기 확인 단계에 결제인증. 근거를 가리키게 하는 CHECK | ✅ |
| 0024 | `data_unlocks` — 실제가격 열람 자격 뷰 | ✅ |
| 0025 | `vendor_candidates` — 후보 저장. 웨딩 단위, 배우자와 공유 | 남음 |
| 0026 | `vendors.slug` — SEO 경로 | 남음 |
| 0027 | `ai_usage` — 기능별 호출·토큰·비용·escalation·사용자 수정률 | 남음 |

**카드번호를 저장할 방법이 없게 만든 것**이 0022의 요점이다. 요청 본문에 그 필드가
없고, DB 컬럼은 `masked_identifier_kind[]` enum이라 `'5432-1234-…'`를 넣으려 하면
타입이 거부한다. `text[]`였다면 언젠가 누가 넣는다. 테스트가 그 거부를 확인한다.

보관 기간은 `retention_interval(kind)` 하나로 갈린다. 뷰가 계산하므로 저장된 파기
시각을 뒤늦게 고칠 일이 없다.

## 6. 구현 우선순위 (제안)

```
① 0번 결정 (이용점수 범위)      ✅ 별점 유지, 기준 5건
② 비로그인 읽기 열기            ✅ Level 1
③ 결제인증 등록 + 24시간 파기   ✅
④ Level 3 Unlock 게이트         ✅
⑤ 결제내역 전용 파서            ← 다음. 지금은 직접 적는다
⑥ 후보 저장 · 비교픽
⑦ AI Router · 비용 추적
⑧ SEO slug + 업체 페이지
⑨ PLAN (웨딩머니·준비리스트·일정)
```

⑤가 다음인 이유는, 지금 등록 화면이 영수증을 보고 **직접 적게** 하기 때문이다.
읽어주는 척하고 빈칸을 내미느니 아직 못 읽는다고 말하는 편이 낫지만, 이 상태로는
제보가 잘 들어오지 않는다. 스펙 7.3이 길을 정해뒀다 — 규칙 기반 파서를 먼저 보고,
안 되는 것만 AI Vision으로.
