# 상담기록(음성 → 구조화) — 구현 전 보고

2026-09-14 대표님 요청 §36 「바로 구현하지 않는다. 먼저 보고한다」에 대한 답이다.
**아직 아무것도 구현하지 않았다.** 아래 판단 필요 6건이 정해져야 1단계가 시작된다.

---

## 0. 먼저 결정이 필요한 것 여섯

### P-1 · 카테고리 네 종이 우리에게 없다

요청은 지원 14종인데 `VENDOR_CATEGORIES`(packages/domain/src/vendor.ts)는 **13종**이고
겹치지 않는 자리가 있다.

| 요청 | 코드에 있나 |
| --- | --- |
| 웨딩홀 · 스튜디오 · 드레스 · 메이크업 · 헤어변형 · 본식스냅 · 예물 · 부케 · 신혼여행 · 혼수 | 있다(10종) |
| **아이폰스냅 · 본식영상 · 예복 · 웨딩플래닝** | **없다(4종)** |
| 청첩장 | 있다 — 그런데 요청은 **미지원**으로 적었다 |
| 결정사 | 코드에 있는데 요청 목록에 없다 |

업종을 더하면 상담기록만 바뀌지 않는다. `PREPARATION_CATEGORIES`를 홈 준비 현황 ·
Pick 탭 · 검색 업종 격자 · 온보딩이 전부 읽는다. **넷을 더하면 그 화면들이 같이 바뀐다.**

- **A안** 업종을 실제로 넷 더한다(앱 전체에 보인다)
- **B안** 상담기록 안에서만 쓰는 분류로 두고 업종 목록은 그대로 둔다
- **C안** 지금 있는 10종으로 시작하고 넷은 나중에

### P-2 · 청첩장을 빼나

요청은 청첩장을 **미지원**에 넣었는데, 승인 대기함 **A-12에서 대표님이
「청첩장·예물·허니문 수집 코드 추가」를 승인**하셨다(2026-09-14). 코드에도
`invitation`이 업종으로 있다.

상담기록에서만 안 받는 것인지, 업종 자체를 내리는 것인지 다르다. **한복은 A-15와
요청이 일치**하므로(웨딩 업종에서 제외) 그대로 뺀다.

### P-3 · 「웨딩플래닝」과 「결정사」는 다른 것이다

CLAUDE.md 2026-09-11 대표 지시가 **「플래너」는 업종이 아니라 B2B 문의 창구**라고
못박고 `wedding_info_company`를 **결정사**로 통일했다. 그런데 요청의 PLANNER는
동행/비동행 · 플래닝 비용 · 스드메 구성을 뽑는 **준비 대행 업종**이다.

결혼정보회사(중매)와 웨딩플래너(준비 대행)는 실제로 다른 업이다. 이름이 겹친다고
합치면 같은 목록에 섞인다. **어느 쪽인지 대표님이 정하셔야 한다.**

### P-4 · 화면에 「AI」를 쓸 수 없다

CLAUDE.md는 **사용자 화면과 관리자 화면 모두 `AI` 금지**다(2026-09-11 대표 지시 —
「한국식 토스식 용어를 사용한다」). 요청의 기능명 「AI 상담기록」과 화면 문구
「AI가 상담 내용을 정리했어요」가 그 규칙과 정면으로 어긋난다.

제안: 화면은 **「상담기록」** · **「웨딩픽이 상담 내용을 정리했어요」**.
**내부 개발 문서와 비용 문서에서는 AI를 그대로 쓴다** — 거기서 빼면 무엇을 부르는
말인지 사라진다(이 문서도 그 자리다).

### P-5 · evidence를 저장하면 그것이 부분 녹취록이다

요청 §27은 필드마다 발화 원문(`"식대는 인당 7만 8천원입니다."`)을 저장하라고 하고,
§31은 전체 녹취록을 보관하지 말라고 한다. **둘은 정도의 차이지 종류의 차이가 아니다.**
발화 원문에는 상담사 이름 · 전화번호가 섞여 들어올 수 있다.

- **A안** evidence를 저장하지 않는다 — 대신 `confidence`만 남긴다. 가장 안전하고 가장 싸다
- **B안** 숫자 필드에만 evidence를 남기고 **길이를 제한**한다(예: 40자) + 개인정보 마스킹 + 본문과 같은 시점에 삭제
- **C안** 요청대로 다 남긴다 — 보존기간과 파기 주체를 방침에 새로 적어야 한다

권합니다: **B안.** 금액 확인은 evidence가 있어야 사용자가 고칠 수 있고, 40자면
문장 하나라 대화가 복원되지 않는다.

### P-6 · 100MB를 받으려면 업로드 방식이 달라진다

요청의 상한은 100MB인데, Gemini에 음성을 요청 본문에 실어 보내는 방식(`inlineData`)은
**audio 문서 기준 총 요청 20MB**가 한도다(일반 한도는 2026-01에 100MB로 올랐지만 audio
쪽 안내는 20MB로 남아 있다 — 두 줄이 어긋난다). base64로 싣는 순간 용량이 약 1.33배가
되므로 100MB 파일은 어느 쪽 한도로도 안 들어간다.

→ **Files API(업로드 후 참조)로 가야 한다.** 지금 제가 만들어 둔
`gemini-visit-note-reader.ts`는 `inlineData` 방식이라 **작은 파일 전용**이다. 15MB를
넘으면 Files API로 올리고 그 참조를 넘기는 길을 따로 만든다.

## 4. DB 변경 — 필요하다

`visit_notes` 네 칸으로는 못 담는다. 새 표를 만든다.

```
structured.consultation_records
  id · wedding_id · vendor_id · vendor_label
  status(3단계 판정) · category · confidence
  common jsonb · category_data jsonb · pricing jsonb
  benefits jsonb · additional_costs jsonb · conditions jsonb
  summary · warnings jsonb · missing_information jsonb
  metadata jsonb(model · analyzed_at · schema_version · user_confirmed · original_deleted)
  created_at · confirmed_at
```

- **카테고리별 칸을 열로 펴지 않고 `jsonb`로 둔다.** 14종 × 20~30칸이면 열이 300개가
  넘고, 한 종을 고칠 때마다 마이그레이션이 생긴다. 열로 두는 것은 **어느 카테고리에나
  있고 검색·통계에 쓰는 값**뿐이다.
- `visit_notes`와의 관계: 손으로 적는 방문노트는 그대로 두고, 상담기록이 확정되면
  방문노트 한 줄을 만든다(업체 · 날짜 · 제안금액). **두 표를 합치지 않는다** —
  손으로 적은 것과 뽑아낸 것은 신뢰도가 다르다.
- **제안금액은 가격 통계에 넣지 않는다.** `visit_notes`의 기존 규칙과 같다
  (요청 §5와 일치: Pick 인증과 별개).
- 마이그레이션 번호: **0330 · 0340** 을 이 작업에 잡는다(현재 최신 0231, 0290~0320은 회수됨).

## 5. API 변경

```
POST   /v1/consultations/uploads      올릴 자리(uploadPath) + 동의 기록 — uploadUrl(서명 URL)은 옛 앱용
PUT    /v1/consultations/:id/audio    녹음 본문(같은 출처 · 100MB) → 저장소로 흘려 보냄 + 도착 기록 (2026-09-26)
POST   /v1/consultations/:id/complete 업로드 완료 — 서명 URL로 올리던 옛 앱만 부른다
GET    /v1/consultations/:id          진행 상태 · 결과
PATCH  /v1/consultations/:id          사용자 수정
POST   /v1/consultations/:id/confirm  확정 저장 + 원본 삭제
DELETE /v1/consultations/:id
```

기존 인증(`requireUser` · `currentUserId`)을 그대로 쓴다. **주인 확인은 결제 증빙과
같은 방식** — 남의 id로 남의 녹음을 읽게 두지 않는다.

## 6. Gemini 호출 구조

```
1차  앞 3분 + 뒤 2분만 보낸다 → 3단계 판정 JSON만 받는다
2차  통과한 것만 전체를 보낸다 → 카테고리별 상세
```

`GEMINI_API_KEY`(secrets) · `GEMINI_MODEL`(vars) 둘 다 **API 서버에만** 둔다.
`삭제된 이전 호스팅 환경 선언`에 키는 이미 올렸고 **모델 이름은 아직 안 올렸다 — 같이 올린다.**

## 7. 사전분류 구조

요청 §6의 JSON을 그대로 쓴다. 구조화 출력(`responseSchema`)이라 스키마 밖의 값은
나오지 못한다. `confidence` 분기도 요청 §7 그대로(0.80 / 0.50).

**다만 §7의 마지막 줄을 코드로 만든다** — `confidence`가 높아도
`consultationSignals`에서 가격·일정·계약·혜택 중 **둘 이상이 true가 아니면** 통과시키지
않는다. 그러지 않으면 「친구와 웨딩홀 얘기한 잡담」이 0.9로 들어온다.

## 8. 카테고리 스키마

공통 25칸 + 카테고리별 필드를 zod로 한 벌만 적고, Gemini 요청 스키마는 거기서
만들어 보낸다(`z.toJSONSchema`). **손으로 두 벌 적지 않는다** — 결제내역에서 이미
같은 이유로 한 벌로 합쳤다.

## 9. 파일 저장/삭제

```
같은 출처 API(PUT …/audio)가 스토리지로 흘려 보냄 → 임시 보관 → 1차 → 2차 → 구조화
(2026-09-26: 서명 URL 직행은 브라우저 CORS preflight에서 막혀 바꿨다 — docs/deployment.md «파일 저장소»)
→ 사용자 확인 → 원본 삭제 → metadata.original_deleted = true
```

- **사용자가 중간에 나가도 지운다.** 확인을 안 하면 남는 설계는 「확인 안 한 파일이
  영원히 남는 자리」가 된다. 결제 증빙과 같이 **상한 시각**을 둔다(제안: 24시간).
- 삭제 실패는 조용히 넘기지 않는다 — 재시도 큐에 넣고 관리자 화면에 남긴다.

## 10. 개인정보 영향 — **여기가 가장 큰 위험이다**

1. **Google LLC가 수탁자·국외이전 표에 없다.** 개인정보보호법 제28조의8은
   **고지가 이전보다 먼저**다. 방침 시행 전에 첫 호출을 내보내면 그 구간이 미고지
   이전이다. → 방침 개정이 **1단계**다.
2. 수집 항목에 **음성**이 없다. 「추출 후 즉시 삭제」와 함께 올린다.
3. **방침에 이미 거짓이 된 문장이 있다.** 「기존 API와 백그라운드 처리는
   미국에 남아 있으며」 — 싱가포르 이전이 끝나 사실이 아니다. 같이 고친다.
4. 요청 §31의 마스킹 대상(전화·주민·계좌·카드·이메일·주소)은 **담을 칸을 만들지 않는
   방식**으로 막는다. 「적지 마라」는 지켜지지 않을 수 있지만 없는 칸에는 못 쓴다.
5. 탈퇴 시 삭제 경로에 새 표를 넣는다(`withdrawal` 스크립트).

| 비웨딩 파일 | 5분에서 끝 | 9,600 | **0.4원** — 48원을 아낀다 |

**§33의 2단계가 실제로 돈을 아낀다.** 비웨딩 파일 하나마다 47.6원씩 안 나간다.

## 12. 회귀 위험

- **P-1에서 A안을 고르면 위험이 커진다** — 업종 목록을 읽는 화면이 홈 · Pick · 검색 ·
  온보딩 · 준비 현황까지라 그 전부가 영향을 받는다. B/C안이면 상담기록 안에 갇힌다.
- `visit_notes`를 건드리지 않으므로 기존 방문노트 화면은 그대로다.
- 스토리지·워커·인증을 재사용하므로 새로 깨질 자리가 적다.
- **가장 큰 회귀 위험은 비용이다.** 사전 검증이 빠지면 긴 파일 하나가 한 번에 수백 원이다.

## 13. 시험 계획

- 3단계 판정: 비웨딩 · 미지원 · 지원 각각 (Gemini는 가짜로 끼운다 — 실제 호출은 돈이 든다)
- `confidence` 분기 세 구간 + 「신호 둘 미만이면 통과 안 됨」
- 14종 스키마가 각각 제 칸만 갖는지 · **전화번호·계좌번호 칸이 없는지**
- 키가 주소가 아니라 헤더로 가는지 · 오류 본문이 메시지에 안 붙는지(이미 있음)
- 남의 상담기록 접근 차단 · 비로그인 차단
- 원본 삭제 · 삭제 실패 재시도
- 파일 검증 7종(형식 · 손상 · 무음 · 길이 · 용량)
