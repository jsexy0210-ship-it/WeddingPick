# 피그마에만 있던 화면 셋 — 「이미 있는 것」 전수 조사

2026-09-14 대표 지시로 뒤집힌 판정 셋을 다시 조사한 결과다.

> 없는 화면은 신규개발이 필요하면 신규로 싹다 진행하고, 이전 파일 활용할 수 있으면 활용한다.

앞선 판정(`claude/rn-screens-vendor` 브랜치 `VENDOR_SCREEN_PARITY.md` 4·7·8행)은 셋을
**「만들지 않음」** 으로 적었다. 그 근거는 「시안에 없다」와 「서버에 필드가 없다」 둘이었다.
이 문서는 **두 번째 근거만** 다시 따진다 — 첫 번째는 대표 지시가 이미 뒤집었다.

조사 기준 SHA: `8a25960` (`origin/main`) · 피그마 `weddingpick_figma` 기본 브랜치.

## 0. 먼저 — 앞선 판정이 놓친 것

`VENDOR_SCREEN_PARITY.md` 8행은 상담 예약을 이렇게 적었다.

> 서버에도 상담원 배정·시간대·**캘린더 공유** 개념이 없어(도메인·API 스키마 grep 0건) 지어낼 근거가 없음

**캘린더 공유는 있다.** 이것이 오늘 찾은 네 번째다(별점 `usageScoreSchema` · 해시태그
`styleTags` · 문의 접수 `inquiries`에 이어서).

| 있는 것 | 자리 |
| --- | --- |
| 마이그레이션 | `packages/db/migrations/0061_wedding_events.sql` |
| 계약 | `packages/api-contract/src/wedding-events.ts` |
| 서버 라우트 | `apps/api/src/routes/wedding-events.ts` |
| 앱 화면 | `apps/mobile/src/app/(tabs)/wedding/[id]/events/` |
| 앱 클라이언트 | `apps/mobile/src/api/client.ts` |

마이그레이션 · 계약 · 라우트 · 화면 · 클라이언트까지 **다섯 층이 모두 붙어 도는 기능이다.**
0065의 주석이 그것을 직접 적어 뒀다 — 「wedding_events(0061, 우리웨딩 일정) … 그쪽은
**커플의 캘린더 일정**이고」.

피그마 `ConsultPage` 639~648행이 그리는 문구가 바로 이것이다.

```
커플 캘린더에 자동으로 공유돼요
지윤 · 준혁 두 분의 우리웨딩 캘린더에 상담 일정이 공유됩니다.
```

그리고 `weddingEventSchema`에는 이 자리가 **미리 비워져 있다.**

```ts
vendorId: idSchema.nullable(),
vendorLabel: z.string().nullable(),
/** 지금은 항상 'manual'. 훗날 업체 결정에서 자동 생성될 자리만 미리 둔다. */
source: weddingEventSourceSchema,   // 'manual' | 'auto'
```

`source: 'auto'`는 **아직 한 번도 쓰이지 않은 값이다.** 상담 신청이 첫 사용처다.

> grep이 0건이었던 이유는 「상담」·「예약」·「consult」로 찾았기 때문이다. 이 기능의 이름은
> 「우리웨딩 일정」이다. **같은 것을 두 이름으로 부르지 않는다는 규칙은 찾을 때도 적용된다** —
> 없다고 적기 전에 그것을 우리가 무엇이라 부르는지부터 본다.

## 1. 업체 상담 신청 — 피그마 `ConsultPage`(533~669행) · 마이그레이션 0300

### 조사표

| 피그마가 그린 것 | 저장소에 이미 있는 것 | 판정 |
| --- | --- | --- |
| 접수 → 사람이 결론 (상태 흐름) | `api-contract/src/inquiries.ts` — `status`·`receivedAt`·`decidedAt`·`resolution` · `domain/src/inquiry.ts` `INQUIRY_STATUSES` | **늘려 쓴다** |
| 접수 확인 문구 | `createInquiryResponseSchema.acknowledgement` — 「기한이 정해지기 전에는 날짜를 약속하지 않는다」 | **이미 있다** |
| 무엇에 대한 신청인지 | `inquirySubjectSchema` — `kind: 'planner' \| 'vendor' \| 'quote'` · **`'vendor'`가 이미 있다** | **이미 있다** |
| 접수 화면 얼개 | `my/contact.tsx` · `my/support.tsx` | **늘려 쓴다** |
| 캘린더 공유 (639~648) | `wedding_events` 다섯 층 + `source: 'auto'` 예비 자리 | **이미 있다** |
| 상담 다녀온 뒤 기록 | `wedding/[id]/visit-notes.tsx` 방문노트 — 「상담을 다녀온 날 들은 금액과 느낌을 적는 자리」 | **이미 있다 · 범위 밖** |
| 날짜 · 시간 선택 (576~626) | 없음 | **신규** |
| 담당자 배정 · 「평균 응답 30분 이내」(558~574) | 없음 | **만들지 않음** (아래) |
| 업체가 부여한 실제 가능 시간대 | 없음 | **만들지 않음** (아래) |

### 늘려 쓰되 표는 따로 둔다 — 이유

`inquiries`를 그대로 쓰지 않는다. **다른 물건이다.**

```
inquiries   고객센터 문의 — 우리에게 묻는다. 날짜·시간이 없다
상담 신청     업체에 묻는다 — 날짜·시간이 핵심이다
```

`createInquiryRequestSchema`에 `preferredDate`·`preferredTime`을 옵션으로 더하는 길이 있지만
택하지 않는다. 그 둘은 **`kind: 'vendor'`일 때만 뜻이 있고 나머지 세 유형에서는 언제나 빈
칸**이다. 한 표에 「어떤 줄에서만 채워지는 칸」을 두면 그 칸이 비었을 때 그것이 「안 골랐다」인지
「고를 필요가 없는 유형」인지를 표가 말하지 못한다. FAQ 쪽에서 `NULL`을 구분에 쓰지 않기로 한
것과 같은 판단이다.

**상태 흐름과 「접수만 한다」 원칙만 본뜬다.** 표는 `structured.vendor_consult_requests`로 새로 판다.

### 화면 문구 — 「예약」이 아니라 「신청」이다

피그마는 「상담 예약」·「9월 18일 · 오전 10:00 **예약하기**」·「상담 일정을 **등록했어요**」로 적는다.
**그대로 쓰면 사용자는 그 시간에 간다.** 우리는 업체 일정을 실시간으로 잡아줄 수 없다.

| 자리 | 피그마 | 우리 |
| --- | --- | --- |
| 화면 제목 | 상담 예약 | **상담 신청** |
| CTA | 9월 18일 · 오전 10:00 예약하기 | **이 시간으로 신청하기** |
| 완료 | 상담 일정을 등록했어요 | **신청을 접수했어요. 업체가 확인하면 알려드려요** |
| 날짜·시간 라벨 | 날짜 선택 / 시간 선택 | **희망 날짜 / 희망 시간** |

`VENDOR_SCREEN_PARITY.md`도 이 화면을 **「F14 상담 신청」** 으로 적었다. 이름은 이미 맞게 붙어 있었다.

### 만들지 않는 것과 그 이유

- **담당자 카드 · 「평균 응답 30분 이내」** — 업체별 담당자도 응답시간 측정값도 서버에 없다.
  지어내면 근거 없는 약속이 된다(`거의`·`대략` 금지와 같은 줄의 문제다).
- **업체가 부여한 실제 가능 시간대** — 업체가 직접 쓰는 길이 지금 없다. 고정 시간 슬롯을
  보여주고 그중에서 고르게 한다. 그 슬롯은 **가능 시간이 아니라 희망 시간**이다.
- **캘린더 자동 생성** — 신청 시점이 아니라 **업체가 확정한 시점에** `wedding_events`에
  `source: 'auto'`로 넣는다. 신청만으로 캘린더에 넣으면 확정되지 않은 일정이 캘린더에 선다.
  → **0300 범위에는 자리(`consult_request_id`)만 두고 실제 생성은 확정 경로가 생길 때.**

## 2. 업체별 FAQ — 피그마 `VendorFlows.tsx`(316~340행) · 마이그레이션 0310

### 조사표

| 피그마가 그린 것 | 저장소에 이미 있는 것 | 판정 |
| --- | --- | --- |
| 아코디언 열고 닫기 | `my/faq/[faqKey].tsx` · `my/guide.tsx` · `my/contact.tsx` | **늘려 쓴다** |
| 표 구성 (묶음·문답·정렬·공개) | `0230_admin_faq.sql` `structured.faq_items` | **본뜬다** |
| 운영자 등록·수정·삭제 | `apps/api/src/faq-admin.ts` · `routes/admin.ts` 다섯 라우트 | **늘려 쓴다** |
| 코드 항목 잠금 · 겹쳐 보이기 | `faq-admin.ts` — `editable: false` | **이미 있다** |
| 서비스 FAQ 본문 | `domain/src/faq.ts` `FAQ_ITEMS` 7항목 | **이미 있다 · 손대지 않는다** |
| 업체 상세의 FAQ 섹션 | 없음 (`search/[vendorId]/index.tsx`에 FAQ 없음) | **신규** |
| **FAQ 공개 조회 계약·라우트** | **없음** | **신규** (아래) |

### 조사 중에 드러난 것 — 0230은 아직 사용자에게 닿지 않는다

`faq_items` 표는 있고 관리자 라우트도 있는데, **공개 조회 라우트가 없다.**
`endpoints.ts`에 `faq` 항목이 0건이고, `routes/` 아래 admin이 아닌 곳에도 0건이다.

앱은 `FAQ_ITEMS`를 `@weddingpick/domain`에서 **직접 import해서 그린다**(`my/support.tsx` ·
`my/guide.tsx` · `my/contact.tsx` · `my/faq/[faqKey].tsx`). 즉 지금은 —

```
운영자가 등록한 FAQ  →  faq_items 표  →  관리자 콘솔에만 보인다
사용자가 보는 FAQ    →  코드의 FAQ_ITEMS  →  앱을 새로 내야 바뀐다
```

**운영자가 등록한 FAQ를 사용자는 못 본다.** 0230이 「화면은 이미 있었고 서버가 없었다」를
고쳤는데, 이번에는 반대쪽이 비어 있다. 업체 FAQ는 처음부터 공개 조회가 필요하므로 이 구멍을
그대로 두고 지나갈 수 없다.

→ **판단 필요**: 서비스 FAQ 공개 조회까지 이번에 붙일지, 업체 FAQ만 붙이고 서비스 쪽은
따로 남길지. 전자는 범위가 늘고, 후자는 「운영자가 고쳐도 안 보이는 표」가 더 오래 남는다.

### 표를 따로 둔다 — 이유

`faq_items`에 `vendor_id uuid NULL`을 붙이는 길은 택하지 않는다.

**「업체가 없는 줄」이 서비스 FAQ가 되는 구분을 `NULL`로 하면, 나중에 읽는 사람이 놓친다.**
`WHERE vendor_id IS NULL`을 빠뜨린 조회 하나가 업체 FAQ를 서비스 FAQ 자리에 세운다. 그리고
그것은 에러가 아니라 **그냥 목록이 길어진 것으로 보인다.**

둘은 다른 물건이기도 하다.

| | 서비스 FAQ (`faq_items`) | 업체 FAQ (신규) |
| --- | --- | --- |
| 무엇에 대한 질문인가 | 웨딩픽 | 이 업체 |
| 코드 항목과 겹치는가 | 겹친다(`FAQ_ITEMS` 잠금) | 겹칠 코드 항목이 없다 |
| 묶음(`category`) | 필요하다 | 업체 하나에 몇 줄이라 불필요 |
| 공개 조회 | 전역 1벌 | 업체마다 |

→ `structured.vendor_faq_items` (마이그레이션 0310). **0230의 컬럼 구성과 그 주석에 적힌
판단은 그대로 가져온다** — `sort_order` 작은 수가 위 · `published` 기본 `false`(작성 중인
항목이 그대로 나가지 않게) · `CHECK (question <> '')` · `updated_by` `ON DELETE SET NULL`.

### 0230의 규칙을 지킨다

> 코드의 FAQ를 표로 복사하지 않는다. 건수를 글에 박아두면 기준이 바뀌는 날 사본이 옛 수를
> 말하고, 문장이라서 아무도 고장으로 보지 않는다.

업체 FAQ는 운영자가 쓰는 자유 문장이라 계산된 값이 들어갈 자리가 없다. **그러니 `FAQ_ITEMS`의
어떤 항목도 업체 FAQ 표에 복사하지 않는다.** 업체 상세에서 서비스 FAQ를 같이 보여줄 이유도
없다 — 「이 업체에 대한 질문」 자리에 「웨딩픽에 대한 질문」이 섞이면 둘 다 안 읽힌다.

### 누가 쓰는가 — 운영자다

업체가 직접 쓰는 길은 지금 없다(`vendor-claims`는 업체 관계자 확인까지만 한다). 관리자 화면이
이미 그 모양이므로 **운영자가 쓰는 것으로 시작한다.** `faq-admin.ts` 옆에 같은 모양으로 붙인다.

### 앞선 판정을 정정한다

`VENDOR_SCREEN_PARITY.md` 7행은 「좋아요·댓글은 `Review` 도메인 타입에 필드가 없어 API 계약
변경 없이는 구현 불가」라고 적었다. **좋아요·댓글에 대해서는 맞다.** 다만 같은 화면의 **신고는
계약·도메인·표·화면이 모두 이미 있다.** 화면 단위로 「없음」을 적으면 그 안에 든 조각이 이미
있는 것을 덮는다.

### 댓글과 업체 반론 — **다른 자리다**

| | 업체 반론 | 댓글 |
| --- | --- | --- |
| 누가 | 업체 관계자(본인이 밝힌 `claimedRole`) | 아무 회원 |
| 무엇을 | 후기 내용에 대한 **반박** | 후기에 대한 **반응·질문** |
| 게시 결정 | **사람이 한다**(`published_rebuttals`) | 즉시 게시 |
| 개수 | 후기당 1개 | 여럿 |
| 자리 | 후기 카드 **안**(`reviews.tsx` 245~252행) | 후기 상세 **아래 스레드** |

**같은 자리로 보지 않는다.** 반론은 「후기를 가리는 대신 옆에 말을 더한다 — 읽는 사람이 양쪽을
다 본다」는 원칙 위에 있고(`reviews.ts` 주석), 그래서 사람이 게시를 결정하고 후기와 나란히 선다.
댓글을 같은 자리에 넣으면 **사람이 검토해 게시한 반론과 즉시 게시되는 댓글이 한 줄에 서고,**
읽는 사람은 둘을 같은 무게로 읽는다. 반론의 무게는 「사람이 봤다」에서 나온다.

화면에서도 나눈다 — 반론은 후기 본문 바로 아래(지금 자리 그대로), 댓글은 그 아래 별도 섹션.
**업체 관계자가 댓글을 달 수는 있다.** 다만 그 댓글은 반론 배지를 달지 않는다.

### 신고 · 차단 · 삭제 — 이번 범위에 넣는다

댓글은 사람이 쓰는 글이다. 셋이 없으면 운영이 불가능하다.

| | 방식 | 근거 |
| --- | --- | --- |
| **신고** | `review_reports`와 **같은 모양**으로 `review_comment_reports`. 사유는 `REPORT_REASONS` 5종을 그대로 쓴다 | 사유가 같다(허위·욕설·스팸·개인정보·기타). 새 목록을 만들 이유가 없다 |
| **삭제** | 작성자 본인 = 즉시 숨김(soft delete, 자리는 남기고 「삭제된 댓글이에요」). 운영자 = 조치 기록과 함께 숨김 | 스레드에서 줄이 사라지면 위아래 대화가 어긋난다 |
| **차단** | **이번 범위 밖 — 판단 필요** (아래) | |
| **가림** | 후기와 같은 `pii-review`·`risk-scan` 경로를 태운다 | 전화번호·계좌번호는 후기든 댓글이든 같은 위험이다 |

**차단을 이번에 넣지 않는 이유**: 차단은 「이 사람이 쓴 것을 나에게 안 보이게」이고, 우리는
후기 작성자를 밝히지 않는다(`reviewSchema.mine`이 「작성자를 밝히지 않으므로 이것 말고는 알
방법이 없다」고 적어 뒀다). 차단하려면 **차단할 대상을 식별할 수 있어야 하고, 그것은 지금
일부러 막아 둔 것이다.** 사용자 단위 차단을 넣으면 그 원칙이 깨진다. 신고 + 운영자 삭제로
시작하고, 차단이 필요하다고 판단되면 그때 식별 문제를 먼저 푼다.

→ **「완료」에 섞지 않는다. 차단은 안 한 것이다.**

### 좋아요 — 누가 눌렀는지 남긴다 · 탈퇴하면 지운다

중복을 막으려면 `(review_id, user_id)` 유니크가 필요하므로 누가 눌렀는지 남는다.

**탈퇴 시 좋아요는 삭제한다**(`ON DELETE CASCADE`). 후기·실 제보와 다르게 잡는 이유:

| | 탈퇴 시 | 근거 |
| --- | --- | --- |
| 후기 · 실 제보 | **분리해 유지** | 「탈퇴는 개인정보 삭제이지 서비스 정보 삭제가 아니다」 — 남이 읽을 내용이 있다(`withdrawal.ts`) |
| Pick · 일정 · 지출 | **즉시 삭제** | 개인화 정보 |
| **좋아요** | **즉시 삭제** | **Pick과 같은 성격이다** — 내용이 없고 「내가 무엇에 반응했는가」뿐이다. 분리해 유지할 내용 자체가 없다 |
| **댓글** | **판단 필요** (아래) | |

좋아요 수는 **저장하지 않고 매번 센다.** `weddingEventStatusSchema`가 「저장하지 않는다.
startsAt과 지금을 비교해 서버가 매번 계산한다」로 적어 둔 것과 같은 이유다 — 센 수를 따로
저장하면 탈퇴로 줄이 지워지는 날 그 수가 틀린 채로 남고, 숫자라서 아무도 고장으로 보지 않는다.

→ **판단 필요 (댓글의 탈퇴 처리)**: 댓글은 「사람이 쓴 글」이라 후기 쪽(분리해 유지)에
가까워 보이지만, 「저희도 여기 가려고 생각 중이었어요」 같은 짧은 반응이 대부분이라 남겨서
얻는 것이 적다. **후기와 같이 분리 유지할지, Pick처럼 지울지 대표님 판단이 필요하다.**
처리방침 문구가 따라 달라진다.

### 후기 사진은 범위 밖이다

피그마 `ReviewDetailPage`는 320px 대표 사진을 그리는데 **`reviewSchema`에 이미지 필드가 없다.**
`vendor-image.ts`는 업체 이미지 전용이다. 후기 사진은 업로드·저장·가림·용량·삭제가 모두 따로
필요한 별개 작업이라 0320에 넣지 않는다. 후기 상세 화면은 **사진 없이** 그린다.

### 용어 — 피그마를 그대로 옮기면 두 곳이 틀린다

1. **「계약 인증」(718행)은 오용어다.** 정본은 **`Pick 인증`**(root `WP-RPT-제보·후기.dc.html`
   #12d L294·348). `VENDOR_SCREEN_PARITY.md`가 이미 짚어 뒀다.
2. **좋아요 토스트가 「Pick 목록에 담겼어요」다**(740~746행). **좋아요와 Pick을 같은 것으로
   그렸다.** Pick은 업체를 담는 것이고 좋아요는 후기에 반응하는 것이다. 같은 것을 두 이름으로
   부르지 않는다는 규칙의 반대편 — **다른 것을 같은 이름으로 부르고 있다.** 좋아요에 Pick을
   쓰지 않고, 하트 아이콘도 Pick Mark와 구분되게 그린다.

## 4. 개인정보 — 코드보다 먼저 알릴 것

### 댓글 — 수집 항목은 **늘지 않는다**

처리방침 제1항(`apps/web/src/subpages.ts`)에 이 행이 이미 있다.

```
후기·문의·신고 | 작성 내용, 첨부자료, 처리상태, 계정 식별자, 답변 이력
              | 게시·처리 목적 달성 또는 탈퇴 시까지. 작성자와 분리된 후기는 유지될 수 있음
```

댓글은 **작성 내용 + 계정 식별자**다. 항목 자체는 이 행 안이다. 다만 **행 이름에 댓글이
없다.** 항목이 아니라 이름 문제이므로 차단 사유는 아니지만, 방침 담당 세션에 넘길 것:

- 행 이름 `후기·문의·신고` → **`후기·댓글·문의·신고`**
- 보유기간 문장에 댓글의 탈퇴 처리를 반영 (위 「판단 필요」가 정해진 뒤)

### 좋아요 — **판단 필요**

「웨딩 준비 관리」 행의 `Pick한 곳`과 같은 성격이지만 그 행에 좋아요가 없다. 항목이
`계정 식별자 + 대상 후기 id`뿐이라 새로 받는 정보는 없다. **행에 한 마디 더할지 방침 담당
세션 판단.**

### 상담 신청 — **여기가 진짜 게이트다**

이용약관 **제3조(제3자 제공)** 가 이 기능을 이미 지목하고 있다.

> **업체 상담·견적·예약 기능**이나 보상 발송을 위해 제공이 필요한 경우 제공받는 자, 목적,
> 항목, 보유기간, 동의 거부권을 **해당 기능 사용 전에 별도로 알립니다.**

**업체에 신청자 정보를 넘기는 순간 제3자 제공 별도 고지·동의가 필요하다.** 그리고 처리방침
제1항 표에 상담 신청 행이 **없다.**

**이것이 「접수만 하고 결론은 사람이 낸다」를 본떠야 하는 두 번째 이유다.** 문구 문제만이
아니다 — 운영자가 받아서 사람이 처리하는 구조에서는 **업체로의 제3자 제공이 아직 일어나지
않는다.** 0300은 그 선 안에 머문다.

→ 업체에 자동으로 넘기는 경로(업체 대시보드·업체 알림)를 붙이는 순간 **방침 개정과 동의
절차가 먼저**다. 0300 범위에 넣지 않는다.

## 6. 정리 — 「새로 만든다 / 늘려 쓴다 / 이미 있다」

| | 이미 있다 | 늘려 쓴다 | 새로 만든다 |
| --- | --- | --- | --- |
| ① 상담 신청 | 캘린더(`wedding_events`) · 방문노트 · `subject.kind='vendor'` · 접수 확인 문구 | `inquiries` 상태 흐름(본뜬다) · 접수 화면 얼개 | 표 · 날짜/시간 선택 화면 |
| ② 업체 FAQ | 코드 항목 잠금 · 아코디언 · 관리자 얼개 | `0230` 컬럼 구성 · `faq-admin.ts` | 표 · 공개 조회 계약·라우트 · 업체 상세 섹션 |
| ③ 좋아요·댓글 | **신고 전부** · 별점 4축 · 인증 배지 · 반론 | `pii-review`·`risk-scan` · 탈퇴 규칙 | 표 셋 · 후기 상세 라우트 · 좋아요 · 댓글 |

**앞선 「만들지 않음」 판정 셋 중 순수 신규는 좋아요·댓글뿐이다.** 나머지는 뼈대가 있다.

## 7. 대표님·MASTER 판단이 필요한 것

「완료」에 섞지 않고 여기 따로 적는다.

1. **FAQ 공개 조회 구멍** — 서비스 FAQ까지 이번에 붙일지, 업체 FAQ만 붙일지.
2. **댓글의 탈퇴 처리** — 후기처럼 분리 유지할지, Pick처럼 삭제할지. 처리방침 문구가 따라 간다.
3. **댓글 차단** — 이번 범위 밖으로 둔다. 작성자를 밝히지 않는 원칙과 정면으로 부딪힌다.
4. **좋아요 방침 표기** — 「웨딩 준비 관리」 행에 한 마디 더할지.
5. **상담 확정 경로** — 업체가 확정하는 길(업체 대시보드·알림)은 제3자 제공 게이트 뒤에 있다.
   0300에는 자리만 두고 만들지 않는다.
