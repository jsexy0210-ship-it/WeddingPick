# 새 서비스 부트스트랩 기준

웨딩픽에서 반복된 시행착오를 새 서비스 시작 때 재사용하기 위한 운영 기준이다.
이 문서는 특정 서비스의 기능 명세가 아니라, 기획·디자인·개발·배포를 같은 구조로 묶는 시작 템플릿이다.

## 1. 저장소 기본 구조

```text
service/
├─ apps/
│  ├─ mobile/              # 주 제품(Expo 또는 네이티브)
│  ├─ api/                 # 인증·도메인 API
│  └─ web/                 # 랜딩·정책·관리 진입점
├─ packages/
│  ├─ domain/              # 앱·API가 공유하는 규칙과 문구
│  ├─ api-contract/        # 요청/응답 타입과 런타임 검증
│  ├─ db/                  # 스키마·마이그레이션·시드
│  └─ ui/                  # 공통 컴포넌트와 토큰 어댑터
├─ spec/
│  ├─ tokens.json          # 색·타이포·간격·크기·radius·모션
│  ├─ strings.ko.json      # 화면 문구의 단일 원본
│  ├─ glossary.json        # 금지어·대체어·표현 규칙
│  └─ screens.json         # 화면 ID·순서·상태·권한·광고 독립성
├─ docs/
│  ├─ 01-business-plan.md
│  ├─ 02-service-policy.md
│  ├─ legal/               # 외부 공개 전 확정하는 법정 고지
│  └─ new-service-blueprint.md
├─ CLAUDE.md               # AI/개발자 공통 구현 규칙
├─ gen-tokens.js           # iOS·Android·Web 토큰 생성기
├─ lint-copy.js            # 사용자 노출 문구 린터
└─ .github/workflows/      # CI·마이그레이션·헬스체크
```

저장소가 여러 개면 위 구조와 `CLAUDE.md`, `spec/`을 각 저장소 루트에 동일하게 둔다. 값은 복사하지 말고 원본 저장소에서 생성·동기화한다.

## 2. 시작 순서

1. 서비스 한 문장, 핵심 루프, 금지 범위를 `README.md`에 고정한다.
2. 정책보다 먼저 화면을 만들지 않는다. 사업계획 → 서비스정책 → 제품명세 순으로 결정한다.
3. `spec/`을 먼저 작성한다. 화면 ID와 상태 세트를 정한 뒤 구현한다.
4. `CLAUDE.md`에 심볼, 용어, 레이아웃, 접근성, 탈퇴, 관리자 인증, PR 기준을 기록한다.
5. 토큰 생성기와 카피 린트를 로컬에서 실행하고 CI에 연결한다.
6. API 계약·DB 마이그레이션·모바일 화면을 같은 기능 단위로 커밋한다.

## 3. 디자인 재현 규칙

- 목업의 기준 viewport, 상태, 샘플 데이터를 먼저 고정한다.
- 색·폰트·간격·아이콘·radius를 코드에 직접 입력하지 않고 `spec/tokens.json`에서 생성한다.
- 문구는 `spec/strings.ko.json`에서 가져오고 `glossary.json`의 금지어를 통과시킨다.
- 화면 ID마다 캡처를 남겨 목업과 실제 결과를 비교한다. 빈 API 응답을 “완료 화면”으로 사용하지 않는다.
- Android 시스템 네비게이션 영역과 iOS safe area를 별도 검증한다.

## 4. 인증·환경 설정

| 항목 | 개발 | 스테이징 | 운영 |
|---|---|---|---|
| API URL | 로컬/터널 | 운영과 동일한 경로 | 고정 HTTPS 도메인 |
| DB | 테스트 DB | 운영과 동일한 스키마 | 영구 PostgreSQL |
| 저장소 | 임시 허용 | 영구 버킷 권장 | S3/R2 등 영구 저장소 필수 |
| OAuth | 개발용 클라이언트 | 별도 클라이언트 또는 제한된 계정 | 플랫폼별 운영 클라이언트 |
| Health | 프로세스 확인 | DB `SELECT 1` 포함 | DB·필수 의존성 포함 |

OAuth는 제공자별로 Android 패키지/SHA-1, iOS Bundle ID, HTTPS callback, 네이티브 scheme을 표로 관리한다. 웹 client ID를 모바일에 재사용하지 않는다. Play 배포 서명 SHA-1은 디버그 APK와 별도로 등록한다.

## 5. 운영 안전장치

- 비밀값은 저장소·앱 번들·문서에 넣지 않고 호스팅 시크릿으로만 주입한다.
- 입력 길이, 출력 토큰, 사용자별 호출 횟수, 파일 크기와 MIME을 서버에서 제한한다.
- AI·외부 API 호출은 비용 로그와 실패 재시도 상한을 함께 둔다.
- `health`가 200이어도 DB가 끊기면 운영 가능으로 보지 않는다.
- 탈퇴·원본 보관·국외 이전·수탁사·법정 고지값은 확정 전 외부 공개를 차단한다.
- 스테이징은 운영과 같은 빌드·환경변수 이름·마이그레이션 순서를 사용한다.

## 6. 브랜치와 출시 게이트

```text
feature/* → PR → main → 자동 배포 → /health 검증 → 모바일 빌드 검증
```

PR 체크리스트:

- [ ] 관련 화면 ID와 상태가 `spec/screens.json`에 있다.
- [ ] 토큰·문구·용어가 원본 파일에서 생성된다.
- [ ] DB 마이그레이션이 재실행 가능하고 롤백 영향을 기록했다.
- [ ] 실제 캡처 또는 API smoke test를 남겼다.
- [ ] 운영·스테이징 환경변수 차이를 검토했다.
- [ ] CI 계정 한도·결제 상태도 확인했다. 작업이 시작되지 않은 실패와 코드 실패를 구분한다.
- [ ] 배포 커밋과 실제 호스팅 커밋이 일치한다.

## 7. 장애 분류와 대응

- **P0**: 로그인·DB·결제·개인정보 삭제·핵심 루프가 중단됨. 배포를 멈추고 복구 후 재검증한다.
- **P1**: 핵심 기능 일부가 실패하거나 운영 데이터가 잘못 표시됨. 우회책과 수정 배포를 우선한다.
- **P2**: 디자인 오차·카피·접근성·관리 화면 등 품질 문제. 다음 릴리스 전에 정리한다.

각 이슈에는 재현 절차, 영향 범위, 마지막 정상 커밋, 운영 로그, 재검증 결과를 남긴다.

## 8. 새 프로젝트 산출물

새 저장소를 시작할 때 최소한 아래를 먼저 커밋한다.

1. `README.md`, `CLAUDE.md`, `spec/` 4종
2. `lint-copy.js`와 현재 토큰 스키마에 맞는 생성기. 기존 `gen-tokens.js`는 구형이며 현재 스키마에서 `undefined`가 출력되므로 그대로 복사하지 않는다.
3. 정책 초안과 미확정값 목록
4. OAuth·환경변수 매트릭스
5. CI의 typecheck/lint/test/build/health 단계
6. 대표 화면 목업 캡처와 실제 캡처 비교 기록

이 순서를 지키면 “디자인은 있는데 코드 기준이 없음”, “로그인은 되는데 운영 callback이 다름”, “헬스체크는 200인데 DB가 죽음” 같은 웨딩픽의 반복 문제를 초기 단계에서 차단할 수 있다.
