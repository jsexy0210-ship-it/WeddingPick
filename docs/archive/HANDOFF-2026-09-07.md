## A·B — 인증 500 (최우선)

### 확인된 사실

- `POST /v1/auth/sessions` → 500, `POST /v1/auth/email/lookup` → 500
- `GET /v1/auth/providers` → 200 — 공개 API는 정상
- `OPTIONS /v1/auth/sessions` → 204 — **CORS 문제가 아니다**
- `GET /health` → 200 — DB 연결 자체는 정상

### 500이 401이 아니라는 점이 위치를 특정한다

`apps/api/src/errors.ts:6`이 `unauthenticated → 401`로 매핑한다. 카카오 검증 실패는
반드시 401로 나간다(`routes/auth.ts:122` catch). **500은 그 try/catch 바깥에서 난
예외**이고, 그 지점은 `routes/auth.ts:130`의 `signIn()` 하나뿐이다.

### 두 500의 공통 의존은 DB 스키마뿐이다

`email/lookup`은 카카오를 전혀 타지 않는다. 겹치는 것은 DB다.

```
email/lookup → findEmailAccount()          apps/api/src/auth/email-account.ts:19
   identity.identities · provider enum 'email'    ← 0075_identity_provider_email
   identity.email_credentials                     ← 0076_email_login

auth/sessions → signIn()                   apps/api/src/auth/sessions.ts:37
   identity.identities · birth_year, mobile       ← 0059_social_profile
   structured.users · display_name_user_set       ← 0059_social_profile
   identity.sessions
```

`signIn`의 SQL은 파라미터 12개 / 컬럼 12개로 일치한다 — **코드 결함이 아니라 실행
환경 문제다.**

### 유력 가설 (미확정)

**운영 DB가 코드보다 뒤에 있다.** 0059 이전이면 A·B 둘 다, 0075/0076만 없어도 B가 깨진다.

정황: main 배포의 DB Migrate가 **「적용할 마이그레이션 없음」**을 출력했다
([run 34074570844](https://github.com/jsexy0210-ship-it/WeddingPickl/actions/runs/34074570844)).
즉 GitHub `DATABASE_URL`이 가리키는 DB는 최신인데 운영은 깨졌다 →
**두 `DATABASE_URL`이 서로 다른 DB일 수 있다.**

`WeddingPickl` 서비스는 Blueprint 밖에서 별도 생성됐고 `DATABASE_URL`이
`infra/render-env.yml`에 없다(운영 대시보드에서 수동 관리).

### 다음 행동 — 추측으로 migrate 돌리지 말 것

운영 DB가 어느 것인지 모르는 상태에서 마이그레이션을 실행하면 엉뚱한 DB를 건드린다.

## C — 서버 로그가 남지 않던 문제 ✅

`apps/api/src/server.ts:41`이 `Fastify({ logger: false })`였다. 오류 처리기의
`app.log.error(error)`도, #98이 추가한 `request.log.warn(...)`도 **조용히 아무 일도
하지 않았다.** Render 런타임 로그에 요청·오류 줄이 0건이던 이유다.

- PR [#100](https://github.com/jsexy0210-ship-it/WeddingPickl/pull/100) 병합 (`b098e3c`)
- 기본 `level: warn`. `info`는 헬스체크가 매번 찍혀 오류가 묻힌다 — `LOG_LEVEL`로 조절
- `authorization`·`cookie` redact
- 오류 처리기를 `request.log`로 전환 — 어느 요청인지 함께 남는다
- `logger.test.ts` — 되돌리면 실패하는 것을 확인했다

> **정정:** #98 본문의 "이유가 서버 로그에 남는다"는 틀렸다. 로거가 꺼져 있어
> 기록되지 않았다. 그 상태로 로그를 찾은 시도는 전부 헛수고였다.

## D — `/health`가 스키마를 못 보던 문제 ✅

```ts
await context.pool.query('SELECT 1');   // 연결만 본다
```

테이블이 하나도 없어도 통과한다. **운영이 깨진 채로 헬스체크가 계속 초록이었던
이유**이고, Render 배포도 그래서 성공으로 끝났다.

`packages/db`에 `schemaState()`를 추가하고 `/health`가 함께 보고한다.

```json
{ "ok": true, "database": "ok",
  "schema": { "applied": 76, "expected": 76, "pending": [], "ok": true } }
```

- **밀려도 503을 주지 않는다.** 헬스체크가 실패하면 인스턴스가 계속 교체되어 정작
  확인하려던 것을 볼 수 없다. 상태만 알리고 판단은 사람이 한다.
- 조회가 실패해도 던지지 않고 값으로 돌려준다(`schema_migrations` 자체가 없는 DB).
- 테스트 2건 — 밀린 상태 보고 / 조회 실패 시 미던짐

## E — CORS 🔴

두 결함이 겹친다.

1. `infra/render-env.yml:47` — `CORS_ORIGINS`에 app-web·web의 onrender 출처 2개뿐.
   **관리자 서비스 출처와 커스텀 도메인이 없다.**
2. `apps/api/src/server.ts:47` — `methods`에 **PATCH가 없다.**

PATCH 라우트가 실재하고(`routes/admin.ts:982`, `:1001`, `:1242`) 관리자 화면 9곳이
실제로 보낸다(`app/admin/*.tsx`, `api/client.ts:564`·`607`·`659`). 브라우저 preflight에서
전부 막힌다.

커스텀 도메인은 **이미 활성**이다 — main CI의 Custom domains 단계가 `weddingpick.kr`·
`admin.weddingpick.kr` 모두 *"in use"* 를 반환했다. 미래 위험이 아니라 현재 차단.

## F·G — 401은 정상 동작

- **F** `GET /v1/me` 401 — 세션이 없으니 맞다. A의 후속 증상이다.
- **G** `POST /v1/me/signup` 401 — **설계대로다.** `routes/signup.ts:76,78`이 `auth`를
  건다. 이건 계정 생성 API가 아니라 **가입 마무리(동의)** API다. 통합정책 v3.13 §N-2가
  "소셜 로그인 성공만으로 가입을 끝내지 말라"고 정해 *세션은 있지만 가입 미완* 상태가
  존재하고, 그 상태를 읽는 경로다. 라우트·미들웨어 오연결이 아니다.

A가 풀리면 F·G는 저절로 사라진다. **401부터 고칠 것이 아니다.**
