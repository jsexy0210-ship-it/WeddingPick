# API를 싱가포르로 옮기는 절차 (승인 B)

**2026-09-11 대표님 결정: 국내 사용자 기준으로만 맞춘다. 해외 사용자는 고려하지 않는다.**

측정 근거는 `docs/perf/audit-2026-09-11.md`, 원본 기록은 `docs/perf/measured.md`에 있다.

---

## 1. 무엇을 옮기는가 — API 하나다. DB는 그대로 둔다

```
지금    사용자(한국) ──태평양──> API (Render · Ohio) ──태평양──> DB (Neon · Singapore)
뒤에    사용자(한국) ──────────> API (Render · Singapore) ─(같은 리전)─> DB (Neon · Singapore)
```

**DB는 이미 싱가포르에 있다.** 옮길 것이 없다. API만 따라가면 두 구간이 동시에 짧아진다.

### 왜 싱가포르인가

Render의 리전은 다섯이다 — Oregon · Ohio · Virginia · Frankfurt · **Singapore**.
**한국도 일본도 없다.** 아시아·태평양은 싱가포르 하나뿐이므로, 국내 기준이면 선택지가 하나다.

DB를 도쿄 같은 곳으로 옮기는 선택지는 **버린다.** Render에 도쿄가 없어서 API는 싱가포르에
남는데, 그러면 API↔DB가 다시 갈라진다 — 지금 고치려는 것이 바로 그 갈라짐이다.

---

## 2. 주소를 바꾸지 않는다 — 이름을 바꿔 끼운다

Render는 만들어진 서비스의 리전을 못 바꾼다. 새 서비스를 만들어야 한다. 그런데
**주소(`weddingpickl.onrender.com`)가 바뀌면 다음이 한꺼번에 깨진다.**

| 깨지는 것 | 왜 |
|---|---|
| **이미 설치된 앱** | `EXPO_PUBLIC_API_URL`이 빌드 시점에 박힌다(`apps/mobile/eas.json`). 이미 깔린 앱은 옛 주소를 계속 부른다 |
| **카카오 · 네이버 로그인** | 리다이렉트 URI가 각 콘솔에 등록돼 있다(`.../v1/auth/naver/callback`). 주소가 바뀌면 등록부터 다시 해야 한다 |
| 앱 웹 · 관리자 · 웹사이트 | `EXPO_PUBLIC_API_URL` · `WEDDINGPICK_API_URL` |
| 워크플로 7개 | keep-warm · api-health · db-inventory · main · perf-probe · android-apk |

그래서 **주소를 유지하는 쪽으로 간다.** 새 서비스를 임시 이름으로 만들어 확인한 뒤,
옛 서비스를 치우고 새 서비스의 이름을 옛 이름으로 바꾼다. Render의 `onrender.com`
주소는 서비스 이름을 따라오므로, 끝나고 나면 주소가 그대로다.

**이 방식이면 저장소에서 고칠 것이 없다.** 위 표의 일곱 가지를 아무것도 건드리지 않는다.

---

## 3. 절차

**대표님이 Render 대시보드에서 하셔야 하는 일이다.** Blueprint 동기화가 깨져 있어
(`render.yaml` 머리말) 이 저장소에서 서비스를 만들 수 없다.

```
1  싱가포르에 새 web service를 만든다
     이름      weddingpickl-sg   (임시)
     리전      Singapore
     런타임    Docker · Dockerfile ./Dockerfile · context .
     헬스체크  /health
     autoDeploy  일단 끈다 — 확인 전에 배포가 돌지 않게
     ※ 리전 드롭다운에서 free로 싱가포르가 열리는지 이때 보인다.
       안 열리면 유료가 되므로 거기서 멈추고 알려주신다(승인 C 사안).

2  환경변수를 옛 서비스에서 그대로 옮긴다
     DATABASE_URL 포함 전부. 원본은 infra/render-env.yml이고
     render-env-sync.yml이 표시 이름으로 서비스를 찾으므로,
     3단계에서 이름을 바꾼 뒤 그 워크플로를 한 번 돌리면 맞춰진다.

3  배포하고 확인한다 (아직 주소는 임시다)
     https://weddingpickl-sg.onrender.com/health 가 200이고 본문의
     schema.ok 가 true 인지. 여기서 아니면 되돌릴 것도 없다 — 그냥 지운다.

4  왕복이 실제로 줄었는지 본다  ← 판정은 여기서
     perf-probe 워크플로의 API 값을 임시 주소로 두고 한 번 돌린다.
     봐야 할 값은 «DB 왕복 1회»다. 200ms대가 한 자리 ms로 떨어지면 성공이다.

5  이름을 바꿔 끼운다
     옛 weddingpickl 의 이름을 weddingpickl-old 로 바꾼다
     새 weddingpickl-sg 의 이름을 weddingpickl 로 바꾼다
     → 주소가 새 서비스로 넘어온다

6  새 서비스의 autoDeploy 를 켠다 (branch=main)

7  옛 서비스는 하루 이틀 두었다가 지운다 — 되돌릴 자리로 남겨둔다
```

## 4. 무엇을 보고 성공이라 하는가

**절대 시간으로 판단하지 않는다.** 측정을 GitHub 러너(미국)에서 하기 때문에, API가
싱가포르로 가면 **러너가 재는 값은 오히려 올라간다.** 러너가 멀어져서다. 국내 사용자는
반대로 좋아진다.

그래서 판정은 **위치와 무관한 값**으로 한다.

```
DB 왕복 1회 = (/health 의 TTFB − / 의 TTFB) ÷ 2

지금    199 ~ 208ms
목표    한 자리 ms
```

`/`와 `/health`는 같은 서버가 같은 네트워크로 처리하므로, 둘의 차이에는 러너 위치가
들어가지 않는다. **이 값만 보면 된다.**

국내 체감은 대표님 컴퓨터에서 직접 재는 것이 가장 정확하다. 이사 전과 후에 한 줄씩.

```
curl -o /dev/null -s -w 'TTFB %{time_starttransfer}s\n' https://weddingpickl.onrender.com/health
```

## 5. 되돌리기

5단계까지는 옛 서비스가 그대로 살아 있다. 이름을 되돌리면 끝난다. 7단계에서 지우기
전까지는 되돌릴 수 있고, **그래서 바로 지우지 않는다.**

## 6. 예상 효과

| | 지금 | PERF-01만 | PERF-01 + 이사 |
|---|---|---|---|
| DB 왕복 1회 | 199ms (측정값) | 199ms | 한 자리 ms (추정값) |
| 업체 상세 · 서버 처리 | 1,048ms (측정값) | 약 435ms (추정값) | 수십 ms (추정값) |
| 사용자→API 구간 | 한국→미 동부 | 그대로 | 한국→싱가포르로 짧아짐 (추정값) |

**한국에서 각 리전까지의 실제 왕복은 재지 않았다.** 이 자리에서는 잴 수 없다 —
측정 러너가 미국에 있다. 방향만 확정이다: 싱가포르가 오하이오보다 한국에 가깝다.
숫자가 필요하면 4절의 한 줄 명령을 이사 전후로 쓰신다.

## 7. 이사로 풀리지 않는 것

**free 플랜의 CPU 0.1코어는 그대로다**(승인 C). DB를 한 번도 안 보는 `GET /`가
37ms 걸리는 데는 이 제약이 들어 있다. 리전을 옮겨도 이 값은 남는다.
