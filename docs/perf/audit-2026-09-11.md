# 로딩 성능 진단 — 2026-09-11

측정한 것과 코드에서 읽은 것을 갈라 적는다. **측정값**은 실제로 잰 숫자이고,
**구조**는 코드를 읽어 센 것이다. 재지 못한 것은 `측정 불가`로 적는다.

원본 측정 기록은 `docs/perf/measured.md`에 있다(워크플로가 직접 적는다).

## A. 근본 원인

측정 결과 **하나가 나머지를 전부 지배한다.**

### API에서 DB까지 한 번 다녀오는 데 199ms가 든다

이 API에는 서로 다른 두 경로가 있다.

```
GET /          DB를 한 번도 안 본다        (server.ts)
GET /health    SELECT 1 + 스키마 조회 2회  (server.ts)
```

둘은 같은 Node가 같은 네트워크로 처리한다. 사이에 있는 것은 **DB 질의 2회뿐**이다
(`schemaState`는 질의 하나다 — `packages/db/src/migrate.ts`). 그래서 차이가 곧 DB 왕복이다.

```
/health  TTFB p50   435.5ms
/        TTFB p50    37.2ms
        ────────────────────
         차이        398.3ms  ÷ 2 = 왕복 1회 199ms
```

두 번 쟀다. 첫 회(12:34 KST)는 262ms, 두 번째(12:54 KST)는 199ms다. 두 번째가 p95와 p50이
거의 붙어 있어(435.5 / 448.7) 더 믿을 만하다 — 첫 회는 러너 쪽이 흔들렸다. **아래 숫자는
전부 두 번째 회를 쓴다.**

### 왜 199ms인가 — 리전이 답이다

추정이 아니라 두 리전 이름으로 확정됐다(`docs/INFRA_ACCESS_AUDIT_2026-09-10.md`).

```
사용자(한국) ──태평양──> API (Render · Ohio, 미 동부) ──태평양──> DB (Neon · AWS Singapore)
```

**요청 하나가 태평양을 두 번 건넌다.** 미 동부↔싱가포르 왕복이 199ms 언저리라는 것과 맞는다.
같은 리전이었다면 한 자리 ms, 미국 안이었다면 60~70ms였을 값이다.

이 값이 근본 원인인 이유는 **배수로 작동하기 때문**이다. 화면 하나가 DB에 순서대로 다섯 번
물으면 그 화면은 199 × 5 = 995ms를 네트워크에만 쓴다. 실제로 그렇게 나온다.

### 그 위에 순차 질의가 쌓여 있다

| 화면 | 구조(코드에서 센 것) | 측정값 TTFB p50 |
|---|---|---|
| 업체 상세 | DB 질의 **5회를 순서대로** (`vendors.ts` `loadVendorDetail`) | **1,048.8ms** |
| 검색 | 질의 1회, 다만 일치 업체 수만큼 상관 서브쿼리 3개 | 444.4ms |
| 홈 전체(**비회원**) | 첫 묶음 하나로 끝난다 — 아래 주의 | 465.3ms |
| 홈 · 많이 확인된 곳 | 위 검색 질의와 같은 것 | 467.6ms |

업체 상세가 이 모형과 거의 정확히 맞는다.

```
37ms(DB 안 보는 바닥) + 5회 × 199ms = 1,032ms      실제 측정 1,048.8ms
```

**느린 질의를 찾는 문제가 아니라, 왕복 횟수를 줄이는 문제다.**

### 주의 — 홈의 무거운 쪽은 아직 재지 않았다

위 「홈 전체」는 **비회원** 값이다. probe가 토큰을 보내지 않았고, 토큰이 없으면
`routes/app.ts`의 bootstrap은 `member`를 null로 두고 **첫 묶음 하나로 끝내고 곧장 반환한다.**
담아둔 후보 · 웨딩픽 추천 · 반복되는 세션 조회는 아예 타지 않는다.

즉 **P0-2가 말하는 경로는 한 번도 측정되지 않았다.** 465.3ms를 홈의 값으로 읽으면 안 된다.
로그인 경로 측정은 다음 차례이고, probe에 토큰 자리를 만들어 뒀다(`API_TOKEN`).

### 전제 정정 — 운영 API는 아직 free 플랜이다

지시문에는 「현재 Render는 유료 플랜으로 전환된 상태」라고 되어 있으나, Render API로
읽은 실제 값은 다르다.

```
WeddingPick-운영 API 서버
  plan=free   region=ohio   branch=main   autoDeploy=yes   numInstances=1
```

free 웹 서비스는 CPU가 0.1코어다. DB를 한 번도 안 보는 `GET /`가 미국 안에서
왕복하는데도 TTFB p50 89.9ms가 나오는 것은 이 제약과 어긋나지 않는다(단정하지 않는다 —
`확인 필요`). `keep-warm.yml`이 10분마다 깨우고 있어 **잠드는 것 자체는 지금 막혀 있다.**

## C. 발견된 병목

### P0 — 사용자가 바로 겪는 것

**P0-1. 업체 상세가 DB에 순서대로 5번 묻는다** · 측정 1,048.8ms
`loadVendorDetail`(`apps/api/src/routes/vendors.ts:218`)에 `Promise.all`이 하나도 없다.
그중 `:253`(비교 견적) · `:313`(제보 금액) · `:340`(결제인증) · `:359`(이용 경험 점수)는
서로 기대지 않고 전부 `vendor.id`만 쓴다. 묶으면 왕복 5회가 2회가 된다 — 199 × 3 ≈ **597ms 감소(추정값)**.

**P0-2. 홈 한 번에 DB 질의 15~19회, 4단계 순차** · **미측정**
`routes/app.ts:31`이 `app.inject`로 다른 라우트를 부르는데, `inject`는 Fastify 생애주기를
통째로 다시 돌린다. 그래서 **같은 토큰의 세션 조회가 4번** 반복된다
(`auth/plugin.ts:195` → `auth/sessions.ts:220`). 다만 그중 둘은 같은 `Promise.all`
안에서 나란히 돌아 체감 시간에는 겹쳐 들어간다 — 순차로 얹히는 것은 약 2회다.

**이 경로는 재지 않았다.** probe가 토큰 없이 불러 비회원 경로만 측정됐다(A절 주의).
숫자를 적을 수 있게 되려면 로그인 토큰으로 다시 재야 한다.

**P0-3. 앱을 열 때 왕복 2회를 직렬로 기다린다**
`features/auth/session-recovery.ts:23`이 `/v1/me/signup`을 먼저 기다리고(`:23`),
그 뒤에 `/v1/me`를 또 기다린다(`:28`). `/v1/me/signup`은 캐시 금지 목록에 있어
(`api/client.ts:208`) 앱을 열 때마다 반드시 네트워크를 탄다.

같은 줄에서 `getAppBootstrap()`을 던져두지만(`:27`) 기다리지 않고 곧바로 `/v1/me`를
부른다. **bootstrap 응답에 `member`가 이미 들어 있고**, 클라이언트는 그것으로 `/v1/me`
캐시를 채울 줄도 안다(`api/client.ts:370`). 순서 때문에 그 자리가 죽어 있다.

**P0-4. 검색이 반환 행이 아니라 일치 업체 전체에 대해 서브쿼리를 돈다**
`vendors.ts:529`의 `count(*) OVER ()`가 `LIMIT`보다 먼저 전체 집합을 훑게 만든다.
그래서 `:521`(대표 이미지) · `:525`(비교 견적 수) · `:536`(제보 금액 배열) 세 서브쿼리가

최대 6,460ms였다(2회차는 러너가 안정적이라 꼬리가 나타나지 않았다 · p50 444ms · 최대 464ms).

### 측정 도구 (먼저 만든 것)

| 파일 | 무엇 |

서버에 응답시간 계측이 없다 — `apps/api/src/server.ts`에 `onResponse` 훅이 하나도 없다.
그래서 측정을 **밖에서** 하는 길을 먼저 냈다. 작업 컨테이너에서는 `onrender.com`으로

### PERF-01 — 업체 상세의 독립 질의 다섯을 한 번에 띄운다

`apps/api/src/routes/vendors.ts` `loadVendorDetail`

열람 이력 · 비교 견적 · 제보 금액 · 결제인증 · 이용 경험 점수는 서로의 답을 쓰지 않는다.
전부 업체 행 하나만 있으면 된다. 그런데도 하나씩 기다리고 있었다. `Promise.all` 하나로 묶었다.

```
고치기 전   업체 행 → 열람 → 견적 → 제보 → 결제 → 점수   왕복 6회 (비회원 5회)
고친 뒤     업체 행 → (나머지를 한꺼번에)                왕복 2회
```

**질의도 조건도 파라미터도 바꾸지 않았다 — 순서만 바꿨다.** 없는 업체의 404도 그대로
업체 행 바로 뒤에서 판정한다. 값을 쓰는 곳마다 흩어서 기다리지 않고 한자리에서 받는 이유는,
하나가 먼저 실패했을 때 남은 거절이 갈 곳을 잃기 때문이다.

**효과는 리전을 어떻게 두느냐에 따라 두 배 이상이 아니라 40배 갈린다.** 나눠 적는다.

| | 왕복 1회 | 업체 상세 예상 | 감소 |
|---|---|---|---|
| 지금 (Ohio ↔ Singapore) | 199ms | 1,048.8 → 약 435ms | **약 600ms** |
| API를 DB와 같은 리전에 두면 | 한 자리 ms | 약 52 → 약 43ms | 약 10ms |

즉 **리전이 붙으면 이 수정의 값은 거의 사라진다.** 그래도 넣는 이유는 리전 결정이 언제
날지 모르고, 옮긴 뒤에도 왕복을 줄인 것은 손해가 아니기 때문이다. 다만 **무엇을 먼저 할지를
정할 때는 리전이 먼저다.**

전부 추정값이다. 실제 값은 배포 후 재측정해야 하고, 그것은 승인 E다.

### PERF-05 — `coalesce(is_active, true)`를 `is_active`로

`apps/api/src/routes/vendors.ts` 2곳 · `apps/api/src/routes/recommendations.ts` 1곳

`vendors_is_active_idx`는 `WHERE is_active`인 부분 인덱스인데
(`packages/db/migrations/0047_vendor_data_quality.sql`), 호출부가 `coalesce()`로 적고 있어
Postgres가 그 안을 들여다보지 못했다. 검색·홈·추천이 공통으로 쓰라고 만든 인덱스가
세 경로 모두에서 죽어 있었다.

컬럼은 `NOT NULL DEFAULT true`다(실제 스키마에서 확인 · NULL 행 0개). 그래서 뜻이 같다.

200,000행을 넣고 플래너에 직접 물어 확인했다.

```
coalesce(is_active, true)  →  Seq Scan on v
is_active                  →  Bitmap Heap Scan  ->  Bitmap Index Scan on v_is_active_idx
```

### 하지 않은 것

- **PERF-02(앱 진입)** · **PERF-03(검색 `count(*) OVER ()`)** · **PERF-04(bootstrap 중복 세션)** 는
  이번에 넣지 않았다. 아래 「남은 것」에 이유를 적었다.
- 로딩 화면과 로더 컴포넌트는 건드리지 않았다.

기준값을 먼저 받아두고(고치기 전 API 72 suite · 932건 전부 통과) 같은 환경에서 다시 돌렸다.
결과는 PR 본문에 적는다.

## G. 추가 권고 — 코드로 풀리지 않는 것

**G-1. API를 DB와 같은 리전(싱가포르)으로 옮긴다. 이것 하나가 가장 크다.**

지금은 요청 하나가 태평양을 두 번 건넌다.

```
사용자(한국) ──태평양──> API (Ohio, 미 동부) ──태평양──> DB (Singapore)
```

**옮기는 쪽은 API다.** API를 싱가포르로 옮기면 두 구간이 동시에 짧아진다 — API↔DB는 같은
리전이라 한 자리 ms가 되고, 사용자→API도 태평양을 건너지 않는다. **DB를 미국으로 옮기면
API↔DB만 풀리고 사용자 구간은 오히려 나빠진다** — 사용자는 한국에 있다.

왕복 199ms가 한 자리 ms가 되면 위 E표의 거의 모든 값이 5~10배 줄어든다. **코드 수정으로
얻을 수 있는 것을 전부 합친 것보다 크다.** 승인 B라 제안까지만 한다.

**G-2. 운영 API가 free 플랜이다.** CPU 0.1코어에서 돈다. 승인 C. `keep-warm.yml`이 잠드는
것은 막고 있으나 CPU 제약은 그대로다. 리전을 옮기려면 어차피 서비스를 다시 만들어야 하므로
G-1과 함께 판단하는 것이 맞다.

**G-3. ~~DB 리전 확인~~ — 확정됐다.** Neon은 **AWS Singapore**다
(`docs/INFRA_ACCESS_AUDIT_2026-09-10.md`). 접속 문자열을 열지 않고 확인했다. 그 문서가
남겨둔 「왕복 지연을 계측해야 한다」는 숙제를 이번 측정이 닫는다 — 199ms다.

**G-4. 로그인 사용자 bootstrap을 재야 한다.** 지금 P0 중 가장 무거운 자리인데 숫자가 없다.
probe에 `API_TOKEN` 자리를 만들어 뒀고, 워크플로는 `PERF_PROBE_TOKEN` 시크릿을 읽는다.
시험용 계정 토큰을 그 이름으로 넣으면 다음 실행부터 잰다. **토큰 값은 로그 · 커밋 · PR 본문에
찍지 않는다** — probe는 curl 인자로만 넘기고 출력에 담지 않는다(확인함).

**G-5. 응답시간 계측을 서버에 넣는 것을 검토한다.** 지금은 밖에서만 잴 수 있어
`인증 / 로직 / DB / 외부 API`를 나눠 보지 못한다. 넣는다면 비밀 값과 사용자 식별자를
남기지 않게 만든다. 배포가 필요하므로 승인 E다.

## 남은 것 — 왜 이번에 안 했는가

**PERF-02 앱 진입의 직렬 왕복 2회.** `session-recovery.ts:23`이 `/v1/me/signup`을 기다린
뒤 `/v1/me`를 또 기다린다. bootstrap 응답에 `member`가 들어 있으니 그것을 기다리면 왕복
하나가 빠진다.

다만 **`optionalUser`는 대기 계정을 403이 아니라 비로그인처럼 다룬다**(`auth/plugin.ts`
「대기 계정은 비로그인처럼 둔다」). 그래서 bootstrap은 대기 계정에도 200에 `member: null`을
준다. `member`가 비었다는 것만으로 「가입 대기」로 읽으면, 안쪽 `/v1/me`가 일시적으로
실패했을 때도 같은 모양이 되어 **가입을 마친 사람을 설정 화면으로 되돌린다.** 그 자리를
`getSignupState()`로 한 번 더 가려야 안전하고, 로그인 분기를 건드리는 일이라 시험을 갖춘
별도 작업으로 뺀다. `session-recovery.ts:22`의 「/me와 bootstrap은 가입 전에는 403이다」는
주석은 `/v1/me`에만 맞고 bootstrap에는 맞지 않는다 — 그 줄도 같이 고쳐야 한다.

**PERF-03 검색의 `count(*) OVER ()`.** 걷어내면 서브쿼리가 반환 행에만 걸린다. 다만 그
값이 응답의 전체 건수라 페이지 표시와 얽힌다. **API 계약에 닿는 변경**이라 따로 다룬다.

**PERF-04 bootstrap의 중복 세션 조회.** 같은 토큰을 네 번 조회하는 것은 맞다. 다만 그중
둘은 `Promise.all` 안에서 나란히 돌아 **체감 시간에는 거의 얹히지 않는다** — 그 묶음은
가장 느린 쪽(업체 검색)이 시간을 정한다. DB 부하는 줄지만 사용자가 기다리는 시간은
거의 그대로다. 인증 경로를 건드리는 값에 비해 얻는 것이 작아 뒤로 미룬다.

**P1-5 인덱스 추가는 승인 A다.** 마이그레이션 파일까지만 만들고 적용하지 않는다.
번호는 0200번대를 쓴다(main이 0160까지 찼다).

**로딩 화면 자체는 손대지 않는다.** `features/loading/delayed-loader.tsx`와 로더
컴포넌트는 다른 세션(`claude/owner-orders-5`)이 2026-09-11 대표 지시로 고치는 중이다.
이 작업은 「무엇을 보여줄까」가 아니라 「왜 기다리는가」만 다룬다.
