## 기준 문서 — 계열이 둘이다

**번호가 둘 다 `v3.x`지만 같은 줄이 아니다.** 서로 다른 문서 계열이고 각자 최신판이 있다.
번호만 보고 큰 쪽이 최신이라고 읽으면 안 된다.

```
통합정책        최상위 운영 · 제품 · 데이터 정책     현행 v3.15 (2026-09-05 갱신)
디자인 핸드오프  화면 · 값 · 용어 · 화면 목록        현행 v3.27 (2026-09-10)
```

**다투는 자리는 정해져 있다.**

| 무엇을 정하나 | 이기는 문서 |
| --- | --- |
| 색 · 크기 · 간격 · 문구 · 화면 구성 · 용어 | 디자인 핸드오프 `current/` |
| 서비스 범위 · 운영 원칙 · 데이터 정책 · 광고 · 탈퇴 | 통합정책 v3.15 |
| 저장소에서 지키는 구현 규칙 | 뿌리의 `CLAUDE.md` |

화면 쪽이 다투면 핸드오프가 이긴다 — 「무조건 최신 핸드오프 md 기준으로 바꾼다」가 사용자
지침이다(2026-09-08). 그것은 **화면 영역에 대한 지침**이지 통합정책을 밀어내는 것이 아니다.
통합정책 v3.15는 그 계열의 최신이고 운영·정책 범위에서 여전히 최상위다.

읽는 순서는 이렇다.

```
1  CLAUDE.md                                   저장소 고정 규칙
2  design-handoff/current/CHANGELOG.md 맨 위    화면 · 값 · 용어의 현행
3  design-handoff/current/  SPEC · PROJECT_RULES · screens.json · tokens.json
4  통합정책 v3.15                                운영 · 제품 · 데이터 정책
```

**버전을 기억으로 말하지 않는다.** 화면에 손대기 전에 `CHANGELOG.md` 맨 위를 그때그때 읽는다
(2026-09-10 사용자 지침). 이 README에 적힌 v3.27과 그 파일이 어긋나면 파일이 맞다.

다른 문서와 어긋나면 **다른 문서를 고친다.** 기준을 화면에 맞추지 않는다.

## 과거 버전 번호를 어떻게 읽을 것인가

코드 주석과 마이그레이션에는 `v2.0`, `v3.1`, `v3.5` 같은 번호가 많이 나온다.
**그 번호들은 "이 규칙이 언제 정해졌는가"를 적어둔 것이지, 지금 기준이 그 버전이라는
뜻이 아니다.** 규칙을 왜 그렇게 두었는지 다음 사람이 되짚을 수 있어야 해서 남긴다.

읽는 법:

- `v2.0 K-6이 폐기했다` — 그 버전에서 내려진 결정의 기록이다. 유효하다.
- `v3.10 §3` — v3.10에서 정해진 규칙이다. 뒤 버전이 다르게 정했으면 뒤가 맞다.
- `v3.13 §O-1` — v3.13에서 정해진 과거 위치를 가리킨다. 내용이 v3.15와 다르면 v3.15를 따른다.
- `v3.14 §O` — v3.14에서 정해진 규칙이다(v3.15는 v3.14에 T장을 더한 것으로, §O는 바뀌지 않았다).
- `v3.15 §T` — 현재 모바일 RN 구현 범위·플래너/광고 제휴 삭제 기준을 가리킨다.
- 두 주석이 서로 다른 말을 하면 **v3.15가 맞다.** 오래된 쪽을 고친다.

새 주석에 과거 버전을 현재 기준처럼 적지 않는다. 지금 정해지는 것은 v3.15다.
