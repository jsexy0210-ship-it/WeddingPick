## 원칙

관리자는 데이터를 일일이 처리하지 않고 **AI 운영을 감독**합니다. 문제 없는 날에는 개별 큐를 열 필요가 없는 것이 목표입니다.

내부 화면이므로 사용자 화면 용어 규칙(AI · 데이터 금지)을 적용하지 않습니다. `AI`, `데이터`, `검증`, `반려` 같은 운영 용어를 그대로 씁니다.

**로그인 지속** — 신뢰기기 + 장기 보안 세션. IP는 보조 신호일 뿐이고, IP가 바뀌어도 신뢰기기면 로그아웃하지 않습니다. 비밀번호를 로컬에 평문 저장하지 않습니다. 재인증 조건은 4가지 — 직접 로그아웃 / 비밀번호·권한 변경 / 신뢰기기 해제 / 비정상 접근 탐지.

## 광고 실운영 전환 게이트 · WP-ADM-034

```
테스트 전체 오픈 → 판단 데이터 충족 → GPT 독립 분석
→ Claude 독립 분석 → 보고서 2건 → 사용자 최종 결정 → 실운영
```

종료일을 고정하지 않고 **판단 데이터 충족 여부**로 분석 시점을 정합니다. 두 AI의 판단이 갈려도 합의하지 않고 그대로 제출합니다. **오픈 스위치는 사람만 조작합니다.**

현재 상태 — 테스트 중 · 판단 데이터 미달 · 사용자 오더 대기

## 공통 규칙

**지금 사람이 봐야 할 것이 맨 위.** 상단 배너가 상태를 먼저 말하고 그 아래가 상세입니다. 문제 없으면 초록, 확인할 것이 있으면 주황, 조치가 필요하면 빨강.

**빈 상태가 정상 상태.** 「확인할 것이 없어요」를 반드시 그립니다. 큐가 비어 있는 것이 실패가 아니라 목표입니다.

**숫자는 `tabular-nums`.** 세로로 자리가 맞아야 훑을 수 있습니다.

**표는 카드 안에서만 가로 스크롤.** 화면 전체가 흔들리지 않습니다.

**위험한 조작은 한 번 더.** 긴급 중지 · 변경 복구는 확인 카드를 띄우고, 무엇이 바뀌는지 항목으로 보여준 뒤 진행합니다.

**강조색은 화면당 4곳 이하.** 코랄은 활성 메뉴 · 주요 CTA · 브랜드 마크 · 강조 수치에만 씁니다.

## 관리자 계정 · 권한 등급 · WP-ADM-053 (2026-09-10 신설)

시안이 없다. 위 26화면과 `html/20-admin.dc.html` · `html/21-admin.dc.html`(두 파일은 내용이
같다) · `html/22-admin-ops.dc.html`에 이 화면이 없는 것을 확인했고, 지어내는 대신 **v3.27 공통
규칙과 기존 관리자 표·배지 꼴을 그대로 따르는 최소 화면**으로 만들기로 정했다(2026-09-10 사용자
확인). 시안이 나오면 이 절이 아니라 시안이 기준이 된다.

### v3.27 공통 규칙 4가지를 어떻게 지키는가

| 규칙 | 이 화면에서 |
|---|---|
| 지금 봐야 할 것이 맨 위 | 상단 배너가 **콘솔이 잠길 수 있는 상태**를 먼저 말한다 — 부트스트랩 계정으로 들어와 있거나 슈퍼 관리자가 한 명뿐이면 주황 |
| 빈 상태가 정상 상태 | 문제 없으면 배너가 「확인할 것이 없어요」(초록). 표가 비면 첫 계정을 만들라고 말한다 |
| 표는 카드 안에서만 스크롤 | 표를 카드로 감싸고 가로 스크롤을 카드 안에 둔다 |
| 위험한 조작은 한 번 더 | 아래 |

**계정 생성 · 등급 변경 · 끄고 켜기는 누른 즉시 서버로 가지 않는다.** 무엇이 바뀌는지 항목으로
보여준 뒤 「진행」을 눌러야 나간다. 「정말 하시겠어요?」는 무엇이 바뀌는지 말해 주지 않아서,
읽는 사람이 자기가 무엇을 누르는지 모른 채 누른다. 예를 들어 뷰어를 운영자로 올릴 때:

```
아이디        newcomer
등급          뷰어 → 운영자
관리자 쓰기   막힘 → 허용
계정 관리     못 함 → 못 함
```

항목의 문구는 등급표(`ROLE_POWER`) 한 곳에서만 나온다. 표의 설명과 확인 카드가 각자 문구를
들고 있으면 언젠가 어긋나고, 어긋난 쪽을 보고 등급을 정하게 된다.

### WP-ADM-020(사용자 · 계정)과 다른 화면이다

| | WP-ADM-020 계정 관리 | WP-ADM-053 관리자 계정 |
|---|---|---|
| 무엇의 계정인가 | 서비스 이용자 | 관리자 콘솔 |
| 사이드바 묶음 | 사용자 | 시스템 |
| 경로 | `/admin/users` | `/admin/admins` |
| 볼 수 있는 사람 | 관리자 전부 | 슈퍼 관리자만 |

이름이 둘 다 「계정」이라 헷갈리기 쉽다. **이름을 다르게 하는 것보다 자리를 떼어 놓는 편이
확실해서**, 두 화면을 다른 묶음에 두었다. 기존 「계정 관리」의 이름과 자리는 그대로다.

### 등급 셋

| 등급 | 읽기 | 관리자 쓰기 | 계정 관리 |
|---|---|---|---|
| 슈퍼 관리자 | ○ | ○ | 생성 · 등급 변경 · 켜고 끄기 |
| 운영자 | ○ | ○ | 못 함 (목록도 안 보임) |
| 뷰어 | ○ | **못 함** | 못 함 |

### 막는 곳은 화면이 아니라 서버다

**화면에서 단추를 숨기는 것은 권한이 아니다.** 뷰어 토큰으로 `PATCH`를 직접 부르면 그대로
통하기 때문이다. 관문(`requireOperatorUser`)이 세션에서 등급을 읽고, `GET`·`HEAD`가 아닌
요청은 뷰어에게 403을 준다.

막는 자리를 쓰기 라우트마다 적지 않고 관문 한 곳에 둔 이유는 **다음 라우트를 더하는 사람이
빠뜨릴 수 있기 때문이다.** 빠뜨린 것은 고장으로 보이지 않아 아무도 모른다. 관문에서 가르면
새 라우트가 기본으로 닫힌 채 태어난다. `admin-write-guard.test.ts`가 저장소의 관리자 라우트를
전수로 훑어 뷰어가 전부 막히는지 확인한다 — 라우트가 늘면 시험이 저절로 따라간다.

### 슈퍼 관리자 보호

- 남이 슈퍼 관리자를 내리거나 끌 수 없다. 슈퍼가 여럿일 때 서로를 내릴 수 있으면 먼저
  누르는 쪽이 이기는 경주가 된다.
- **마지막 슈퍼 관리자는 자기 자신도 내릴 수 없다.** 그러면 아무도 계정 관리에 들어갈 수
  없다. 라우트가 막고, 마이그레이션 0102의 트리거가 한 번 더 막는다 — 라우트는 하나 더 생길
  수 있고 psql로 직접 고치는 날도 온다.
- 등급을 올리는 것은 슈퍼 관리자만. 운영자가 자기를 슈퍼로 올릴 수 있으면 등급이 없는 것과
  같다.

### 비밀번호

첫 비밀번호는 **만드는 사람이 직접 입력한다.** 서버가 만들어 화면에 한 번 보여주는 방식을
쓰지 않는 이유는, 그러면 「한 번만 보여주고 다시 못 본다」를 화면이 지켜야 하기 때문이다.
직접 입력하면 지킬 것이 없다.

저장되는 것은 scrypt 해시뿐이고, 응답·로그·감사기록 어디에도 원문이 돌아가지 않는다.

### 환경변수 계정의 운명 — 부트스트랩 전용

`ADMIN_LOGIN_ID` · `ADMIN_PASSWORD_HASH`는 **DB에 켜져 있는 슈퍼 관리자가 하나도 없을 때만**
통한다. 슈퍼 관리자가 하나 생기는 순간 그 길은 닫히고, 밖에서 보면 아이디가 틀린 것과 같은
답이 온다.

그렇게 정한 이유는 두 가지를 함께 지키기 위해서다. 지워 버리면 슈퍼 관리자를 전부 꺼뜨린 날
아무도 못 들어가고, 그냥 두면 환경변수를 아는 사람이 등급 체계를 우회한다.

**이 경로는 권한을 주지 않는다.** 부트스트랩 계정이 슈퍼 관리자로 보이는 것은 표에 줄이
생겨서가 아니라 환경 설정에서 파생된 것이고, 진짜 슈퍼 관리자가 생기면 저절로 사라진다.
로그인 라우트는 `admin_accounts`에 한 줄도 쓰지 않는다.

### 감사기록

계정 생성 · 등급 변경 · 켜고 끄기가 `structured.decisions`에 남는다(`workflow='admin_account'`).
`structured.audit_log`라는 표는 없고, 감사 기록 화면(WP-ADM-052)이 실제로 읽는 것이 이 표다 —
새 표를 만들지 않은 값어치가 여기 있다. 그 표의 `evidence_refs`는 `{kind, id}` 꼴만 통과시키므로
**비밀번호가 새어 들어갈 자리가 구조적으로 없다.**
