# 관리자 로그인 — 설계 결정

2026-09-10 사용자 결정 — **관리자는 별도 로그인 계정을 쓴다.**

## 지금 상태 (2026-09-10 실측)

관리자 로그인 화면이 **없다.** 링크를 누르면 이렇게 된다:

```
/admin  →  admin/index.tsx 가 인증 확인 없이 /admin/queue 로 리다이렉트
        →  admin/_layout.tsx 는 사이드바 + Slot 뿐, 인증 게이트 없음
        →  admin/_api.ts 가 일반 사용자 세션 토큰을 그대로 붙임
        →  서버(requireOperatorUser)가 403
        →  화면은 떴는데 전부 오류. 「로그인하세요」라고 말하는 자리가 없다
```

핸드오프 `screens.json`의 관리자 화면 26개(`WP-ADM-001~`) 목록에는 로그인 화면이 없다.
**목록에만 없고 시안에는 있다** — `html/21-admin.dc.html`의 `isLogin` 갈래가 그것이다
(2026-09-10 관리자 핸드오프로 확인). 번호가 없을 뿐 화면은 정해져 있다.

## 결정

**아이디 · 비밀번호로 로그인하는 관리자 전용 경로를 만든다.** 시안이 그렇게 그려져
있고(`21-admin.dc.html`), 사용자도 같은 결정을 확인했다(2026-09-10).

v3.25가 이메일 로그인을 폐기하고 「카카오 단일 로그인」으로 확정했지만, 그것은
**사용자 화면의 결정이다.** 관리자는 그 결정의 예외로 둔다 — 운영자는 앱 사용자와
같은 사람일 필요가 없고, 카카오 계정에 운영 권한을 매다는 것보다 분리하는 편이
권한을 회수하기 쉽다.

## 로그인 지속 — **보류** (2026-09-10 사용자 결정)

ADMIN.md는 신뢰기기 + 장기 보안 세션을 정했다. **지금은 만들지 않는다** — 사용자가
사무실 PC에서 쓰는 중이고, 자택 환경에서 이어서 정하기로 했다.

보류한 것:

- 신뢰기기 등록과 해제
- IP가 바뀌어도 유지되는 장기 보안 세션
- 재인증 조건 네 가지(직접 로그아웃 · 비밀번호나 권한 변경 · 신뢰기기 해제 ·
  비정상 접근 탐지)

**그동안은 일반 운영자 세션을 쓴다**(`config.operatorSessionTtlDays`). 만료되면 다시
로그인한다.

**시안의 「이 PC에서는 계속 로그인 유지」 체크박스는 그리지 않는다.** 눌러도 아무 일도
하지 않는 조작을 화면에 두면, 관리자는 유지된다고 믿고 자리를 뜬다 — 없는 편이 낫다.
신뢰기기를 만들 때 시안대로 되살린다.

## 지켜야 할 것

### 비밀번호 원문은 저장소에 없다

**어떤 경우에도 원문을 커밋 · 문서 · 로그 · PR 본문에 적지 않는다.** 서버가 아는 것은
scrypt 해시뿐이다(`identity.email_credentials`가 이미 `scrypt$<salt>$<key>` 꼴을 쓴다 —
0076 참고).

아이디와 해시는 환경변수로 온다. 저장소에는 **이름만** 적는다:

```
ADMIN_LOGIN_ID
ADMIN_PASSWORD_HASH
```

`infra/render-env.yml`의 `secrets` 목록에 이름을 더하면 GitHub Secrets의 같은 이름에서
Render로 흘러간다. 값을 이 파일에 적지 않는다.

### 해시는 사람이 만든다

원문을 인자로 받지 않는 작은 도구를 둔다 — 인자로 받으면 셸 기록에 남는다.

```
npm run admin:password-hash    # 표준입력으로 받아 해시만 찍는다
```

### 실패는 무엇이 틀렸는지 말하지 않는다

「아이디가 없어요」와 「비밀번호가 틀렸어요」를 가르면 아이디가 있는지 확인하는 데
쓰인다. 한 문장으로 답한다.

### 시도를 제한하고 남긴다

무차별 대입을 막는다. 실패도 성공도 감사 로그(`audit-log`)에 남긴다 — 관리자 권한이라
누가 언제 들어왔는지 나중에 물을 일이 생긴다.

### 세션은 운영자 TTL을 쓴다

`config.operatorSessionTtlDays`가 이미 있다. 일반 사용자보다 짧다.

## 만들 것

| 무엇 | 어디 |
| --- | --- |
| 로그인 화면 | `apps/mobile/src/app/admin/login.tsx` |
| 인증 게이트 | `apps/mobile/src/app/admin/_layout.tsx` — 운영자 세션이 없으면 로그인으로 |

`admin/index.tsx`의 무조건 리다이렉트를 먼저 없앤다 — 인증을 확인하기 전에 내부 화면으로
보내는 줄이 지금 문제의 시작이다.

## 화면 번호가 어긋난다

`ADMIN.md`의 26개와 코드의 라우트 32개가 맞지 않는다. 어느 라우트가 어느 `WP-ADM`
번호인지 대조하는 일이 먼저다 — 번호를 모른 채 화면을 고치면 시안의 어느 칸을 고친
것인지 말할 수 없다.

## 링크 미리보기(OG 카드) 관리 — WP-ADM 링크 미리보기

카카오톡·슬랙에 주소를 붙이면 뜨는 카드의 제목·설명·그림을 관리자에서 고친다. 화면은 `/admin/og-card`.

### 저장과 반영은 다른 일이다

웹은 정적 HTML 생성기다. 저장하면 표(`structured.site_meta`)가 바뀔 뿐이고, 사이트에 나가려면 다시 빌드해야 한다. 그래서 단추가 둘이다.

| 단추 | 하는 일 |
|---|---|
| 저장 | 표에만 적는다 |
| 저장 후 반영하기 | 저장하고 웹 배포를 건다 |

저장이 실패하면 배포를 걸지 않는다 — 걸어봐야 옛 문구가 다시 나갈 뿐이다.

### 「반영됨」을 추측하지 않는다

저장 시각과 배포 시각을 비교해 「반영됨」이라고 말하지 않는다. 배포는 실패할 수 있고, 정적 사이트는 실패하면 **옛 빌드를 계속 내보낸다**. 시각만 보면 안 바뀐 화면을 바뀐 것으로 읽는다.

대신 화면이 공개 사이트를 직접 읽어 `og:title`을 꺼내 보여준다. 못 읽으면 「확인하지 못했어요」라고 적는다 — 「바뀌지 않았다」가 아니다.

### 손이 필요한 것 하나

「반영하기」가 당길 **배포 훅 주소**가 있어야 한다.

1. Render → `weddingpick-web` → Settings → Deploy Hook에서 주소를 만든다
2. GitHub Secrets에 `RENDER_WEB_DEPLOY_HOOK`으로 넣는다
3. `infra/render-env.yml`이 이미 그 이름을 선언해 두었으므로 env sync가 API로 흘려보낸다

없으면 저장은 되고 「반영하기」만 무엇이 빠졌는지 말한다.

**Render API 키를 쓰지 않는다.** API 키는 계정의 모든 서비스를 건드릴 수 있어 인터넷에 열린 서버에 두기에는 넓다. 배포 훅은 웹 서비스 하나만 다시 배포하는 주소다.

### 비워두면 기본값

칸을 비우면 그 항목은 `spec/strings.ko.json`의 값으로 돌아간다. 표에는 **바꾼 것만** 남는다 — 손대지 않은 항목까지 복사해 두면 나중에 spec이 바뀌어도 낡은 사본이 계속 이긴다.

그림 주소를 비우면 저장소에 든 기본 그림(`weddingpick-og.png`)을 쓴다. 그 그림의 글자는 `spec/strings.ko.json`의 `webLanding.og`에서 오고, 바꾸는 방법은 `apps/web/README.md`에 있다.

## 구현 완료 — 2026-09-10

「관리자 링크를 눌러도 로그인 화면이 안 나온다」는 보고의 원인은 화면이 없어서가 아니라 **인증 경로 자체가 없어서**였다. `/admin` → `admin/index`가 확인 없이 `/admin/queue`로 보내고 → 화면이 관리자 API를 부르고 → 서버가 403을 주는데 → 그 뜻을 말해 줄 자리가 없어 오류 경계가 「잠시 문제가 생겼어요」를 띄웠다.

### 만든 것

| 자리 | 하는 일 |
|---|---|
| `POST /v1/admin/login` | 아이디·비밀번호 대조 후 세션 발급 |
| `admin/login.tsx` | 시안(`21-admin.dc.html` `isLogin`)대로 520 + 어두운 오른쪽 판 |
| `admin/_layout.tsx` | 토큰 없으면 로그인으로. 로그인 화면은 사이드바 없이 홀로 |
| `admin/_session.ts` | 관리자 토큰을 사용자 토큰과 **다른 자리**에 둔다 |
| `admin/_api.ts` | 401·403이면 토큰을 지우고 `AdminUnauthorized`를 던진다 |
| `0100_admin_identity.sql` | `identity_provider`에 `admin` 추가 |

### 왜 표를 새로 만들지 않았나

`identities → users → sessions`가 이미 세 가지를 하고 있다 — 같은 사람이 다시 로그인해도 새 계정을 만들지 않고, 토큰 원문을 저장하지 않고, 운영자에게 더 긴 세션을 준다. 관리자용으로 다시 만들면 셋 중 하나를 빠뜨리게 된다.

### 로그인이 곧 권한은 아니다

`POST /v1/admin/login`이 하는 일은 「이 사람이 그 아이디의 주인인가」까지다. 운영 권한(`is_operator`)은 **CLI로만** 켠다.

```sh
npm run retention --workspace @weddingpick/api -- --operator <user-id>
```

라우트가 권한까지 줄 수 있으면 그 한 곳이 뚫렸을 때 권한도 함께 넘어간다. 그래서 첫 로그인은 계정만 만들고 403으로 돌아오며, **그 응답이 실행할 명령과 user-id를 알려준다.**

### 손이 필요한 것 둘

1. 해시를 만들어 `ADMIN_PASSWORD_HASH`로, 아이디를 `ADMIN_LOGIN_ID`로 GitHub Secrets에 넣는다

   ```sh
   npx tsx scripts/admin-password-hash.ts
   ```

   원문을 인자로 넘기지 않는다 — 셸 기록(`~/.bash_history`)과 프로세스 목록(`ps`)에 남는다.

2. 첫 로그인 뒤 응답이 알려주는 `--operator` 명령을 한 번 실행한다

둘 다 없으면 로그인은 **어떤 비밀번호도 받아들이지 않는다.** 설정이 빠진 것을 통과로 읽지 않는다.

### 밀어보기 방어

아이디가 하나뿐인 공개 경로라 아무 제한이 없으면 비밀번호를 기계로 밀어볼 수 있다. 15분 창에서 5회를 넘기면 응답을 늦춘다(최대 8초). 프로세스 안에 두는 것이라 재시작하면 지워지고 서버가 여럿이면 각자 센다 — 완전한 방어가 아니라 **속도를 죽이는 것**이 목적이다.

아이디가 틀려도 비밀번호를 끝까지 대조한다. 아이디에서 바로 돌아오면 응답 시간만으로 「이 아이디는 있다」를 알 수 있다.

### 첫 로그인 뒤 권한 켜기 — 워크플로

CLI가 유일한 길이면 서버 셸에 못 들어가는 사람은 403에서 멈춘다. 로그인은 되는데 들어갈 수는 없는 상태다.

Actions → **관리자 운영 권한** → Run workflow → 사용자 id를 넣는다. 그 id는 첫 로그인 실패 응답이 알려준다.

권한을 내릴 때도 같은 워크플로에서 「켜지 않고 내린다」를 켠다.

여전히 **로그인 경로는 권한을 주지 않는다.** 사람이 다른 문으로 켜는 것이고, 그 문이 CLI에서 워크플로로 하나 늘었을 뿐이다.
