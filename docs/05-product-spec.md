## 1. Phase 1 범위 (Verify)

사업계획서 37번 Phase 표의 1단계만 구현 대상으로 잡는다. North Star Metric이 "월간 인증 견적·계약 분석 건수"이므로, **촬영 → 분석 → 결과 확인 → 인증** 단선 퍼널을 끝까지 동작시키는 것이 Phase 1의 완료 조건이다.

**포함**
- 문서 입력: 카메라 촬영 / 사진 선택 / PDF 선택
- AI 문서 분석 (문서분류 · OCR/문서이해 · 항목 추출 · 개인정보 탐지)
- 저신뢰 항목 사용자 확인 단계
- 실제 가격 비교 (중앙값 기준, 표본 수·기준기간 표시)
- 내 웨딩 저장 (견적/가계약/계약 이력)
- 검증 등급 L0~L2 부여 및 배지 표시
- 원본 문서 보관·자동삭제 파이프라인

**제외 (Phase 2 이후)**
- 업체 비교(최대 3곳), 플래너 비교 → Phase 2
- 배우자 연결, 우리 웨딩 공동 의사결정 → Phase 3
- 박람회, 외부 캘린더/지도, 주차, 방문 브리핑 → Phase 4
- 광고, Lead, B2B Data → Phase 6

**업체 자료 확보**: 지방행정 인허가 데이터(공개 자료)로 업체를 등록한다. 특정 사이트를 긁어오지 않는다(사업계획서 20번). 영업 중인 곳만 넣고, 지역은 시도·시군구까지만, 자료의 갱신일자를 마지막 확인일로 남긴다. 등록하면 그 이름으로 기다리던 견적이 자동 연결된다. 출처는 앱에 표시한다(아래 8번). `결정 필요`: 데이터셋의 공공누리 유형 확인.

**Cold Start 대응**: 사업계획서 32번 기준으로 인증자료 100건 전까지는 시장 중앙값을 **표시하지 않는다**(제품 원칙 2 — AI가 시장 데이터를 만들어내지 않는다). 그 구간에서 사용자에게 제공되는 가치는 "내 견적의 구조화 + 계약조건 체크리스트 + 추가비용 후보 목록"이다. `결정 필요`: 업체·상품 단위로 최소 표본 몇 건부터 중앙값을 노출할지.

## 3. 데이터 모델

원본 문서 28번 원칙("원본·개인정보·구조화 데이터·통계 데이터는 분리 관리")을 스키마 레벨에서 강제한다. 아래는 논리 모델이며 `결정 필요`: 실제 DB 선정 후 물리 스키마 확정.

**타입과 계산 규칙은 [`packages/domain`](../packages/domain)에, PostgreSQL 스키마는 [`packages/db`](../packages/db)에 코드로 있다** (2026-08-28). 둘 다 호스팅·프레임워크에 기대지 않으므로 백엔드를 무엇으로 정하든 그대로 쓴다. 아래 표기와 코드가 어긋나면 코드가 맞다.

DB에서는 세 영역을 스키마로 나눴다 — `originals` / `structured` / `stats`. 분리를 권한 단위로 만들 수 있다.

### 3.1 원본 영역 (분리 저장, 자동삭제 대상)
```
RawDocument
  id, ownerUserId, storageKey, mimeType, pageCount
  uploadedAt, retentionUntil, deletedAt, deleteAttempts
  status: uploaded | analyzed | scheduled_delete | deleted | delete_failed
```
- 저장소는 구조화 데이터와 **물리적으로 분리**된 버킷
- `retentionUntil` 경과 시 자동삭제. 실패 시 `delete_failed`로 남기고 운영 알림 (서비스정책서 4번)
- `결정 필요`: 보관 기간 일수 (서비스정책서 미확정 항목)

### 3.2 구조화 영역 (마스킹 후)
```
Quote                      // 견적/가계약/계약 공통 문서 분석 결과
  id, weddingId, rawDocumentId(nullable — 삭제 후 null)
  docType: official_price | quote | pre_contract | revised_quote | contract | final_payment
  vendorId, plannerId, productName
  totalAmount, discountAmount, contractDate, servicePeriod
  verificationLevel: L0 | L1 | L2 | L3 | L4
  source: user_input | ai_extraction | vendor_official | public_data
  createdAt, confirmedAt

QuoteLineItem
  id, quoteId, kind: included | excluded | additional_candidate
  label, amount, note

ContractTerm
  id, quoteId, category: cancellation | refund | penalty | schedule | other
  text, riskFlag

ExtractionField           // AI 추출 원자 단위 + 신뢰도 (확인 단계의 근거)
  id, quoteId, fieldPath, value, confidence
  needsConfirmation, confirmedByUser, userCorrectedValue

Vendor
  id, category: wedding_info_company | hall | sdm | planner_agency | snap | goods | etc
  name, region, officialInfo(jsonb), sourceType, lastVerifiedAt

Planner
  id, vendorId(nullable), name, regions[], affiliations[]

Wedding                   // Phase 3에서 배우자 연결 시 members 2인으로 확장
  id, ownerUserId, partnerUserId(nullable), weddingDate(nullable)

User
  id, authProvider, createdAt, deletedAt
```

### 3.3 통계 영역 (별도 저장, 재계산 대상)
```
PriceStat
  vendorId, productKey, docType, periodStart, periodEnd
  sampleCount, median, p25, p75, p90
  minVerificationLevel                 // L2 이상만 집계
  recomputedAt
```
p90은 가격 판단 4단계의 마지막 경계라 함께 저장한다 (`packages/domain/src/pricing.ts`).
- 사업계획서 27번 원칙에 따라 **중앙값·분포·판단은 전부 서버 계산**. AI 출력은 여기 직접 들어가지 않는다. `computePriceStat`이 그 계산이다.
- 판단 표현 4단계(낮은 편 / 비슷한 수준 / 다소 높은 편 / 높은 편)는 사분위 기준으로 구현했다. 임계값은 여전히 `결정 필요`이며 `packages/domain/src/policy.ts` 한 곳에 모여 있다.
- `sampleCount`와 `periodStart~periodEnd`는 노출 시 **항상 동반 표시** (사업계획서 9번). `PriceStat` 타입이 이 셋을 한 덩어리로 묶어 떼어놓기 어렵게 했다.
- 표본이 `minimumSampleCount`에 못 미치면 `computePriceStat`은 통계 대신 `null`을 준다 — 데이터가 부족하면 시장가격을 만들지 않는다(제품 원칙 2).

## 4. 문서 분석 파이프라인 (제안)

```
① 업로드          앱 → 서명 URL → 원본 버킷 (RawDocument.uploaded)
② 문서 분류        AI: 견적서 / 가계약서 / 계약서 / 기타
③ 개인정보 탐지     AI: 이름·연락처·주민번호 일부·서명 위치 탐지
④ 마스킹          구조화 데이터 생성 전 마스킹 적용
⑤ 항목 추출        AI: 업체·플래너·상품·가격·할인·계약일·포함/별도·추가비용 후보·취소환불
⑥ 업체 매칭        AI 후보 제시 → 서버가 Vendor 확정
⑦ 신뢰도 판정      필드별 confidence → needsConfirmation 플래그
⑧ 사용자 확인      A-07. 핵심 필드는 예외 없이 통과 필요
⑨ 저장/집계        Quote 확정 → PriceStat 재계산 큐
⑩ 보관/삭제        retentionUntil 도달 시 원본 자동삭제
```

**원칙 준수 체크**
- ③④는 오픈 초기 사람 재검토 1단계 유지 (서비스정책서 4번)
- ⑨의 집계는 `verificationLevel >= L2`만 반영 (서비스정책서 2번)
- AI 호출 비용은 문서 단위로 기록 — 사업계획서 35번 "AI 비용관리" 자동화 대상

## 5. 기술 스택

1인 운영·90~95% 자동처리(사업계획서 35번) 목표를 전제로, 운영 부담이 가장 적은 조합을 고른다.
**모바일 앱만 확정(2026-08-28, Expo SDK 57로 스캐폴드 완료)**. 나머지는 제안 상태다.

| 영역 | 제안 | 근거 |
|---|---|---|
| 모바일 앱 ✅ | React Native + Expo SDK 57 (TypeScript, expo-router) | 카메라·파일 선택·푸시가 표준 모듈로 해결됨. iOS/Android 동시 대응. OTA 업데이트로 1인 운영 부담 감소 |
| 웹 | Next.js 정적 랜딩 | 웹 역할은 소개·다운로드·정책 게시로 한정 (서비스정책서 9번). 앱 기능 재현 금지 |
| 백엔드 ✅ | Fastify (TypeScript) + PostgreSQL, 상시 구동 | 스키마·타입 공유. 중앙값·분위수 집계에 관계형이 맞고, 1인 운영에 관리 요소가 적다 |
| DB | PostgreSQL | 중앙값·분위수 집계와 jsonb를 동시에 요구하므로 관계형이 적합 |
| 원본 저장소 | 객체 스토리지 (구조화 DB와 분리된 버킷, 수명주기 정책으로 자동삭제) | 28번 분리 관리 원칙 + 자동삭제 요건 |
| 문서 AI | Claude (문서 이해 + 구조화 출력) | 문서분류·항목추출·계약조건 파악을 한 번에. 출력은 스키마 고정 |
| 배치/큐 | 통계 재계산, 원본 삭제, 인증 1차판정 | 사업계획서 35번 자동화 목록 |

| 1 ✅ | 레포 구조 + 앱 스캐폴드 + CI | 5개 탭이 뜨는 빈 앱. typecheck·lint·web 번들이 CI에서 통과 |

| 3 🚧 | 촬영·업로드 + 원본 저장소 분리 | 원본이 분리 버킷에 저장, retentionUntil 기록<br>촬영·업로드·보관기간 기록·삭제 예정일 표시까지 동작한다. **보관 일수가 정해지지 않아 기본값이 없다** — 값을 넣지 않으면 retentionUntil이 비고 자동삭제도 돌지 않는다. 임의의 숫자로 남의 계약서를 지우거나 무기한 보관하는 쪽을 조용히 고르지 않으려는 것이다 |
| 4 🚧 | AI 분석 (분류·추출·신뢰도) | 실제 견적서 샘플에서 핵심 필드 추출<br>워커와 정확도 측정 하네스 완료. 실제 업체 견적서로 돌려보는 것만 남았다 |
| 5 ✅ | 확인 단계 + 결과 화면 | 핵심 필드 확인 없이 저장 불가<br>API·DB 트리거·화면까지 완료 |
| 6 🚧 | 개인정보 탐지·마스킹 + 자동삭제 배치 | 보관기간 경과 원본이 실제로 삭제, 실패 시 알림<br>탐지(종류 기록)와 삭제 작업 완료. 보관 일수가 정해져야 실제로 돈다 |
| 7 ✅ | 검증 등급 + 인증 신청 | L0~L2 부여 및 배지 표시<br>등급 체계·배지·신청 화면(A-13)·접수 API 완료. 목표 등급에 맞는 증빙이 없으면 접수하지 않는다. 승인은 사람이 증빙을 확인해야 나며, 자동승인은 스키마가 막는다 |
| 8 ✅ | PriceStat 집계 + 가격 비교 화면 | 표본 부족 시 중앙값 미노출 동작 확인<br>API·화면 완료. 표본이 모자라면 이유를 보여준다 |
| 9 🚧 | 정책 화면 + 웹 랜딩 | 약관·개인정보처리방침·분석 안내 게시<br>랜딩([`apps/web`](../apps/web))과 앱 안내 화면 완료. **분석 안내는 랜딩에서 게시했다.** 약관·개인정보처리방침은 확정본이 없어 본문을 싣지 않고 상태만 적는다 |

6번(마스킹·자동삭제)은 법률검토 체크리스트에서 최우선 자문 대상이므로, **자문 결과가 나오기 전에는 실제 사용자 문서를 수집하지 않는다.**

## 7. 공개 기준과의 대조

견적서의 조건이 공개된 소비자 보호 기준과 어떻게 다른지 알려준다. 코드는
[`packages/domain/src/consumer-standards.ts`](../packages/domain/src/consumer-standards.ts)에 있고,
출처와 마지막 확인일을 함께 둔다(사업계획서 25번).

| 기준 | 내용 | 출처 |
|---|---|---|
| 예식업 취소 위약금 | 90일 전 계약금 환급 / 89~60일 10% / 59~30일 20% / 29일 이후 35% | 공정거래위원회 소비자분쟁해결기준 |
| 스드메 필수 옵션 | 사진 파일 구입비·드레스 피팅비·메이크업 얼리스타트비는 기본 제공에 포함 | 공정거래위원회 결혼준비대행업 불공정약관 시정 (18개 업체) |

**법률 판단이 아니다.** 이용약관 제3조에 따라 계약의 적법성을 판단하지 않고, "기준은 이런데
이 조항은 이렇다"만 보여준다. 가계약 검증(사업계획서 8번)이 말하는 "데이터 기반 확인 사항"이
바로 이것이다.

계산은 서버가 하고 앱은 문장을 받아 보여주기만 한다 — 규칙이 바뀌면 한 곳만 고친다.

## 8. 자료 출처 표시

바깥에서 가져온 자료는 어디서 왔는지 밝힌다. 공공데이터는 공공누리 유형과 무관하게
출처 표시가 공통 조건이다. 목록은
[`packages/domain/src/data-sources.ts`](../packages/domain/src/data-sources.ts) 한 곳에 있다.

| 자료 | 제공기관 | 쓰이는 곳 |
|---|---|---|
| 지방행정 인허가 데이터 | 행정안전부 | 업체 이름·지역·영업 여부 |
| 소비자분쟁해결기준 (예식업) | 공정거래위원회 | 취소 위약금 기준과의 대조 |
| 결혼준비대행업 불공정약관 시정 | 공정거래위원회 | 기본 제공이어야 하는 항목 확인 |

표시되는 곳:

- **안내 화면(A-17) "자료 출처"** — 자료명·제공기관·확인일·쓰이는 곳을 모두 보여준다.
- **분석 결과 화면** — 업체 정보가 공공데이터에서 온 경우에만 "업체 정보 출처: …"를 붙인다.
  문장은 서버가 만들어 `vendor.sourceNote`로 내려주고, 앱은 받아서 그대로 그린다.
  사용자 문서에서만 나온 업체는 밝힐 바깥 출처가 없으므로 `null`이다.

**이용허락범위(공공누리 유형)는 아직 비워둔다.** 데이터셋 페이지에서 확인하기 전에는
적지 않는다 — 확인하지 않은 유형을 화면에 띄우면 지키지도 않을 약속을 하는 것이다.
마지막 확인일은 함께 적어, 기관이 자료를 고쳤을 때 얼마나 오래된 것인지 보이게 한다
(사업계획서 25번).

```
GET  /v1/auth/providers             A-02 쓸 수 있는 로그인 방법
POST /v1/auth/sessions              A-02 로그인
DELETE /v1/auth/sessions            A-14 로그아웃
```

- 가격은 표본 수·기준 기간과 한 객체로만 나간다.
- 비교 불가 응답에는 이유가 반드시 붙는다.
- 인증 접수 응답에는 승인 상태가 존재하지 않는다 — 계약에 `'received'`밖에 없다.
- 문장은 서버가 만들어 내려준다(`vendor.sourceNote`, `lineItem.standardNote`, `term.standardNote`). 앱은 코드로 판단하지 않고 받은 문장을 그린다.
- 로그인 제공자 목록은 개발용 대체 경로를 `isDevelopmentStandIn`으로 밝힌다. 개발용 문을 실제 로그인인 척 그려두면 그 빌드가 어디까지 나가는지 아무도 모른다.

`결정 필요`: Apple·Kakao 클라이언트 ID — 실제 제공자 토큰 검증이 여기에 달려 있다.

## 10. 웹 랜딩

[`apps/web`](../apps/web)이 정적 HTML 한 장을 만든다. 프레임워크도 런타임 자바스크립트도
없다 — 소개 한 장에 필요한 것은 글과 링크뿐이고, 자바스크립트를 켜지 않아도 읽을 수
있어야 한다.

```
npm run build --workspace @weddingpick/web   # apps/web/dist/index.html
```

**글은 도메인에서 가져온다.** 랜딩에 숫자를 따로 적어두면 기준이 바뀔 때 한쪽만 고쳐지고,
그때 어느 쪽이 우리가 지키는 약속인지 알 수 없게 된다. 그래서 아래는 모두
`@weddingpick/domain`에서 온다:

| 랜딩의 내용 | 출처 |
|---|---|
| 분석 안내 7가지, 결과 고지 문구 | `analysis-notice.ts` — 앱 안내 화면·결과 화면이 같은 것을 쓴다 |
| 확인 단계와 가격 비교 반영 여부 | `verification.ts` |
| 최소 표본 수 | `policy.ts` |
| 예식업 취소 위약금 기준 | `consumer-standards.ts` |
| 자료 출처와 확인일 | `data-sources.ts` |
| 약관·정책의 게시 상태 | `policies.ts` — 앱 정책 화면(A-15)이 같은 것을 쓴다 |

테스트가 이 연결을 지킨다: 도메인 값이 랜딩에 실제로 실렸는지, 게시 상태와 링크가
어긋나지 않는지, 확인하지 않은 공공누리 유형을 적지 않았는지를 확인한다.

**문의처(`WEDDINGPICK_CONTACT_EMAIL`)는 비어 있다.** 없으면 없다고 적는다 — 그럴듯한
주소를 지어 붙이면 사람들이 받지 않는 곳으로 편지를 보낸다. `결정 필요`.

## 11. 업체 검색 (A-16 · A-17)

**우리가 아는 것만 보여준다.** 검색 결과에 순위는 없다 — 그런 것을 만들려면 재는
무언가가 있어야 하는데 없다. 담기는 것은 업체가 있다는 사실, 분류와 지역, 그리고
확인된 계약이 몇 건 모였는지다.

업체 상세에는 이용점수가 붙는다(19번). 검색 목록에는 붙이지 않는다 — 점수로 줄을
세우면 그게 순위가 되고, 확인된 후기 다섯 건짜리 업체가 그 자리를 차지한다.

| 화면의 것 | 어디서 오나 |
|---|---|
| 이름 맞추기 | DB의 `structured.normalize_vendor_name` — 앱·서버가 따로 흉내내면 색인과 어긋나 "있는데 안 나오는" 업체가 생긴다 |
| 확인된 계약 수 | `structured.comparable_quotes` 뷰 — 등급·확인 조건이 뷰 안에 있다 |
| 상품별 중앙값 | `computePriceStat` — 표본이 모자라면 `null`이라 상품 자체가 응답에서 빠진다 |
| 지역 필터 목록 | 자료에 실제로 있는 시도만. 전국 목록을 박아두면 눌러도 아무것도 안 나오는 필터가 생긴다 |

**0건을 숨기지 않는다.** "확인된 계약 자료가 아직 없습니다"라고 적는다. 숨기면 자료가
없는 업체와 싼 업체가 같은 얼굴이 된다.

**표본이 모자란 상품은 응답에 넣지 않는다.** 중앙값 없는 상품 이름만 내려보내면 화면이
그것을 가격으로 그릴 여지가 생긴다. 대신 업체 상세가 "몇 건 모였지만 아직 모자라다"고
말한다.

검색은 pg_trgm GIN 색인을 쓴다(마이그레이션 0007). 두 글자 이하 검색어에는 색인이 쓰이지
않고 훑는다 — 느려지되 결과는 같다.

### 3곳 비교

한 번에 세 곳까지. 넘으면 표가 읽히지 않는다 (`MAX_COMPARED_VENDORS`). 좁은 화면에서
세 칸짜리 표는 아무것도 읽히지 않으므로, 항목을 위에서 아래로 두고 각 항목 안에서 업체를
나란히 놓는다.

**단서가 결과와 한 응답으로 나간다.** 계약에서 `caveats`가 `min(1)`이라 비어 보낼 수 없다.
따로 받아오게 두면 화면이 표만 그리고 이 말을 빠뜨릴 수 있는데, 그러면 우리가 만든 표가
사업계획서 2번이 꼽은 "비교의 어려움"을 되레 가리게 된다.

| 언제 | 무슨 말을 붙이나 |
|---|---|
| 늘 | 금액만으로는 비교하기 어렵다 — 웨딩홀은 식사·주차·교통·시설, 스드메는 품질과 추가비용 |
| 분류가 섞였을 때 | 어떤 분류가 섞였는지 이름을 들어 알린다 |
| 시도가 다를 때 | 어느 지역들인지 들어 알린다 |
| 자료가 없는 곳이 있을 때 | 몇 곳인지와 함께 "자료가 없다는 뜻이지 싸거나 비싸다는 뜻이 아니다" |

늘 붙는 것은 마지막 하나뿐이다. 매번 같은 경고를 늘어놓으면 아무도 읽지 않는다.
규칙은 [`packages/domain/src/vendor-comparison.ts`](../packages/domain/src/vendor-comparison.ts)에
있고 테스트가 지킨다.

### 플래너 탐색

사업계획서 11번은 플래너를 독립 비교대상으로 본다. 그런데 업체와 결정적으로 다른 점이
하나 있다 — **플래너는 개인이다.**

견적서에서 읽어낸 플래너 이름은 사용자가 자기 계약을 확인받으려고 올린 문서에서 나온
것이다. 그것을 누구나 검색할 수 있는 목록에 싣는 것은 수집한 목적과 다른 이용이다.
그래서 공개를 스키마에서 막았다 (마이그레이션 0008):

| 무엇을 | 어떻게 |
|---|---|
| 기본값 | `listing_status`가 `private`. 넣는 쪽이 잊어도 공개되지 않는다 |
| 공개 근거 | `public_data`(공개된 자료에 실려 있음) 또는 `vendor_official`(업체·본인이 밝힘)만. **`ai_extraction`은 CHECK 제약이 거부한다** |
| 노출 중단 | `withdrawn`이 되면 트리거가 되돌리기를 막는다. 공개 자료를 다시 가져와도 되살아나지 않는다 |
| 검색이 보는 곳 | `structured.listed_planners` 뷰 하나. 조건이 뷰 안에 있어 경로가 빠뜨릴 수 없다 |

비공개 플래너의 상세도 404다 — "있지만 안 보여준다"와 "없다"를 구분해주지 않는다.

화면에는 늘 두 가지가 함께 나간다: **왜 이 사람이 검색에 나오는지**(`listingBasis`)와
**원하지 않을 때 어떻게 하는지**(`withdrawalNotice`). 계약에서 둘 다 `min(1)`이라 비워
보낼 수 없다. 개인 이름을 목록에 싣고 이유를 적지 않으면, 본인도 다른 사람도 그것을
따져볼 방법이 없다.

노출 중단 요청은 문의 창구(아래 12번)로 들어오고, 운영자가 처리하면서 실제로 내린다.

`결정 필요`: 공개 근거를 만드는 절차. 지금은 규칙만 있고 넣는 쪽이 없어 목록이 비어 있다.
- 공개 자료에서 플래너를 가져오는 작업 (업체 인허가 자료에는 플래너가 없다)
- 본인·업체가 등록을 요청하는 창구

## 12. 문의 창구

여러 화면이 "알려주세요", "확인해보세요"라고 말한다. 받을 곳이 없으면 그 말은 지키지
않을 약속이다. 앱의 **MY → 문의하기**가 그 말을 받는다.

| 받는 것 | 어디서 들어오나 |
|---|---|
| 업체 이의 제기 | 문의 화면 (서비스정책서 6번 반론권) |
| 플래너 노출 중단 | 플래너 상세의 "검색에서 내려주세요" — 대상이 채워진 채 열린다 |
| 업체 정보 정정 | 업체 상세의 "업체 정보가 다릅니다" |
| 분석 결과가 다릅니다 | 분석 결과 화면의 "원본과 다릅니다" |
| 개인정보 | 문의 화면 |
| 그 밖의 문의 | 문의 화면 |

**필요 이상으로 받지 않는다.** 이름도 주소도 묻지 않고, 회신할 방법 하나만 받는다.
로그인 사용자는 앱으로 답을 받으므로 그것도 비워둘 수 있다. 다만 답할 방법이 아예 없는
문의는 스키마가 거부한다(`inquiry_has_reply_route`) — 받아만 두고 답할 수 없으면 접수한
척한 것이다.

**접수와 처리를 분리한다.** 응답 계약에 `'received'`밖에 없고, 결론에는 사람과 시각이
남아야 한다(`decision_has_reviewer`). 서비스정책서 6번의 "증빙 재검토"는 자동으로
일어나지 않는다. 처리 이력은 `structured.inquiry_events`에 남는다 — 상태만 덮어쓰면 반복
이의제기 패턴을 볼 수 없다(서비스정책서 6-5). 접수 자체도 트리거가 이력의 첫 줄로 남긴다.

**처리는 사람이 명령으로 한다.**

```bash
npm run inquiries --workspace @weddingpick/api -- --list
npm run inquiries --workspace @weddingpick/api -- --show <id>
npm run inquiries --workspace @weddingpick/api -- --review <id> --by <user-id>
npm run inquiries --workspace @weddingpick/api -- --answer <id> --by <user-id> \
  --resolution "..." [--withdraw-planner]
```

`--withdraw-planner`를 붙여야만 플래너가 실제로 내려간다. 되돌릴 수 없는 조작이라
(11번의 트리거) 결론을 낼 때 명시적으로만 한다.

**처리 기한은 아직 정해지지 않았다.** 서비스정책서 미확정 항목 "반론 접수 후 처리 영업일
기준"이다. 정해지기 전에는 날짜를 약속하지 않고 "아직 정하지 못했다"고 말한다
(`INQUIRY_RESPONSE_BUSINESS_DAYS`가 `null`). 정해지면 그 한 값만 채우면 앱과 랜딩의
문구가 함께 바뀐다.

**앱 밖에서 연락할 방법은 아직 없다.** 앱을 쓰지 않는 사람 — 특히 검색에서 자기 이름을
발견한 플래너 — 에게는 그게 유일한 길이어야 하는데, 이메일 주소가 정해지지 않았다.
랜딩(10번)이 그 사실을 그대로 적는다. `결정 필요`.

## 13. 배우자 연결 (A-18)

사업계획서 2번이 꼽은 다섯 문제 중 하나가 "부부 공동 의사결정"이다 — 견적·후보·일정·의견이
메신저와 캡처 이미지에 흩어져 함께 결정하기 어렵다.

**연결은 양쪽이 각각 동의해야 이뤄진다.** 한쪽이 초대를 만들고(동의 1), 다른 쪽이
**무엇이 공유되는지 보고 나서** 받아들여야(동의 2) 연결된다. 코드를 넣으면 바로 연결되지
않고 공유 범위를 한 번 거치는 이유다 — 동의는 무엇에 동의하는지 알 때만 동의다.

공유 범위는 [`packages/domain/src/partner-link.ts`](../packages/domain/src/partner-link.ts)에
있고 초대·수락 양쪽 화면이 같은 목록을 본다.

| | 내용 |
|---|---|
| 함께 보는 것 | 정리된 견적·계약 내용, 가격 비교 결과, 문서 업로드일과 원본 삭제 예정일 |
| 공유하지 않는 것 | **원본 문서 파일 자체**, 상대방의 계정 정보, 자료 확인 신청에 낸 증빙 |

원본과 개인정보를 자동 공유하지 않는 것은 이용약관 제5조다. 웨딩 상세 응답에는 상대의
식별자가 들어갈 자리가 없고, 누가 누구인지는 `isMe`로만 구분한다.

**링크가 새어나가도 남의 계약이 열리지 않게:**

- 코드는 해시로만 저장한다. DB가 유출돼도 그것만으로 들어올 수 없다 — 세션 토큰과 같다.
- 만들 때 한 번만 내려간다. 잃어버리면 새로 만든다.
- 기한이 있다(`INVITE_TTL_HOURS`, 72시간). 영원히 살아 있는 링크는 언젠가 낯선 사람을 들인다.
- 한 웨딩에 살아 있는 초대는 하나(부분 유니크 색인). 새로 만들면 이전 것이 죽는다 —
  취소한 줄 알았던 링크가 살아 있으면 안 된다.
- 쓸 수 있는 조건은 `structured.usable_wedding_invites` 뷰 안에만 있다. 받아들이는 경로가
  조건을 빠뜨릴 수 없다.
- 한 계정은 한 웨딩에만 속하고, 한 웨딩에는 두 사람까지다.

**어느 쪽이든 끊을 수 있다.** 한쪽이 붙잡아둘 수 있으면 그건 연결이 아니라 구속이다.
끊기 전에 무엇이 어떻게 되는지 보여준다. 끊으면 연결 시각도 함께 사라진다 — 트리거가
둘을 같이 움직여 "없는 사람이 언젠가 연결돼 있었다"는 상태를 만들지 않는다.

`결정 필요`: 초대를 링크로 보낼지. 지금은 코드를 공유 시트로 보내고 받는 쪽이 앱에서
넣는다. 딥링크를 쓰려면 도메인이 정해져야 한다(10번).

## 14. 인증 심사 (A-13의 뒷면)

A-13은 신청을 **접수만** 한다. 등급은 사람이 증빙을 보고 나서야 오른다
(서비스정책서 7번). 그 "사람이 보는" 자리가 없으면 신청은 쌓이기만 하고
L1~L4는 영원히 붙지 않는다. 시장 대표가격은 L2 이상만 쓰므로, 심사가 없으면
가격 비교 자체가 서지 않는다.

### 도구

```
npm run verifications --workspace @weddingpick/api -- --list
npm run verifications --workspace @weddingpick/api -- --show <id>
npm run verifications --workspace @weddingpick/api -- --review <id> --by <user-id>
npm run verifications --workspace @weddingpick/api -- --approve <id> --by <user-id> --note "..."
npm run verifications --workspace @weddingpick/api -- --reject <id> --by <user-id> --reason "..."
```

`--by`는 심사한 사람의 사용자 id다. 결론에는 예외 없이 사람이 남는다.

### 승인이 통과해야 하는 것

승인은 되돌리기 어렵다 — 등급이 오르는 순간 그 문서는 다른 사람이 보는 중앙값에
들어간다. 그래서 접수 때 한 번 거른 조건을 승인 직전에 다시 본다
(`canApprove`, `packages/domain/src/verification.ts`). 접수와 승인 사이에 증빙이
지워졌거나 문서 등급이 다른 경로로 올랐을 수 있기 때문이다.

| 조건 | 막는 것 |
| --- | --- |
| 심사자 ≠ 신청자 | 자기 증빙을 자기가 확인하는 것 |
| 목표 등급에 맞는 증빙이 있다 | 계약인증(L2)에 견적서만 내고 통과하는 것 |
| 이미 그 등급이 아니다 | 심사자가 헛일하는 것 |

세 조건은 도메인 코드와 DB 제약 양쪽에 있다. 도구를 거치지 않고 SQL로 직접
건드려도 스키마가 막는다.

### 스키마가 지키는 것 (0011)

- `decision_has_reviewer_who_is_not_the_requester` — 승인이든 반려든 결론에는
  신청자가 **아닌** 심사자가 남는다.

  0002의 `approved_is_not_self_service`는 이름이 "self service가 아니다"이고
  주석이 "자동승인을 스키마에서 막는다"였는데, 실제로 검사한 것은
  `decided_by IS NOT NULL` 하나였다. 신청자가 자기 id를 넣으면 그대로 통과했다.
  이름이 약속한 것을 제약이 지키지 않고 있었고, 0011에서 바로잡았다.
- `structured.verification_events` — 접수·심사 시작·승인·반려가 남는다.
  접수는 트리거가 자동으로 남기므로 사람이 잊어서 비는 일이 없다. 나머지는
  `human_action_has_actor`가 사람을 요구한다.
- `structured.pending_verification_requests` — 심사가 필요한 신청을 목표 등급과
  **실제로 낸 증빙**과 함께 보여준다. 심사자가 봐야 하는 것은 신청 한 줄이 아니라
  그 둘이 맞는지다.

### 밀리면 알린다 — 7일

심사가 열려 있는 동안 그 증빙 원본은 파기되지 않는다(15번). 그래서 심사가
밀리는 것은 심사만의 문제가 아니라 **개인정보가 그만큼 오래 남는다는 뜻**이다.

**접수 후 7일**부터 밀린 것으로 본다 (2026-08-28 확정). 접수한 날부터 세고,
심사를 시작했다고(`in_review`) 시계를 되돌리지 않는다 — 시작은 결론이 아니고,
신청한 사람이 기다리는 것은 결론이다.

파기 알림과 같은 규칙으로 운영자에게 푸시가 간다. 건수만 담고, 왜 급한지를
한 줄 덧붙인다.

```
인증 심사가 밀려 있습니다
3건이 아직 결론이 나지 않았습니다. 가장 오래된 것은 11일째입니다.
심사가 끝나야 그 원본의 파기 일정이 시작됩니다.
```

**두 알림은 따로 센다.** 하나로 합쳐 세면 파기가 줄어드는 사이 심사가 쌓여도
"숫자가 그대로"라 조용해진다. 알림 기록(`operator_alerts`)이 종류를 컬럼으로
들고 있고, 늘었을 때와 오래 방치됐을 때만 보내는 규칙은 공유한다.

```
npm run verifications --workspace @weddingpick/api -- --backlog
```

`--list`에도 밀린 건은 `(9일째)`로 표시된다. `--backlog`를 따로 봐야만 알 수
있으면, 안 보는 날에는 모른다.

일수는 SQL의 `structured.verification_backlog_days()`와 도메인의
`VERIFICATION_POLICY.backlogDays` 두 곳에 있고, 테스트가 둘이 같은지 본다.

### 아직 없는 것

**심사자가 누구인가.** 도구는 사용자 id를 받을 뿐, 그 사람이 심사 권한이 있는지
확인하지 않는다. 지금은 서버에 접근할 수 있는 사람만 이 명령을 돌릴 수 있다는
것이 유일한 통제다. 운영 인력이 정해지면 역할을 스키마에 넣어야 한다.

## 15. 보관 점검

서비스정책서 4번은 자동삭제 실패에 **"알림 및 수동 처리 프로세스"**를 요구한다.
지우는 쪽은 있었지만 실패한 것을 사람에게 보여주는 쪽이 없었다. 개인정보가
보관 기간을 넘겨 남아 있는데 아무도 모르는 상태가 가능했다.

### 조용히 남는 두 가지

| 상태 | 어떻게 되나 | 드러나나 |
| --- | --- | --- |
| 삭제 실패 | 다음 차례에 다시 시도된다 | `delete_attempts`가 오른다 |
| 페이지 기록 없음 | **시도조차 되지 않는다** | 아무것도 오르지 않는다 |

두 번째가 문제다. `expired_documents`는 지울 스토리지 키를 함께 주려고
`raw_document_pages`와 INNER JOIN을 한다. 그래서 페이지 기록이 없는 문서는
목록에 아예 오르지 않는다. 보관 기간이 지나도 영원히 남고, 삭제 작업은 실패조차
하지 않으므로 `delete_attempts`도 오르지 않는다.

지금 업로드 경로는 문서와 페이지를 한 트랜잭션에서 넣으므로 정상적으로는
생기지 않는다. 그러나 "지금은 안 생긴다"는 것은 안전장치가 아니다. 0012의
`unreachable_expired_documents` 뷰가 이 상태를 드러낸다 — 비어 있는 것이 정상이고,
비어 있지 않으면 그 자체가 알림이다.

### 알림

워커가 보관 정리를 한 바퀴 돌 때마다 손이 필요한 문서가 있는지 함께 본다.
있으면 매번 말한다. 시끄러운 편이 낫다.

### 보관 기간은 검증 완료 후 30일

**검증이 끝난 날로부터 30일** (2026-08-28 확정).

"검증 완료"는 원본이 더 이상 필요하지 않게 된 시점이다. 셋 중 **가장 나중**이
기준이 된다.

| 무엇 | 왜 |
| --- | --- |
| 업로드 | 바닥. 이게 없으면 분석되지 않고 버려진 업로드가 영원히 남는다 |
| 사용자 확인 (A-07) | 핵심 필드를 사람이 확인한 시점 |
| 인증 심사 결론 | 승인·반려가 난 시점 |

그리고 **아직 결론이 나지 않은 인증 신청의 증빙이면 셈이 시작되지 않는다.**
심사가 늦어지는 사이 증빙 파일이 지워지면 심사자가 확인할 근거를 잃기 때문이고,
기준을 업로드에서 검증 완료로 옮긴 이유가 바로 이것이다.

### 그래서 파기 시각은 저장하지 않는다

업로드 때 한 번 찍고 끝나는 값이 아니다. 확인과 심사가 끝날 때마다 달라진다.
저장해두면 어딘가에서 다시 계산하는 것을 잊고, **화면에 적힌 날짜와 실제로
지워지는 날이 달라진다.** 그래서 `originals.document_retention_schedule` 뷰가
그때그때 계산하고, 컬럼은 지웠다(0018).

일수는 SQL 쪽에도 필요하다(뷰가 비교해야 한다). `originals.retention_days()`가
SQL의 정본이고 도메인의 `RETENTION_POLICY.originalDays`가 정책의 정본이며,
**둘이 같은지 테스트가 확인한다.**

### 조용한 것을 안전하다고 읽으면 안 된다

파기 목록이 비어 있는 이유가 둘이다.

- 정말 지울 것이 없다
- **아직 셈이 시작되지 않았다** — 심사가 열려 있다

후자는 무기한이다. 심사에 결론이 날 때까지 원본이 남고, 심사가 적체되면
개인정보가 그만큼 오래 남는다. 그게 이 기준의 대가다. 그래서
`originals.retention_held_for_verification`이 그 상태를 따로 드러내고,
`--due`가 함께 말한다.

```
파기 예정 1건.
  <id>  예정일 2026-08-13 (15일 지남)  파일 1개  담긴 것: 이름, 연락처

그 밖에 1건은 심사가 열려 있어 아직 일정이 서지 않았다.
```

앱도 이 둘을 구분해 말한다. 날짜가 없을 때 "모른다"가 아니라 "인증 심사가
끝나면 정해집니다"라고 한다 — 사용자에게는 다른 이야기다.

### 파기는 사람이 한다

예정일이 됐다고 서버가 지우지 않는다. **운영자가 직접 지운다**(운영 결정).
`RETENTION_MODE`로 두 방식이 다 보이게 해뒀고, 기본값은 `manual`이다 — 설정을
빠뜨린 환경이 남의 계약서를 조용히 지우는 것보다, 지우지 않고 알리는 쪽이
되돌릴 수 있는 실수다.

그래서 알리는 일은 기계가 한다. 사람이 달력을 보고 있기를 기대하는 것은
절차가 아니다.

| 무엇 | 어디로 |
| --- | --- |
| 파기 예정 원본이 생겼다 | 운영자 기기로 푸시 |
| 예정일이 언제인지 | 사용자 앱 화면 (A-12) |

**푸시는 운영자에게만 간다.** 파기 대상은 남의 계약서고, 그 사실을 그 사람에게
알리는 것은 우리 일이 아니다. 사용자는 앱에서 예정일을 본다.

**푸시 본문에는 건수만 담는다.** 푸시는 잠금화면에 뜬다 — 폰을 잠깐 든 사람,
어깨너머로 본 사람에게 그대로 읽힌다. 누구의 문서인지, 어떤 개인정보가
담겼는지는 앱을 열어야 알 수 있다. 파기해야 할 개인정보를 알리려다 그것을 다시
흘리면 알림이 문제 자체가 된다.

```
파기 예정 원본이 있습니다
원본 3건을 지울 때가 됐습니다. 가장 오래된 것은 예정일이 2일 지났습니다.
```

같은 말을 반복하면 사람은 알림을 끈다. 그러면 알림이 있으나 마나가 된다.
그래서 **일이 늘었을 때**와 **처리되지 않은 채 `RETENTION_REMINDER_HOURS`가
지났을 때**만 보낸다. 일이 줄어드는 것은 알리지 않는다 — 사람이 지우고 있다는
뜻이라 방해할 이유가 없다.

### 누가 운영자인가

`users.is_operator`. **사람이 DB에서만 켠다** — 앱에도 API에도 이 값을 바꾸는
길이 없다. 알림을 받는 자리이자 남의 계약서를 지우는 자리라, 스스로 올라갈 수
있으면 안 된다.

기기 등록(`POST /v1/devices`)은 누구나 한다. 등록한다고 알림을 받게 되는 것은
아니다 — 운영자인지는 서버가 보낼 때 판단하고, 앱은 자기가 운영자인지 알 필요가
없다.

### 도구

```
npm run retention --workspace @weddingpick/api -- --operator <user-id> [--off]
npm run retention --workspace @weddingpick/api -- --due
npm run retention --workspace @weddingpick/api -- --delete <document-id>
npm run retention --workspace @weddingpick/api -- --list
npm run retention --workspace @weddingpick/api -- --sweep
npm run retention --workspace @weddingpick/api -- --collect-unreachable
```

`--due`로 때가 된 것을 보고 `--delete`로 하나씩 지운다. **한 번에 다 지우는
명령은 두지 않았다** — 되돌릴 수 없는 일에 "전부"를 붙이면 손이 미끄러졌을 때
남는 것이 없다.

`--delete`는 예정일이 오지 않은 문서를 거절한다. 앱이 그 날짜를 화면에 보여주고
있고, 그보다 먼저 지우는 것은 약속을 깨는 일이다.

`--list`는 남은 문서에 **어떤 종류의 개인정보가 담겨 있는지** 함께 보여준다
(값이 아니라 종류다). 주민번호가 든 문서가 11일째 남아 있는 것과 이름만 든
문서가 하루 남은 것은 급한 정도가 다르다.

이 도구는 **파일을 지우지 않는다.** `--sweep`은 정규 삭제 작업을 한 번 더 돌릴
뿐이고, `--collect-unreachable`은 집어가지 못하는 문서를 처리 목록에 올리기만
한다. 페이지 기록이 없다는 것은 지울 파일을 우리가 모른다는 뜻이므로,
스토리지를 사람이 직접 확인해야 한다. 우리 기록만 보고 "지웠다"고 적으면
파기 기록이 거짓이 된다.

## 16. 개인정보 재검토 (서비스정책서 4번)

문서를 읽는 쪽은 개인정보의 **값**을 옮기지 않고 종류만 적도록 되어 있다. 그건
지시일 뿐 보장이 아니다. 특히 계약조건은 "원문 그대로" 옮기라고 되어 있어,
취소 조항에 담당자 연락처가 섞여 있으면 그대로 따라 들어온다.

그래서 사람이 한 번 본다. 본 뒤에야 그 문서의 값이 **남들이 보는 면**으로 갈 수
있다. 본인이 자기 계약서를 자기 화면에서 보는 것은 유출이 아니므로 막지 않는다.

### 관문은 하나다

```sql
CREATE OR REPLACE VIEW structured.comparable_quotes AS
  ... WHERE confirmed_at IS NOT NULL
      AND verification_level >= 'L2'
      AND pii_review <> 'pending'   -- 여기
```

시장 대표가격으로 가는 길은 이 뷰 하나뿐이라 여기서 막으면 우회로가 없다.
등급과 재검토는 서로 다른 질문에 답한다 — 등급은 "이 금액이 진짜인가", 재검토는
"이 안에 남의 개인정보가 섞여 있지 않은가". 둘 다 통과해야 한다.

### 무엇을 보는가

검토자가 봐야 하는 것은 문서 한 줄이 아니라, 문서에서 **글자를 그대로 옮겨온**
필드다. 금액·날짜·인원수는 숫자라 개인정보가 새어 들어올 자리가 아니다.

업체명 · 플래너 이름 · 상품명 · 홀 이름 · 계약조건 원문 — 이 다섯이다.

`findPiiHints`가 연락처·주민번호·이메일·계좌 **꼴**을 찾아 "여기 좀 보라"고
가리킨다. **사람을 대신하지 않는다** — 이름은 형태로 잡히지 않고, 계좌처럼 보이는
상품 코드도 있다. 걸리지 않았다고 깨끗한 것이 아니다.

### 도구

```
npm run pii --workspace @weddingpick/api -- --list
npm run pii --workspace @weddingpick/api -- --show <quote-id>
npm run pii --workspace @weddingpick/api -- --clean <quote-id> --by <user-id>
npm run pii --workspace @weddingpick/api -- --redact <quote-id> --by <user-id> \
  --field contractTerms --kind phone
```

지운 기록(`pii_redactions`)에는 **지운 값을 남기지 않는다.** 개인정보를 지우면서
그 개인정보를 다른 표에 옮겨 적으면 지운 것이 아니다. 어느 필드에서 어떤 종류를
지웠는지만 남는다.

실제로 값을 고치는 것은 사람이 DB에서 한다. 어떤 글자를 남기고 어떤 글자를 지울지는
문맥을 봐야 정해지고, 도구가 대신 판단하면 남겨야 할 계약조건까지 날린다.

## 17. 플래너 등록 요청

11번이 규칙과 제약을 세웠지만 **넣는 쪽이 없어** 목록이 언제나 비어 있었다.

개인 플래너는 인허가 데이터에 실리지 않는다(사업자가 아니다). 그래서 실질적으로
가능한 근거는 `vendor_official` 하나다 — 소속 업체나 본인이 스스로 밝히는 것.

**문의 창구(12번)를 그대로 쓴다.** 접수·회신 경로·사람 결정·이력이 이미 있고,
무엇보다 노출 중단과 **같은 창구여야** 한다. 올리는 문과 내리는 문이 따로 있으면
한쪽만 관리되기 쉽다.

| | 올리기 (`planner_listing`) | 내리기 (`planner_delisting`) |
| --- | --- | --- |
| 대상 | 필요 | 필요 |
| 근거 | **필요** (`evidence_url`) | 필요 없음 |
| 되돌리기 | 언제든 내릴 수 있다 | **다시 올릴 수 없다** |

비대칭은 의도한 것이다. 내려달라는 요청에 근거를 요구하면 내리기가 올리기보다
어려워지고, 그건 개인에게 불리한 쪽으로 기운다.

증빙 파일을 받지 않고 **가리키는 곳**만 받는다 — 신분증 사본 같은 것을 우리가 들고
있을 이유가 없다. 확인은 사람이 그 주소를 열어보고 한다.

```
npm run inquiries --workspace @weddingpick/api -- --answer <id> --by <user-id> \
  --resolution "..." --list-planner
```

등록 요청(`planner_listing`)이 아닌 문의로는 올릴 수 없다. 다른 문의를 처리하다가
실수로 개인 이름이 검색에 올라가는 일이 없게 한다.

## 18. 초대 딥링크

코드를 손으로 옮겨 적게 하면 한 글자만 틀려도 막힌다. 앱 스킴으로 연다.

```
weddingpick://join?code=<코드>
```

공유 문구에는 **링크와 코드를 함께** 담는다. 링크는 앱이 깔린 사람에게 한 번에
열리고, 코드는 그렇지 않은 사람이 손으로 넣는 길이다. 둘 중 하나만 담으면 한쪽이
막힌다.

도메인이 없어 못 하는 것은 **앱이 없는 사람이 링크를 눌렀을 때 스토어로 보내주는
것**(유니버설 링크) 하나다. 도메인이 정해지면 더할 수 있고, 그때까지 기다릴 이유는
없었다.

링크로 들어오면 코드가 채워지지만 **자동으로 연결되지는 않는다.** 링크를 눌렀다는
것이 공유 범위에 동의했다는 뜻은 아니다 — 무엇에 동의하는지 보여주는 단계는 그대로
거친다(13번).

입력칸에 링크를 통째로 붙여넣어도 받는다. 사람들이 실제로 그렇게 한다.

- [ ] **계약서의 비밀유지 조항 — 사용자에게 위약벌** — 웨딩홀 약관 제12조가 "계약내용을 제3자에게 누설하면 계약금의 2배액을 위약금으로 지불"한다고 정하고 있다(원문 확인 2026-08-28). 의무 주체는 이용자만이고 제3자 예외는 없다. **이 앱을 쓴 대가로 손해를 볼 수 있는 쪽이 사용자다** — 성격이 달라졌으므로 법률 확인이 급하다(법률검토 체크리스트 🔴). 확인 결과에 따라 업로드 화면에 고지가 필요할 수 있다

## 19. 이용 후기 (사업계획서 17·19번)

후기를 받는다. 다만 아는 것과 모르는 것을 갈라서 받는다 — 누가 무엇을 알 수 있는지,
무엇이 확인된 것인지가 이 설계의 전부다.

### 누가 쓰느냐에 따라 묻는 것이 다르다

같은 예식장을 두고도 보는 것이 다르다. 계약자는 가격과 응대를 알고, 하객은 주차·
교통·식사를 안다. 합쳐 버리면 둘 다 흐려진다.

| 자리 | 웨딩홀에서 답하는 항목 |
| --- | --- |
| 계약자 · 신랑신부 | 음식 맛·메뉴·온도, 연회장 혼잡, 직원 응대, 주차, 교통, **추가비용 사전안내** |
| 하객 | 위에서 추가비용을 뺀 것 |

추가비용을 하객에게 묻지 않는 이유가 이 설계의 요점이다. 사업계획서 1번이 꼽은
문제가 "견적서 금액과 실제로 낸 금액이 다르다"인데, 그걸 아는 사람은 계약한
사람뿐이다. 모르는 것을 물으면 짐작으로 채우고, **그 짐작이 업체 점수가 된다.**

항목 목록은 서버가 만들어 내려준다(`GET /v1/vendors/{vendorId}/review-form`). 앱에
박아두면 항목이 늘 때마다 앱을 새로 내야 하고, 그동안 두 곳의 규칙이 어긋난다.

### 점수에는 확인된 후기만 들어간다

광고비로 노출은 살 수 있어도 평가는 살 수 없다(서비스정책서 5번). 그래서 관문을
하나 둔다 — `structured.scored_reviews`. 게시 중이고 확인된 후기만 이 뷰에 들어오고,
이용점수는 이 뷰만 읽는다. 가격의 `comparable_quotes`와 같은 자리다.

**미인증 후기는 화면에 보이되 점수를 움직이지 않는다.** 지우지 않는 이유는 문서
등급과 같다 — 확인되지 않았다는 것과 거짓이라는 것은 다르다.

표본이 5건(화면데이터구조 스펙 5.5)에 못 미치면 점수를 만들지 않고 이유를 준다.
**확정 비율도 내보내지 않는다** — 4건에서 계산한 4.5점을 회색으로 흐려 보여주는
것도 안 된다. 흐린 숫자도 숫자고, 사람들은 숫자를 읽는다. 후기 두세 건으로 만든
점수는 정보가 아니라 소음이고, 업체 하나를 망칠 수도 살릴 수도 있다.

### 확인은 이미 있는 인증을 이어받는다

별도의 증빙을 다시 받지 않는다. 이 사람의 문서 중 이 업체 것이 인증 심사를
통과했으면(14번) 그것이 곧 "실제로 계약했다"는 증거다. 같은 것을 두 번 확인하게
하면 사람들은 두 번째에서 그만둔다.

| 근거 | 후기 표시 |
| --- | --- |
| 인증 심사를 통과한 계약 문서(L2 이상) | 계약 확인 |
| 결제인증 제보(20번) | 결제 확인 |
| 없음 | 미인증 |

견적인증(L1)으로는 확인해 주지 않는다. **견적서를 받은 것과 그 업체를 이용한
것은 다른 일이다** — 상담만 받고 계약하지 않은 사람의 후기에 확인 배지가 붙으면,
그 배지는 "이용했다"는 뜻이 아니게 된다. 둘 다 있으면 사람이 심사한 쪽이 이긴다.

**작성자에게 묻지 않는다.** 요청 본문에 확인 단계를 넣을 자리가 아예 없다 — 자기
후기를 "계약 확인"이라고 말할 수 있으면 그 표시는 아무 뜻이 없다.

확인한 사람은 그 문서를 승인한 심사자를 그대로 이어받는다. 후기 쪽에서 새로 만들지
않는다. 그리고 등급은 올랐는데 승인 기록이 없으면 확인해 주지 않는다 — 지금은
일어나지 않지만, 나중에 등급을 올리는 다른 길이 생겼을 때 그 길이 조용히 "확인된
후기"를 찍어내지 못하게 하기 위해서다.

무엇으로 확인되는지는 **쓰기 전에** 보여준다. 다 쓰고 나서 "미인증입니다"라고 하면
그건 통보고, 그 자리에서 사람들은 글을 지운다.

### 이의와 신고

업체가 이의를 제기하면 사람이 확인하는 동안 내려둔다(서비스정책서 6번). 내려두는
것과 지우는 것은 다르다 — 확인 결과 문제가 없으면 다시 올라간다.

임시조치 기간은 **30일**이고, 이 숫자는 우리가 정하지 않았다. 정보통신망법
제44조의2가 정한 상한이다. 길게 잡으면 업체가 이의만 제기해도 불리한 후기를 오래
지울 수 있고, 그건 반론권이 아니라 검열이 된다. 트리거가 이 상한을 지킨다.

신고는 접수만 된다. 응답의 `status`가 `'received'` 하나뿐이라, 신고만으로 글이
내려가는 길이 계약에 없다. 신고만으로 내려가면 그건 신고가 아니라 삭제 버튼이고,
업체가 불리한 후기를 지우는 데 쓴다.

### 알아둔 우회로

0008이 플래너 공개를 잠갔다 — 견적서에서 읽은 이름은 근거 없이 검색에 오르지
않는다. 그런데 후기는 자유 글이라 "김○○ 플래너가 친절했어요"라고 적으면 그 잠금을
**우회한다.**

자유 글에서 한국 이름을 기계로 걸러낼 수는 없다(성이 형태로 잡히지 않는다). 그래서
막지 못한다. 대신 세 가지를 해둔다: 쓰기 화면에서 적지 말아 달라고 말하고,
신고 사유에 개인정보 노출을 두고, `structured.reviews` 테이블 주석에 이 우회로가
존재한다는 사실을 적어뒀다.

### 화면

| 경로 | 하는 일 |
| --- | --- |
| `/search/{vendorId}` | 이용점수 요약. 표본이 모자라면 이유 |
| `/search/{vendorId}/reviews` | 후기 목록 · 점수 · 단서 · 신고 |
| `/search/{vendorId}/write-review` | 후기 쓰기 |

### 아직 없는 것

- **이의 처리 도구.** 스키마와 트리거는 있지만 운영자가 이의를 넣고 결론을 내는
  명령줄 도구가 없다. 지금은 문의 창구(12번)로 받아 DB에서 직접 손대야 한다
- **후기 수정·삭제.** 한 사람이 한 업체에 하나라 고치려면 문의로 와야 한다
- 스드메 세 업체를 한 평점으로 합치지 않는 규칙(`canMergeScores`)은 도메인에 있지만,
  패키지 계약을 한 화면에서 셋으로 나눠 묻는 흐름은 아직 없다

## 20. 결제인증 제보 (사업계획서 v3 6번)

계약서 원본 업로드가 P1에서 빠진 자리를 결제내역이 메운다. 웨딩홀 약관 제12조의
비밀유지 조항(위약벌 계약금 2배)이 실물 계약서에서 확인됐고, 그 위약벌을 무는
쪽이 **이 앱을 쓴 사용자**다. 결제문자·카드 영수증에는 계약 조건이 없어 그 조항이
걸리지 않는다.

### 심사가 아니라 등록이다

이 한 줄이 나머지를 전부 결정한다.

| | 인증 심사 (14번) | 결제인증 등록 |
| --- | --- | --- |
| 사람이 보는가 | 본다 | 안 본다 |
| 문서 등급 | 오른다 | **안 오른다** |
| 시장 대표가격 | 들어간다 | **안 들어간다** |
| 원본 보관 | 검증 완료 후 30일 | **24시간** |
| 하는 일 | 자료를 남들이 보는 중앙값에 넣는다 | 결제인증 표시 + 실제가격 열기 |

서비스정책서 7번의 자동승인 금지는 등록 경로가 생겼다고 느슨해지지 않는다.
등록으로는 아무 등급도 오르지 않으므로, 승인할 것이 없다.

### 가격이 세 자리로 갈린다

```
structured.comparable_quotes    사람이 심사한 L2 이상 계약    → 시장 대표가격
structured.usable_payment_proofs 기계가 읽은 결제내역          → 결제인증 금액
structured.usable_price_reports  문서 없이 적어준 숫자         → 제보 금액
```

셋은 **UNION되지 않는다.** 표를 셋으로 나눈 이유가 이것이다 — 한 표에 넣으면
언젠가 한 질의가 셋을 합치고, 그때 근거가 다른 숫자가 하나로 나간다.

응답에서도 갈라져 있다. `prices.products` / `prices.paidPrice` /
`prices.reportedPrice`. 화면이 셋을 다른 칸에 그린다.

### 카드번호를 저장할 방법이 없다

여신전문금융업법 대응(스펙 8.2)을 관례가 아니라 **타입**에 둔다.

- 요청 본문에 카드번호 필드가 없다. 앱이 보내려 해도 보낼 곳이 없다
- DB 컬럼은 `masked_identifier_kind[]`다. `'5432-1234-5678-9012'`를 넣으려 하면
  enum이 거부한다. `text[]`였다면 언젠가 누가 넣는다
- 남는 것은 "카드번호가 있었다"까지다

가족카드 명의자 같은 남의 이름도 같은 규칙이다(스펙 8.4) — 추출규칙 10번이 이미
"개인정보는 값이 아니라 종류만"이라 이름 필드가 애초에 없다.

### 원본 24시간

```sql
originals.retention_interval('payment_proof') → 24 hours
originals.retention_interval('document')      → 30 days
```

두 값이 다른 것은 두 가지가 다른 것을 재기 때문이다. 30일은 **사람이 심사할
시간**이고(심사자가 원본을 다시 봐야 한다), 24시간은 **카드번호가 찍힌 이미지를
들고 있지 않겠다**는 값이다. 결제인증에는 심사가 없으니 길게 잡을 이유가 없다.

종류는 등록할 때가 아니라 **올릴 때** 받는다. 나중에 정하게 두면, 찍어만 두고
등록하지 않은 결제내역이 30일짜리 문서로 남는다.

### 이용자 3단계 (사업계획서 v3 7번)

| 단계 | 조건 | 볼 수 있는 것 |
| --- | --- | --- |
| Level 1 | 비로그인 | 검색, 업체 기본정보, 후기 전체, 이용점수 |
| Level 2 | 로그인 | + 내 웨딩, 배우자 연결, 제보·후기 쓰기 |
| Level 3 | 결제인증 1건+ | + 실제 계약 가격, 결제인증 금액, 제보 금액 |

Level 3의 잠금은 **판별 유니온**이다:

```ts
prices: { available: true, products, paidPrice, reportedPrice }
      | { available: 'locked', productCount, requirement }
```

필드를 그냥 비워 보내면 화면이 "0원"이나 빈칸을 그릴 여지가 남고, 언젠가 어느
화면이 그렇게 그린다. 유니온으로 두니 타입 검사가 가격을 그리던 화면 둘을 정확히
짚어냈다.

**수기 제보로는 열리지 않는다.** 문서 없이 숫자만 적어 넣고 남의 결제 분포를 열 수
있으면, 그 문은 잠겨 있지 않은 것이다.

잠긴 채로도 **몇 건이 모였는지와 어떻게 열리는지는 말한다.** 잠갔다고만 하고 방법을
말하지 않으면 파는 것처럼 보인다.

### 비로그인 (Level 1)

`optionalUser`가 토큰이 있으면 붙이고 없으면 지나간다. **틀린 토큰은 그대로
401이다** — 조용히 비로그인으로 떨어뜨리면, 만료된 토큰을 든 사람에게 남의 화면을
보여주게 되고 그 사람은 자기가 로그인한 줄 안다.

### 화면

| 경로 | 하는 일 |
| --- | --- |
| `/capture` | 제보. 결제인증이 앞, 견적서 분석이 뒤 |
| `/capture/payment/consent` | 구체적 동의 (스펙 8.1). 문구는 도메인에서 가져온다 |
| `/capture/payment/register` | 값 확인 · 등록 |

### 결제문자 읽기 — AI를 부르지 않는다

스펙 7.3이 순서를 정해뒀다: DB 재사용 → 캐시 → 함수 → **규칙 엔진** → … → 저비용
AI → 고성능 AI. 결제문자는 카드사가 기계로 찍어 보내는 글이라 형태가 거의 고정돼
있다. 이걸 AI에 보내는 것은 곱셈을 시키려고 사람을 부르는 것과 같다.

`POST /v1/payment-proofs/parse`는 **글**을 받는다. 이미지가 아니다. 사용자가
결제문자를 붙여넣으면 서버가 읽는다 — 그래서 **서버에 이미지가 올라가지 않는다.**
올라가지 않은 것은 새지도, 파기할 일도 없다. 가장 싸고 가장 안전한 길이다.

읽는 규칙 넷:

| 항목 | 규칙 |
| --- | --- |
| 금액 | **고르는 규칙이 아니라 빼는 규칙.** 누적·잔액·한도·적립 뒤의 금액을 뺀다 — 가장 큰 수를 고르면 대개 누적을 집는다 |
| 일시 | 연도가 없으면 **오늘보다 뒤가 되지 않는 가장 가까운 해.** 앞으로의 결제는 없다 |
| 수단 | 카드사 이름이 아니라 **행위**로 본다. "카카오뱅크"는 체크카드일 수도 이체일 수도 있어, 이름으로 정하면 둘 중 하나는 늘 틀린다 |
| 가맹점 | 알아본 토큰을 지우고 **남는 것.** 줄 단위로 버리면 `05/20 14:23 가온예식홀`에서 이름까지 버린다 |

**취소·환불 문자는 거절한다.** 이걸 결제로 등록하면 낸 적 없는 돈이 낸 돈이 되고,
분포가 위로 끌린다. 읽기 실패보다 나쁘다 — 읽기 실패는 눈에 보이지만 이건 안 보인다.

읽은 값은 **저장되지 않는다.** 사람이 확인한 뒤에 등록이 따로 온다. 확신이 낮은
항목(연도를 추정한 날짜, 후보가 여럿인 가맹점)은 화면이 짚어준다 — 문서 쪽
`needsAttention`과 **같은 기준값**을 쓴다. 두 화면이 다른 기준으로 "확인해 주세요"를
띄우면 사용자는 그 표시를 못 믿게 된다.

파서에도 **카드번호를 담을 자리가 없다.** 반환 타입에 그런 필드를 만들지 않았으므로,
읽더라도 밖으로 나가지 못한다. 나가는 것은 종류뿐이다.

만들면서 실제 문자 형태로 찔러보고 세 가지를 고쳤다:

- **마스킹되지 않은 이름**(`승인 홍길동님`)을 못 보고 있었다. `홍*동`만 찾고
  있었는데, 마스킹된 쪽보다 안 된 쪽이 더 위험하다. 그리고 그 이름이 **가맹점
  자리로 새어 들어갈 수 있었다**
- **날짜를 계좌번호로 읽었다.** `2026-07-03`이 계좌번호처럼 생겼다
- **`체크카드`가 가맹점 후보로 남았다.** 카드사 이름만 지우고 있어서. 다만 홀로 선
  `카드·은행·뱅크`만 지운다 — `하나웨딩컨벤션`의 하나는 상호의 일부다

### 아직 없는 것

- **이미지에서 읽기.** 규칙 파서는 글만 읽는다. 카드 영수증 실물 사진은 아직
  안 된다 — 스펙 7.3의 다음 단계(저비용 AI Vision)가 그 자리다. `needsVisionFallback`이
  언제 넘겨야 하는지를 이미 정해뒀다: 가맹점·금액·일시 중 하나라도 못 읽었을 때.
  **결제 수단 하나 때문에는 넘기지 않는다** — 못 읽으면 '확인 안 됨'으로 두면 되고,
  그것 때문에 AI를 부르는 것이 스펙 7.3이 막으려던 바로 그 일이다
- **원본을 붙여 올리는 흐름.** 계약(`rawDocumentId`)과 24시간 파기는 붙어 있고
  테스트도 있지만, 등록 화면이 아직 이미지를 올리지 않는다
- 가맹점 이름이 여러 업체에 걸리면 고르지 않는다. 이어붙이는 운영 도구가 없다
- **AI 비용 추적**(스펙 7.3의 나머지). 지금은 부르는 AI가 없어 셀 것도 없지만,
  Vision이 붙는 순간 필요해진다

## 21. AI를 부르는 순서와 그 값 (화면데이터구조 스펙 7.3)

스펙 7.3이 처리 순서를 정해뒀다:

```
DB 재사용 → 캐시 → 함수 → 규칙 엔진 → 이벤트 자동화 → 저비용 AI → 고성능 AI
```

결제내역 읽기가 이 순서를 그대로 코드로 옮긴 자리다(`proof-pipeline.ts`):

| 단계 | 언제 도는가 | 비용 |
| --- | --- | --- |
| 규칙 파서 | 늘 먼저 | 없음 |
| 저비용 모델 | 규칙이 가맹점·금액·일시 중 하나라도 못 읽었을 때 | 기록됨 |
| 상위 모델 | 저비용 모델의 확신이 낮을 때 | 기록됨 |
| 사람이 적기 | 위가 다 안 되거나 예산이 바닥났을 때 | 없음 |

**각 단계는 앞 단계가 실패했을 때만 돈다.** 글로 읽히면 사진을 함께 줘도 모델을
부르지 않는다. 순서가 무너지면 비용이 조용히 늘고, 늘어난 뒤에 청구서로 알게 된다.

**취소 문자는 위로 올라가지 않는다.** 규칙이 취소로 본 것도, 저비용 모델이 취소로
본 것도 거기서 끝난다 — 안 된다는 답을 살 때까지 되묻는 것과 같기 때문이다.

### 재는 것

스펙 7.3이 요구한 지표를 `structured.ai_usage`가 **호출 한 건에 한 줄씩** 남긴다.
합계만 두면 성공률도 escalation률도 되돌릴 수 없다 — 그 셋은 호출 단위의 사실이다.
비율은 저장하지 않고 `ai_usage_monthly` 뷰가 센다.

세 가지가 이 표에서 조심스럽게 다뤄진다:

- **단가를 모르는 모델은 비용이 `NULL`이다. 0이 아니다.** 0으로 두면 "공짜였다"로
  읽히고 합계에 섞여 예산이 실제보다 넉넉해 보인다. 대신 몇 건이 빠졌는지를 옆에
  함께 세고, 운영 도구가 그걸 반드시 말한다
- **`user_corrected`는 세 값이다** — 아직 모름(NULL) · 그대로 씀(false) · 고침(true).
  false로 시작하면 등록하지 않고 떠난 사람이 "그대로 썼다"로 집계된다. 비율을 낼
  때 NULL은 분모에서 빠진다 (이용점수의 "모름"과 같은 규칙)
- **실패한 호출도 남는다.** 성공률을 내려면 실패를 세야 한다

단가는 우리가 정한 값이 아니라 받아 적은 값이라, **언제 받아 적었는지**를 함께
남긴다(`MODEL_PRICES_AS_OF`). 낡은 것을 모른 채 쓰는 것보다 낡은 줄 아는 편이 낫다.

### 예산

기능별 월 한도를 걸 수 있다(`ai_budgets`). **기본값은 없음이다** — 문의 응답 기한과
같은 규칙으로, 정해지기 전에는 숫자를 지어내지 않는다. 지어낸 한도를 걸어두면 실제로
얼마가 드는지 재보기도 전에 막히고, 왜 막혔는지는 아무도 모른다.

넘기면 **사진에서 읽어주는 것만 멈춘다.** 등록도 규칙 파서도 그대로 돈다 — 스펙
7.3의 마지막 줄이 "AI가 죽어도 핵심 서비스는 정상 동작해야 함"이고, 예산 소진은
AI가 죽은 것과 같은 상태다. 화면에는 "직접 적어주시면 그대로 등록됩니다"가 나가고,
그 문구에 AI라는 말은 없다.

```
npm run ai-cost --workspace @weddingpick/api -- --status
npm run ai-cost --workspace @weddingpick/api -- --usage [--months 3]
npm run ai-cost --workspace @weddingpick/api -- --budget payment_proof_vision 20 --by <user-id>
```

한도를 정한 사람이 남는다. 인증 심사·문의와 같은 규칙이다.

### 모델을 이름으로 박아두지 않는다

저비용/상위 두 모델이 설정값이다(`PROOF_READER_CHEAP_MODEL`, `PROOF_READER_STRONG_MODEL`).
**저비용 우선이 실제로 이득인지는 재봐야 알 수 있기 때문이다** — escalation률이 높으면
두 번 부르는 값이 한 번에 좋은 모델을 부르는 값보다 커진다. `ai_usage_monthly`가 그
비율을 세고, 운영 도구가 그 사실을 출력 끝에 적어 놓는다.

### 이미지에도 카드번호를 담을 칸이 없다

모델에게 "적지 마라"고 부탁하는 대신 **적을 곳을 없앤다.** 구조화 출력 스키마에
카드번호 필드가 없으므로 스키마 밖의 값은 나오지 못한다. 부탁은 지켜지지 않을 수
있지만 없는 칸에는 못 쓴다. 지시문에도 규칙을 적지만, 그건 두 번째 방어선이다.

### 아직 없는 것

- **AI Router의 나머지.** 스펙 7.3은 "모든 AI 요청 전에 DB조회/계산/규칙처리/캐시
  가능 여부를 먼저 확인"을 요구한다. 결제내역 읽기에는 그 관문이 있지만, 문서 분석
  쪽은 아직 곧바로 모델을 부른다
- **사용자별 일일 호출 제한**과 **동일 질문 캐시**
- 방문노트·자유질의는 화면 자체가 없다

## 22. 후보 저장 (사업계획서 v3 8번의 COMPARE)

3곳 비교(11번)는 있었는데 **담아둘 곳이 없었다.** 볼 때마다 업체를 다시 찾아
골라야 했고, 결혼 준비는 몇 달에 걸친 일이라 그 사이에 앱을 몇 번이나 껐다 켠다.

### 사람이 아니라 웨딩에 매단다

이것이 이 표의 유일한 설계 결정이다. 배우자가 담은 곳을 내가 보고, 내가 담은 곳을
배우자가 본다 — 사람에 매달면 **각자 다른 목록을 들고 같은 이야기를 하게 된다.**
사업계획서 12번의 공동 의사결정이 그 말이다.

따라오는 것 둘:

- **누가 담았는지는 남기되, 지우는 권한과는 무관하다.** 배우자가 담은 것도 뺄 수
  있다. 담은 사람만 뺄 수 있게 하면 "저건 네가 담은 거니 네가 빼"가 되고, 그건
  함께 고르는 것이 아니다
- 화면에는 "배우자가 담았습니다"가 붙는다. 상대가 마음에 들어 한 곳인지 알아야
  이야기가 된다

### 서른 곳까지

저장 공간 때문이 아니라 **비교가 안 되기 때문이다.** 서른 곳을 담아두면 그건
후보가 아니라 검색 결과 사본이고, 고르는 일을 도와주지 못한다.

상한은 트리거와 라우트 두 곳에 있다. 트리거는 어떤 경로로 들어와도 막고, 라우트는
**왜 안 되는지와 무엇을 하면 되는지**를 말한다 — 트리거 예외 문구는 사람이 읽을
말이 아니다.

### 업종별로 나눠 본다

목록이 업종별로 묶여 내려간다. 서른 곳을 한 줄로 늘어놓으면 무엇을 견주는 중인지
보이지 않는다. 그리고 각 묶음에 `comparable`이 붙는데, **비교는 같은 업종끼리만
뜻이 있기 때문이다** — 웨딩홀과 스튜디오의 가격을 나란히 놓은 표는 아무것도 말하지
않는다.

두 곳 미만이면 견주기 단추 대신 "두 곳 이상 담으시면"이라고 적는다.

### 가격은 목록에 없다

후보 목록에 가격을 싣지 않는다. Level 3 잠금(20번)을 우회하는 길이 생기기도 하고,
무엇보다 이 화면은 **무엇을 견주는 중인가**를 보는 자리지 값을 보는 자리가 아니다.

| 경로 | 하는 일 |
| --- | --- |
| `/wedding/{id}/candidates` | 담아둔 곳. 업종별로 묶여 나온다 |
| `/search/{vendorId}` | 담기 단추 |

## 23. 우리웨딩 (디자인 핸드오프 14~16번)

웨딩 스케줄 · 지출내역 · 방문노트. 셋 다 **웨딩에 매단다. 사람이 아니라** —
후보 저장(22번)과 같은 이유다.

### 웨딩 스케줄 — 열넷을 미리 깔아준다

처음 결혼을 준비하는 사람은 **무엇을 해야 하는지부터 모른다.** 빈 목록을 주고
채우라고 하면 그 목록은 영영 비어 있다. 그래서 목록을 처음 열 때 열네 개를 넣는다.

**한 번만 깐다.** "빠진 것이 있으면"이 아니라 "비어 있으면"이 조건이다 — 지운
항목을 다시 깔면 지우는 일이 아무 뜻이 없어진다.

상태는 날짜로 자동 판정한다: 나흘 이상 남음 `예정`, 사흘 이내 `진행중`, 지남 `완료`.

**사용자가 정한 값이 이긴다.** 자동 판정은 날짜만 보고 짐작하는 것이라, 사람이
아니라고 말했으면 그쪽이 맞다. 그때 화면에 `직접 지정`을 적어 **이 값이 날짜를
안 따라간다는 것**을 보이게 한다. `state: null`을 보내면 다시 자동 판정으로 돌아간다 —
지우는 것이 아니라 "직접 지정을 그만둔다"는 뜻이라 그 차이가 계약에 있다.

> 지난 날을 `완료`로 보는 것은 짐작이다. 날이 지났다고 실제로 했는지는 모른다.
> 핸드오프가 정한 규칙이고, 틀렸을 때 고칠 방법(직접 지정)이 화면에 있어 받아들였다.

수정은 **보낸 칸만 고친다.** 안 보낸 칸을 null로 지우면 날짜만 바꾸려던 사람이
업체까지 잃는다.

### 지출내역 — 낸 돈과 낼 돈은 다른 자리에

결제인증(20번)과 직접 입력이 한 목록에 모인다. **섞어도 되는 이유는 둘 다 내
돈이기 때문이다** — 섞으면 안 되는 것은 근거가 다른 **남들의** 숫자였다
(`comparable_quotes` · `usable_payment_proofs` · `usable_price_reports`). 대신 어디서
온 값인지를 줄마다 적는다.

**잔금은 합계에 더하지 않는다.** 더하면 "지금까지 결제한 금액"이 거짓말이 된다 —
아직 안 냈다. 응답에서 `paidTotal`과 `scheduledTotal`이 **다른 필드인** 이유가
이것이다. 합쳐 보내면 화면이 더할 여지가 남는다.

**결제인증에서 온 줄은 지출내역에서 지울 수 없다.** 그건 지출 기록이 아니라 제보이고,
지우면 남의 분포에서도 빠진다. 제보를 무르는 것은 다른 문이어야 한다.

일곱 업종을 네 갈래(웨딩홀·결정사·스드메·기타)로 묶는다. 일곱 색을 나란히 놓으면
어느 것이 큰지 읽히지 않는다. **0원인 갈래도 자리를 지킨다** — 빼면 막대의 색 순서가
자료에 따라 달라지고, 같은 화면을 두 번 보는 사람이 다른 것으로 읽는다.

**예산 기본값을 두지 않는다.** 결혼 예산은 사람마다 열 배씩 차이가 나서, 평균값을
깔아두면 그건 안내가 아니라 유도다. 넘겼을 때 음수를 감추지도 않는다 — 얼마나
넘겼는지가 필요한 정보다.

### 방문노트 — 제안가는 가격이 아니다

그 자리에서 들은 값이다. **문서도 결제도 아니라서 가격 통계 어디에도 들어가지
않는다** — 들은 말이 남의 화면에 중앙값으로 나가면, 우리는 들은 말을 사실로 파는
것이 된다. 테스트가 세 관문을 모두 확인한다.

업체를 못 찾아도 적을 수 있다. **방문은 계약보다 먼저다.**

| 경로 | 하는 일 |
| --- | --- |
| `/wedding/{id}/tasks` | 웨딩 스케줄 |
| `/wedding/{id}/expenses` | 지출내역 · 예산 |
| `/wedding/{id}/visit-notes` | 방문노트 |

### 아직 없는 것

- **도넛 차트**(핸드오프 14번). 지금은 누적 막대로 그린다 — `conic-gradient`가
  React Native에 없어 SVG나 직접 그리기가 필요하다
- **FAB**. 지금은 목록 아래 단추다
- 홈의 다음 일정·진행률 섹션 (24번에서 홈을 다시 만들 때)

## 24. 홈 (디자인 핸드오프 5·6번)

여덟 자리가 순서대로 선다: D-Day · 다음 일정 · 퀵메뉴 · 웨딩 스케줄 · 지출 현황 ·
관심업체 · 결제 데이터 안내 · 홈 편집.

### 두 자리는 고정이다

**D-Day와 다음 일정은 숨길 수 없다.** 핸드오프가 그렇게 정했고, 이유가 있다 —
오늘 무엇을 해야 하는지가 홈의 이유다. 그 둘까지 숨길 수 있게 두면 홈이 빈 화면이
될 수 있다. 나머지 다섯은 순서를 바꾸고 숨길 수 있다.

### 빈 상태에서 레이아웃을 바꾸지 않는다

핸드오프가 명시한 규칙이다. 값만 `0`이나 `—`로 두고 자리는 지킨다 — 자료가 없다고
다른 화면으로 갈아끼우면, 자료가 생겼을 때 사용자는 처음 보는 화면을 만난다.

`—`와 `0원`을 가려 쓴다. 다음 결제가 없으면 `0원`이 아니라 `—`다 — **0원은 "낼
것이 없다"로 읽힌다.** 지출 총액은 실제로 0원이라 `0원`이라고 쓴다.

### 두 가지를 렌더해 보고 고쳤다

브라우저로 띄워 보니 눈에 보이는 것이 둘 있었다:

- **끝낸 일이 "다음 일정"에 떠 있었다.** `nextTask`가 날짜만 봤다. 날짜가 앞이어도
  이미 했다고 표시한 일을 다음이라고 내밀면, 홈이 할 일을 알려주는 자리가 아니라
  달력을 읽어주는 자리가 된다
- **이미 실제가격을 볼 수 있는 사람에게 "등록하시면 보실 수 있어요"가 떠 있었다.**
  숨기기와 다른 일이다 — 숨기기는 사용자가 정하고, 이건 사실이 정한다

### 홈 편집

순서와 숨김을 **기기에 저장한다**. 서버에 두면 홈이 뜰 때마다 한 번 더 기다려야
하는데, 이건 보기 좋으라고 바꾸는 값이지 잃으면 큰일 나는 값이 아니다. 새 기기에서는
기본 순서로 돌아간다 — 그 대가를 알고 고른 것이다.

저장된 순서를 읽을 때 **목록에 없는 것은 버리고 빠진 것은 뒤에 붙인다.** 섹션이
늘거나 줄면 저장된 순서가 낡는데, 그대로 쓰면 새 섹션이 영영 안 보이거나 없어진
섹션 자리가 빈칸으로 남는다.

### 아직 없는 것

- **끌어서 옮기기.** 핸드오프는 드래그 핸들을 적었지만 라이브러리를 넣을 수 없어
  `위로`·`아래로` 단추로 옮긴다. 하는 일은 같고, 스크린 리더로도 쓸 수 있다는
  점은 오히려 낫다
- 다음 일정을 탭했을 때 뜨는 수정 시트 (지금은 웨딩 스케줄로 간다)
- 지출 현황의 ⓘ 툴팁
