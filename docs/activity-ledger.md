# 회원 활동 원장 — 두 층

대표 지시(2026-09-14) — 「변경된 RN기준으로 회원들의 모든 활동을 내가 확인할 수
있어야 하며, DB에 정리하도록한다. 추후 데이터를 판매할 것이다.」

**이번 작업은 「팔 수 있는 모양으로 쌓기」까지다.** 실제로 파는 것은 계약·가격·상대가
정해져야 하고 그것은 대표님 결정이다. 내보내는 명령은 **파일로 떨구는 것까지**이고,
외부로 자동 전송하는 길은 만들지 않았다.

---

## 왜 두 층인가

```
1층  structured.activity_events    회원 id가 붙는다.  대표님이 보시는 자리
2층  structured.activity_rollups   사람을 못 알아본다.  파는 자리
```

한 층으로 지으면 팔 수가 없다. 개인정보를 제3자에게 주려면 그 항목에 대한 **별도
동의**가 있어야 하고(개인정보보호법 제17조), 가입할 때 받은 동의에는 없다. 반면
**익명정보는 개인정보가 아니라서**(제58조의2) 동의 없이 거래할 수 있다.

2층을 나중에 얹을 수 없어서 처음부터 함께 지었다. 2층이 요구하는 것은 「자유 입력이
아닌 목록값」과 「사람을 셀 수 있는 키」인데 둘 다 나중에 만들 수 없다 — 1층이 이미
자유 입력으로 쌓여 있으면 접을 방법이 없다.

## 이미 있는 기록표와 겹치지 않는다

저장소에는 이미 다섯 개의 기록표가 있고 **지우지도 합치지도 않았다.**

| 표 | 담는 것 | 주어 |
| --- | --- | --- |
| `inquiry_events`(0009) | 문의 한 건의 상태 변화 | 문의 |
| `verification_events`(0011) | 인증 심사의 상태 변화 | 심사 |
| `vendor_change_log`(0048) | 업체 필드가 무엇에서 무엇으로 | 업체 |
| `withdrawal_audit_log`(0058) | 탈퇴에 운영자가 개입한 전부 | 운영자 |
| `review_objection_log`(0110) | 후기 이의를 왜 그렇게 처리했는지 | 운영자 |

저 다섯은 **특정 흐름의 상태 변화**를 담고, 새 원장은 **회원의 행동**을 담는다. 같은
사건이 양쪽에 남는 자리가 있지만(제보 제출) 묻는 질문이 다르다 — 저쪽은 「그 제보가
어떻게 됐나」, 이쪽은 「이 회원이 그날 무엇을 했나」.

## 1층 — 활동 원장

### 담는 것 열하나

2026-09-14 대표님 확정 IA(홈 · 웨딩노트 · Pick · 라운지 · MY, 검색은 홈 상단
검색바)를 기준으로 골랐다.

| 사건 | 어디서 담기는가 |
| --- | --- |
| `screen_view` 화면 열기 | 앱이 보낸다 |
| `search_submitted` 검색 | 서버 (`GET /v1/vendors` + `q`) |
| `category_selected` 업종 고르기 | 서버 (`GET /v1/vendors` + `category`) · 앱 |
| `pick_added` / `pick_removed` | 서버 (candidates POST · DELETE) |
| `compare_started` 비교 시작 | 서버 (`GET /v1/vendors/compare`) |
| `vendor_viewed` 업체 열람 | 서버 (`GET /v1/vendors/:vendorId`) |
| `report_submitted` 제보 제출 | 서버 (`POST /v1/payment-proofs`) |
| `visit_note_written` 방문노트 | 서버 (`POST …/visit-notes`) |
| `onboarding_step` 온보딩 단계 | 서버(완료) · 앱(중간 단계) |
| `withdrawal_requested` 탈퇴 접수 | 서버 (`POST /v1/me/withdrawal`) |

**서버가 볼 수 있는 것은 화면을 고치지 않고 담는다.** Fastify `onResponse` 훅 하나가
모든 응답을 지나며 표를 본다(`apps/api/src/activity-hook.ts`). 지금 RN 화면 스물몇
개가 동시에 다시 그려지는 중이라, 화면마다 기록 한 줄을 넣어두면 그 화면이 다시
그려질 때 함께 지워진다. 서버가 보는 것은 화면이 바뀌어도 그대로다.

### 일부러 담지 않는 것

- **스크롤 위치 · 체류 시간 · 누른 자리의 좌표** — 화면 하나를 얼마나 오래 봤는지까지
  세면 행동이 아니라 사람이 기록된다
- **방문노트와 메모의 본문** — 적었다는 사실만 남기고 글은 담지 않는다
- **알림 발송과 열람** — 이미 `notification_deliveries`가 담는다. 같은 것을 두 곳에
  적지 않는다
- **접속 IP · 기기 식별자** — 처리방침의 「서비스 보안·운영」 항목이 따로 담는 값이다.
  원장은 행동만 받는다
- **전화번호 · 카드번호 · 결제 증빙 원문 · 녹음** — 스키마 CHECK가 막는다
  (`reward_payouts`의 휴대폰 CHECK와 같은 자리)

**「비교 결과」를 한 줄로 담지 않는 것은 빠뜨린 것이 아니다.** 「스튜디오 3곳 비교 후
A 선택」은 그 자체로 사람이 좁혀지는 문장이고, 2층으로 접을 때 가장 위험한 축이 된다.
비교는 `compare_started`로, 그 뒤의 선택은 `pick_added`로 각각 남는다 — 두 줄을 시각으로
이으면 대표님은 같은 것을 보실 수 있고, 2층은 둘을 따로 센다.

### append-only

고치거나 지우지 않는다. **약속이 아니라 트리거가 막는다.**

- `UPDATE` — 언제나 거절. 틀린 줄은 그대로 두고 `corrects_event_id`를 단 새 줄을 붙인다
- `DELETE` — **그 회원의 계정이 이미 사라졌을 때만** 통과. 파기는 부모 행을 먼저 지우고
  CASCADE가 뒤따르므로, 트리거가 볼 때 `users`에 그 사람은 없다. 반대로 살아 있는
  회원의 줄을 지우려 하면 부모가 그대로 있어 막힌다

정정 줄은 **같은 사람의 줄만** 가리킬 수 있다 — 복합 외래키
`(corrects_event_id, user_id) → (id, user_id)`가 강제한다. 트리거가 아니라 외래키라
쓰기 비용이 늘지 않는다.

### 탈퇴하면

**원장은 사라지고 집계는 남는다.**

파기 워커가 `structured.users` 행을 실제로 지우고(`withdrawal.ts` `attemptDeleteAccount`),
그때 원장도 CASCADE로 함께 지워진다. 행동 기록은 계정과 이어져 있을 때만 뜻이 있는
값이라 연결만 끊어 남기지 않는다 — 시각과 업종과 지역이 남은 줄은 계정 연결이 없어도
한 사람의 그날을 그린다.

방침 제18조가 「후기와 실 제보는 연결정보를 분리하여 유지될 수 있다」고 적은 것과 다르게
간다. 후기는 남이 읽는 글이고 실 제보는 금액 통계의 근거라 지우면 다른 사람의 화면이
바뀌지만, 원장은 그렇지 않다.

2층은 사람을 못 알아보는 묶음 수치라 개인정보가 아니고, 이미 뽑혀 따로 저장돼 있다.
탈퇴 한 사람 때문에 지난달 집계가 흔들리지 않는다.

### 쓰는 비용

화면이 기다리는 시간에 **아무것도 더하지 않는다.**

1. **응답을 보낸 뒤에 적는다** — `onResponse` 훅이라 사용자는 이미 응답을 받았다
2. **한 줄에 한 번씩 DB를 두드리지 않는다** — 메모리 큐에 쌓아 50줄씩 한 번의 INSERT로
   내보내고, 차지 않아도 2초마다 비운다
3. **색인은 셋뿐이다** — 색인 하나가 늘 때마다 INSERT가 느려진다

큐에 남은 줄은 프로세스가 죽으면 사라진다. 그것을 받아들인다 — 원장이 놓치는 줄 몇을
아끼려고 요청마다 쓰기를 기다리게 하는 것이 더 비싸다. **버려진 줄의 수는 관리자
화면이 그대로 보여준다**(0이 아니면 원장이 온전하지 않다는 뜻이다).

## 2층 — 집계층

**사람 단위 행이 없다.** 한 행은 한 묶음이고, 그 묶음에 몇 사람이 들었는지를 함께 적는다.

### 최소 인원 기준 — 10명

한 묶음에 서로 다른 회원이 **열 명 미만이면 행 자체를 내보내지 않는다.** 0으로 적거나
「적음」으로 적는 것도 내보내는 것이다 — 그 칸이 비어 있다는 사실 자체가 「열 명이 안
된다」를 말하고, 옆 칸과 견주면 남은 수가 드러난다.

근거 넷.

1. **저장소가 이미 정한 수다.** `DISCLOSURE_THRESHOLDS.detailed = 10` — 실 제보의
   기준금액을 밖으로 낼 수 있는 문턱이 10이다. 같은 성격의 판단(한 사람의 값이 숫자로
   드러나는가)에 문턱을 둘로 두면 언젠가 한쪽만 고쳐진다. 그래서 새 수를 만들지 않고
   그 상수를 그대로 쓴다.
2. **축이 늘면 좁혀지는 정도가 다르다.** 3은 한 업체·한 축(금액)에 대한 구간 문턱이다.
   2층은 기간·자리·업종·지역·예산을 겹친다.
3. **되돌릴 수 없는 쪽이다.** 3과 5는 앱 안에서 보이는 값이라 잘못 잡으면 내리면 된다.
   2층은 계약으로 밖에 나가고, 나간 뒤에는 지울 수 없다.
4. **가명정보의 예시값을 그대로 쓰지 않는다.** 개인정보보호위원회 가이드라인이
   k-익명성 예시로 드는 3 이상은 가명정보(안에서 결합·분석)의 이야기다. 익명정보로 밖에
   내보내는 자리는 그보다 높게 잡는 것이 실무다.

**인원만으로는 모자라다.** 열 명이 들어도 「서울 · 스튜디오 · 3천만원대」는 한 줄로
사람을 그린다 — 지시서가 재식별의 예로 든 문장이 정확히 그 모양이다. 그래서 **겹치는
축은 둘까지만** 허용한다(`ACTIVITY_MAX_AXES`). 지역·업종·준비 예산 중 셋을 한꺼번에
채운 행은 CHECK가 막는다.

두 기준 모두 **코드와 스키마 양쪽에 있다.** 코드가 판단하고 CHECK가 마지막 그물이다 —
뽑는 코드가 언젠가 잘못 세도 작은 묶음은 표에 들어가지 못한다. 두 값이 어긋나지 않는지는
시험이 지킨다(`apps/api/src/test/activity-ledger.test.ts`).

### 접는 규칙 v1 (`fold/v1`)

**행마다 `fold_rule`로 함께 저장된다.** 나중에 「이게 정말 익명인가」를 다시 따질 때
어느 기준으로 접힌 값인지 알아야 한다. 규칙을 고치면 판 번호를 올린다.

| 축 | 어디서 오는가 |
| --- | --- |
| `region` | 그 회원의 웨딩 지역. 짧은 꼴 아홉으로 맞춘다(`REGION_SUFFIX_PATTERN` — SQL과 코드가 같은 규칙을 쓴다). 목록에 없으면 NULL이고 지역 묶음에서 빠진다 — 모르는 값을 「그 외」로 밀어 넣지 않는다 |
| `category` | 사건이 업종을 직접 들고 있으면 그것. 업체를 가리키는 사건이면 그 업체의 업종 |
| `budget_bracket` | 그 회원의 준비 예산 구간. `unknown`(「아직 모르겠어요」)은 사용자가 실제로 고른 칸이라 그대로 한 묶음 |

**자유 입력은 그대로 올라가지 않는다.** 검색어 원문은 1층에만 있고, 2층으로는
`foldSearchText`가 집어낸 업종 이름·지역 이름만 간다. 둘이 함께 든 말(「스튜디오
드레스」)은 **접지 않는다** — 하나를 골라 세면 그 선택이 곧 지어낸 값이다. 어디에도
걸리지 않는 말은 축 없는 묶음에 든다.

### 뽑은 이력

`structured.activity_rollup_runs`가 언제 어느 범위를 훑었고 **최소 인원에 못 미쳐
몇 묶음이 빠졌는지**를 남긴다. 빠진 수가 곧 「기준이 적당한가」의 답이다 — 열에 아홉이
빠지면 기준이 너무 높거나 축을 너무 잘게 갈랐다는 뜻이고, 하나도 안 빠지면 기준이
놀고 있다는 뜻이다.

## 쓰는 법

```
# 지난 주를 다시 묶는다 (관리자 화면의 「지난 주 다시 묶기」와 같은 일)
POST /v1/admin/activity/rollup   { "periodStart": "2026-09-08", "periodDays": 7 }

# 내보낼 값을 파일로
npm run activity:export --workspace @weddingpick/api -- --out out/activity.json
npm run activity:export --workspace @weddingpick/api -- --from 2026-08-01 --csv
```

**내보내는 것은 2층뿐이다.** 1층을 내보내는 함수는 만들지 않았다 — 필요해 보이면
그것은 이 층을 잘못 쓰고 있다는 뜻이다.

관리자 화면은 `/admin/activity`(사이드바 「조회 · 회원 활동」)다. 위가 원장, 아래가
내보낼 묶음이다. 나가는 표를 따로 열어야 하면 아무도 열지 않고, 그러면 무엇이
나가는지 모르는 채로 나간다.

## 아직 남은 것

- **화면 진입(`screen_view`)을 앱이 부르는 줄이 아직 없다.** 담는 길은 다 뚫렸다
  (`apps/mobile/src/features/activity/ledger.ts` · `POST /v1/activity/events`) — 부르는
  한 줄만 화면 쪽에 들어가면 된다. 지금 RN 화면들이 동시에 다시 그려지는 중이라
  (`claude/rn-screens-*` · `claude/rn-nav-auth`) 그 세션들이 넣어야 한다. 먼저 넣으면
  그 화면이 다시 그려질 때 함께 지워진다.
- **원장의 보관 기간을 정하지 않았다.** 탈퇴하면 사라지는 것은 정했지만, 탈퇴하지 않은
  회원의 오래된 줄을 언제까지 두는지는 정한 적이 없다. 감사 기록은 90일이고 원본은
  24시간·30일인데 원장은 지금 무기한이다. **처리방침이 정할 값이라 여기서 정하지
  않았다.**
- **처리방침의 수집 항목에 이 원장이 없다.** 아래 참고.

## 처리방침 범위 — MASTER 보고 사항

**방침을 고치지 않았다.** `apps/web/src/subpages.ts`는 방침 세션(`claude/policy-gemini-audio`)
전담이라 손대지 않는다. 읽고 판단한 것만 적는다.

1. **약관 제8조(실 제보의 이용)는 이 원장을 덮지 않는다.** 제8조가 말하는 것은 「실
   제보」 — Pick 인증 자료에서 뽑은 금액·품목·이용일이다. 원장이 담는 것은 **행동**이라
   다른 항목이다.

2. **방침 1항(처리 목적·항목·보유기간) 표에 이 원장에 해당하는 줄이 없다.** 가장 가까운
   것이 「서비스 보안·운영 — 접속일시, IP, 기기·앱 정보, 오류·보안 로그, 요청 식별자」인데
   그 목적은 **보안·운영**이고, 원장의 목적은 통계와 상품 개선이다. 목적이 다르면 같은
   줄로 볼 수 없다.

3. **따라서 원장을 켜기 전에 방침에 줄이 하나 늘어야 한다.** 대략 이런 모양이다 —
   「서비스 이용기록(화면 이동, 검색어, Pick, 비교, 열람 이력) · 통계 작성과 서비스 개선 ·
   탈퇴 시까지」. 보유기간은 위의 「아직 남은 것」과 같은 값이다.

4. **판매는 방침 3항(제3자 제공)이 아니라 제58조의2가 여는 길이다.** 3항은 「동의 또는
   법령상 근거가 있는 경우에만」이라 적혀 있고, 지금 받은 동의에는 그 항목이 없다.
   2층이 익명정보인 한 3항의 대상이 아니지만, **2층이 정말 익명인지는 내보내기 전에
   한 번 더 확인할 일**이고 그 근거로 `fold_rule`과 `k_threshold`를 행마다 남겼다.

이 넷은 **판단 필요**다. 완료에 섞지 않는다.
