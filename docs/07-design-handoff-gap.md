# 디자인 핸드오프(v7)와 지금 코드의 차이

2026-08-29에 받은 `design_handoff_weddingpick` — 21개 화면, 확정된 토큰, 인터랙션
규칙. README가 명세이고 HTML 두 개는 레퍼런스다.

이 문서는 무엇이 이미 있고, 무엇을 새로 만들어야 하고, **무엇이 이미 정한 것과
부딪히는지**를 적는다. 마지막 것이 먼저다 — 부딪히는 것을 모른 채 만들면 두 번 만든다.

> 항목 안에 적어뒀다.

## 0. 먼저 정해야 하는 것 — 어제 정한 것과 부딪히는 셋

### 🔴 0-1. 업체평가 — 별점 vs 체크리스트

핸드오프 8번:

> **업체평가** — 항목별 ProgressBar. … 캡션 `별점이 아니라 체크리스트 응답을 환산한
> 값이에요`

**어제(2026-08-28) "별점만 유지"로 정하고 만들었다.** 05a의 체크리스트를 버린 이유는
그 항목(가격설명·계약일치·매칭이행·과도권유)이 전부 결정사 전용이라 웨딩홀 음식·주차에
쓸 수 없어서였다. 핸드오프는 그 결정을 뒤집는다.

지금 있는 것: `RatingPicker`(1~5 별점), `review_aspects` 표, 업종·역할별 항목,
`computeUsageScore`, 후기 쓰기·목록 화면 둘.

**되돌리는 비용**: 도메인 파일 하나, 마이그레이션 하나, UI 부품 하나, 화면 둘.
크지는 않지만 두 번째로 만드는 것이다.

체크리스트가 나은 이유는 05a에 적혀 있었다 — **"모름"이 분모에서 빠진다.** 별점은
모르는 것도 3점쯤으로 찍히고 그게 평균에 들어간다.

**결정: 둘 다 — 업종으로 가른다.** 결정사는 체크리스트, 웨딩홀·스드메·플래너는
별점. 05a가 결정사 전용 문서였던 것을 그대로 반영한 것이다 — 체크리스트 항목
(가격설명·계약일치·매칭이행·과도권유)은 결정사 계약에만 있는 것이라 웨딩홀 음식이나
스튜디오 보정에는 쓸 수 없다.

만들면서 나온 것 셋:

- **`yesIsGood`이 필요했다.** "과도하게 권유받았나요?"에 '예'는 나쁜 답이다. 전부
  예=좋음으로 세면 **강권하는 업체가 높은 점수를 받는다.** 항목마다 어느 쪽이 좋은
  답인지 들고 있게 했다
- **표를 따로 뒀다**(`review_checklist_answers`). `review_aspects`에 answer 컬럼을
  붙이면 rating과 answer 중 하나만 채워진 행이 생기고, 언젠가 한 질의가 둘을 섞는다
- **한 후기가 두 방식을 섞을 수 없게 트리거로 막았다.** 섞이면 업체평가에 별점
  막대와 비율 막대가 나란히 서고, 읽는 사람은 두 숫자가 같은 것을 재는 줄 안다

응답에서도 `aspects`(1~5)와 `checklist`(0~100)가 다른 배열이다. 4.2점과 78%는 다른
것을 재는 숫자라 한 배열에 넣으면 화면이 같은 막대로 그린다.

### 🟡 0-2. 촬영 — 앨범 허용 여부

핸드오프 11번: **`앨범 업로드 없음`**

어제 결정: **"캡처 허용"**. 결제문자는 대부분 이미 찍혀 있는 화면 캡처라, 막으면
제보가 거의 안 들어온다고 판단했다.

지금 있는 것: 제보 화면에 결제문자 **붙여넣기**(글)가 주 경로이고, 견적서 쪽에만
앨범 불러오기가 남아 있다. 핸드오프에는 붙여넣기 경로가 아예 없다 — 촬영만 있다.

**붙여넣기는 사진을 서버에 올리지 않아 파기할 원본이 생기지 않는다.** 촬영만 남기면
모든 제보가 24시간 파기 대상 이미지를 만든다.

**결정: 셋 다 연다.** 붙여넣기 · 촬영 · 앨범. 화면에서 붙여넣기를 앞에 두고,
사진은 "결제문자가 아니라 종이 영수증이라면"이라고 적어 두 번째로 뒀다 — 올라가지
않은 것은 새지도 파기할 일도 없다는 이유를 화면 문구가 그대로 말한다.

### 🟡 0-3. "진짜 가격" — 브랜드 메시지 폐기

핸드오프 카피 규칙:

> "진짜 가격", "적정가", "정확한 가격" 같은 표현은 사용하지 않고
> `가격 차이 / 실제 결제 사례 / 결제 구간 / 결제 분포`로 통일

**"찍으면, 진짜 가격이 보인다"는 사업계획서의 핵심 획득 메시지다.** 지금 여섯 곳에
박혀 있다(README, 웹 랜딩, 홈, MY 공유 문구, 사업계획서 둘).

**결정: 전부 교체.** `같은 업체도, 결제 금액은 달라요` — 핸드오프 온보딩 1장의
첫 줄을 그대로 썼다. 사실을 말할 뿐 판정하지 않는다.

바꾼 곳: 저장소 README · 웹 랜딩 · 홈 · MY 공유 문구 · 디자인 미리보기. **사업계획서
01과 01a는 그대로 뒀다** — 원본 문서를 옮긴 것이라 고치면 기록이 거짓이 된다.

그리고 **규칙을 코드에 뒀다**(`copy-rules.ts` + `apps/web`의 검사). 문서에만
적어두면 지켜지지 않는다 — 실제로 네 곳에 박혀 있었고 아무도 몰랐다. 검사는 앱·웹·UI
소스를 훑되 **주석은 건너뛴다**: 규칙을 설명하려면 금지어를 적어야 하고, 그걸 막으면
왜 금지했는지 적을 수 없다. 심어보고 잡히는 것까지 확인했다.

## 2. 새로 만들어야 하는 것

**화면**

- 0 스플래시 · 1 온보딩 5장 · 2 이름·예식일 등록 · 3 예식일 캘린더 · 4 로딩 스켈레톤
- 5 홈 (지금 홈과 구조가 다르다) · 6 홈 편집
- 14 지출내역 · 15 웨딩 스케줄 · 16 방문노트 — **PLAN 영역 전체**
- 18 미션 완료 모달 · 19 설정 · 20 알림 · 내 제보 내역 · 업체 반론 등록

**서버·데이터**

| 필요 | 지금 |
| --- | --- |
| `users.name`(5자), `weddings.wedding_date` 등록 흐름 | 컬럼은 있고 화면이 없다 |
| 웨딩 스케줄 14개 프리셋 + 상태 자동판정 | 없음 |
| 지출내역 · 총 예산 | 없음 |
| 방문노트 | 없음 |
| 관심업체 = 후보 저장 | **있다** (0026) |
| 알림 | 기기 등록은 있고 알림함이 없다 |
| 업체 반론 (게시 승인 포함) | 문의로만 받는다 |
| 홈 섹션 순서·숨김 | 없음 |

**디자인 시스템**

지금 `packages/ui`는 Montage(Wanted) 토큰 위에 서 있다. 핸드오프는 **Toss TDS**
값을 확정해 줬고 색·타이포·간격이 전부 다르다. 핸드오프도 "자체 디자인 시스템이
있다면 그쪽 컴포넌트로 치환하되 크기·간격·상태 규칙은 유지하라"고 적었다.

두 갈래다:

1. **토큰만 갈아끼운다** — `Colors`/`Fonts`/`Spacing`의 값을 Toss 값으로. 이름은
   그대로라 화면 34곳이 안 바뀐다. 빠르고, 되돌리기 쉽다
2. **Montage를 걷어낸다** — `@montage-ui/theme` 의존을 없애고 값을 직접 든다

핸드오프가 픽셀 단위 재현을 요구하므로 결국 2번이 된다. 다만 1번으로 시작해도
화면 작업과 병행할 수 있다.

## 3. 등급 체계가 3단계에서 4단계로

| 핸드오프 | 조건 | 지금 |
| --- | --- | --- |
| 게스트 | 비회원 | Level 1 ✓ |
| 메이트 | 로그인 | Level 2 ✓ |
| **프렌드** | **배우자 연결** | **없다 — 등급이 아니었다** |
| 패밀리 | 결제인증 | Level 3 ✓ (`data_unlocks`) |

배우자 연결이 등급이 된 것이 유일한 구조 변화다. 상태는 `role` 3값 +
`spouseLinked` 하나로 파생시키면 된다 — 핸드오프의 상태 명세도 그렇게 돼 있다.

**열람 범위 하나가 넓어졌다.** 핸드오프는 게스트에게 업체 상세 **전체**(업체평가·
인증후기·공식정보)를 연다. 지금도 그렇고, 잠기는 것은 실제 결제 블록 하나뿐이다 —
맞다.

## 4. 인증 배지 이름이 또 다르다

핸드오프 8번: `계약인증 · 이용인증 · 상담제보`
지금: `미인증 · 결제 확인 · 계약 확인`

핸드오프에 **결제인증 배지**가 색 토큰에는 있는데(green `#0f8b4c`) 후기 배지 목록에는
없다. 카피 규칙의 배지 목록에는 `결제인증`이 있다. 목록이 서로 어긋나 있어, 화면을
만들 때 확인이 필요하다.

## 5. 지켜야 할 규칙 중 코드에 영향이 큰 것

- **파생 값은 저장하지 않고 계산한다** — 핸드오프가 명시적으로 적었고("저장해두면
  반드시 어긋난다"), 우리가 이미 그렇게 하고 있다(파기 일정, 이용점수, 잠금 상태)
- **화면 이동은 단일 헬퍼를 거친다** — expo-router가 스택을 들고 있어 그대로 맞는다
- **화면이 바뀌면 오버레이를 전부 닫는다** — 지금은 오버레이가 거의 없다. 시트를
  쓰기 시작하면 이 규칙이 필요해진다
- **빈 상태에서 레이아웃을 바꾸지 않는다** — 값만 0/—. 지금은 빈 상태를 다른 문구로
  바꾸는 곳이 여럿이라 손볼 곳이 있다
- 배지는 띄어쓰기 없이, `~해요`체, 느낌표·이모지 없음

## 6. 순서 (제안)

```
① 0번 셋 결정                    ✅ 업종별 분기 · 셋 다 열기 · 카피 교체
② 토큰을 Toss 값으로 갈아끼운다   ← 다음. 화면 이름 안 바뀜
③ 이름·예식일 등록 + 스플래시·온보딩
④ 홈 재구성 + 홈 편집
⑤ PLAN — 웨딩 스케줄 · 지출내역 · 방문노트
⑥ MY 미션 · 등급 4단계
⑦ 알림 · 내 제보 내역 · 업체 반론
⑧ 나머지 화면 모양 맞추기
```

③이 앞인 이유는 이름과 예식일이 **스킵 불가**라서다 — 그게 없으면 홈의 D-Day도
웨딩 스케줄의 상태 판정도 만들 수 없다.
