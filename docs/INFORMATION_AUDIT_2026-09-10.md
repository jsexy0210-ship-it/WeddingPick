# 웨딩픽 앱·관리자 통합 검수 — 2026-09-10

후속 검증: 사용자가 제공한 최신 디자인 ZIP의 내부 충돌과 구현 대조는 [디자인 ZIP 검수 보고서](DESIGN_ZIP_AUDIT_2026-09-10.md)를 함께 확인한다. 특히 검색 구조 등은 ZIP 내부 명세도 서로 충돌하므로 개별 원본을 확정하기 전에 일괄 반영하지 않는다.

## 결론

반복 오류의 핵심은 **화면·서버·정책 문서가 서로 다른 계약을 사용하고, 실제 동작 검증 없이 성공·완료로 판정되는 구조**다. 디자인만 수정해도 해결되지 않는다. 관리자 렌더링, 저장·작업 실행, 정보 표시, 배포 검증을 먼저 연결해야 한다.

### 검수 기준과 범위

- 기준 저장소: `jsexy0210-ship-it/WeddingPick`, main `e34193ee1644c664f107d529002ae53ef775389a`.
- 최초 검수 `e5f3b581` 이후 main에 `8391a02`(관리자 v3.27), `e34193e`(배지)가 추가되어 최신 복제본을 갱신하고 재확인했다.
- 기존 작업 폴더에 사용자 변경이 많아 `.audit-latest`에 별도 복제했다. 기존 변경을 초기화하거나 덮어쓰지 않았다.
- 앱 웹과 관리자에 실제 로그인한 상태에서 주요 경로를 열었다. 최신 오류 재확인 시 웹 번들은 `entry-1305787775b10dcd3854b2ec9dfe8363.js`였다. 번들만으로 배포 SHA를 단정하지 않는다.
- 제품 코드·운영 DB·배포 설정은 변경하지 않았다. 삭제·승인·FAQ 저장·재계산 등 운영 쓰기 작업은 실행하지 않았다.
- 아래 코드 경로와 줄은 별도 표시가 없으면 위 SHA의 저장소 루트 기준이다.
- 전 화면의 모든 상태, 390×844 원본 대조, 실기기 네이티브·푸시·카메라, 실제 파일 업로드·저장 결과까지 완료한 검수는 아니다. 정밀 속도 수치도 미측정이다.

## 1. 관리자 화면이 멈추는 공통 원인 — P1

`apps/mobile/src/app/admin/_api.ts:23`은 응답을 `Promise<unknown>`으로 반환한다. 각 화면은 이를 `as XxxData`로 단정하지만 서버 응답의 필드 구조가 다르다. 따라서 타입 검사 통과가 실제 화면 렌더링을 보장하지 않는다.

| 화면/경로 | 현재 클라이언트 기대 | 서버 실제 응답 | 실제 화면 결과 |
|---|---|---|---|
| 수익 `/admin/revenue` | `summary`, `contributionMarginRate` 등 | 최상위 `mrr`, `arr`, `planBreakdown` | `contributionMarginRate` 접근 오류 |
| 파이프라인 `/admin/data-pipeline` | `today.received`, 실패 큐 | `stages`, `lastRunAt` | `received` 접근 오류 |
| 약관 `/admin/terms` | `documents.find(...)` | `items` | `find` 접근 오류 |
| 광고 게이트 `/admin/ads-gate` | `blockers`, `steps` | `enabled`, `rules` | `length` 접근 오류 |
| 이메일 매칭 `/admin/email-matching` | `summary.total` 등 | `items`, `total` | `total` 접근 오류 |
| 이미지 `/admin/images` | `summary.pending`, `summary.total` | `items`, `hasMore`, `nextCursor` | `pending` 접근 오류 |
| 브리핑 `/admin/briefing` | `unresolvedRisks`, `autoProcessed` 등 | `briefing`, `budgetStatus` | `length` 접근 오류 |
| AI 사용량 `/admin/ai-usage` | `models` | `usage`, `budgetStatus` | `map` 접근 오류 |

초기 버전에서 재현한 관리자 오류는 10개였으며, 최신 변경 이후 **자동화·복구 화면 2개의 렌더링 오류는 해소**됐다. 위 8개는 남아 있다. 자동화·복구가 빈 상태로 열린다는 사실이 실제 운영 기능 연결 완료를 뜻하지는 않는다.

서버 근거: `apps/api/src/routes/admin.ts:1169`(수익), `:1194`(광고 게이트), `:1200` 부근(AI), `:1226`(브리핑), `:1243`(파이프라인), `:1248`(매칭), `:1253`(이미지), `:1467`(약관).

재현 자료: [계약 재현 결과](audits/2026-09-10/admin-contracts.json), [읽기 전용 재현 스크립트](../scripts/audits/admin-contracts.cjs). 서버의 리터럴 응답을 AST로 추출하고 실제 클라이언트 필드 접근을 재생한 5개 사례다. React 전체 테스트나 운영 API 호출은 아니다. 수익의 첫 오류 필드는 렌더 순서와 재생 표현식 차이로 다르지만 모두 같은 `summary` 누락이다.

**조치:** 공유 응답 스키마로 서버와 화면을 연결하고 실제 응답으로 렌더링 검증한다. 임의로 누락값을 전부 0·빈 배열로 바꾸면 장애가 정상 수치로 위장될 수 있다. `미연결/집계 전/정상 0건/오류`를 구분해야 한다.

## 2. 성공 응답만 있고 기능 결과가 없는 경로 — P1

| 항목 | 코드 근거 | 영향 |
|---|---|---|
| FAQ 저장 | `admin.ts:958–971`: GET은 항상 `[]`, POST는 UUID만 생성, 수정·삭제는 작업 없이 204 | 저장 창이 닫혀도 다시 조회하면 데이터가 남지 않음. `faq.tsx:88` 이후 성공 처리와 연결됨 |
| 가격 통계 재계산 | `admin.ts:1589`: 실제 작업 등록 없이 202와 `queued:true` | 사용자는 실행된 것으로 오해할 수 있음 |
| 이미지 승인·폐기 | `admin/images.tsx:111,118`은 POST, 서버 `admin.ts:1308,1320` 부근은 PATCH | 렌더링을 고친 뒤에도 메서드 불일치로 실패 가능. 실패 처리가 사용자에게 드러나지 않음 |
| 미연결 조작 | `BACKEND_PENDING`에 따른 비활성 조작이 8개 파일에 15개 | 파일·버튼 존재를 기능 완성으로 볼 수 없음 |

15개는 해당 플래그로 막힌 조작만 센 값이다. 전체 미구현 기능 수가 아니다. 정적 호출 목록 [검수 자료](audits/2026-09-10/admin-routes.json)의 `missing`은 동적 URL·쿼리 오탐 가능성이 있어 그대로 결함 개수로 사용하지 않았다.

**조치:** 실제 DB 저장 후 재조회, 실제 작업 ID 발급 후 완료 상태 확인까지 연결한다. 미연결 상태에서 성공 응답을 반환하지 않는다.

## 3. 앱의 정책·기능·정보 불일치 — P1/P2

### 폐기한 기능과 정책이 화면에 남음

- **별점:** `docs/design-handoff/current/SPEC.md:427,439`은 별점·숫자 평점을 금지하지만 상세 `search/[vendorId]/index.tsx:642`, 후기 `reviews.tsx:213`, 작성 `write-review.tsx:210,253`, 수정 `edit-review.tsx:101`에 별점이 있다. 실제 상세·후기에서도 표시를 확인했다.
- **수동 가격 제보:** `CHANGELOG.md:75`에서 WP-RPT-010을 폐기했지만 상세 `index.tsx:528`에서 진입하고 `price-report.tsx:70,207`에서 제출한다. 실제 MY→제보에도 ‘증빙 없이 들은 금액’ 가격 제보가 노출된다. 단순히 옛 파일만 남은 문제가 아니다.
- **개인정보 안내:** `my/privacy.tsx:43–44`는 출생연도 수집·삭제를 설명하지만 실제 구현은 연령대 `age_range`다. `auth/age-range.ts:11`에는 출생연도를 쓰지 말라는 9월 10일 사용자 지시가 명시돼 있다. **연령대 구현을 출생연도로 되돌릴 사안이 아니라 안내를 최신 정책과 일치시킬 사안**이다.

### 실제 이동·검색 문제

- 홈→3곳 비교→뒤로 클릭 및 Enter 후 비교 URL에 그대로 머물렀다. MY→제보→뒤로도 제보 화면에 머무는 현상을 재현했다. `features/navigation/depth-back.ts:39` 이후 `dismissTo`가 throw할 때만 `replace`가 실행된다. 탭 간 이동 실패를 처리하지 못할 가능성이 있지만, 내부 라우터 원인은 추가 계측이 필요하다.
- 지역 필터에 `서울/서울특별시`, `경기/경기도`, `부산/부산광역시` 등이 따로 표시됐다. 서버 `routes/vendors.ts:352–357`은 지역 문자열 첫 단어 그대로 집계하고 검색 화면 `search/index.tsx:268,911`은 이를 그대로 표시한다. 표준 지역 코드 또는 명칭 정규화가 필요하다.

### 검수용 표본과 실제 정보의 구분 부족

- 제이픽처스 상세에 ‘공공기관 확인’, 행정안전부 출처, 제보 건수와 가격 통계가 표시됐다. 후기 문구는 `seed-samples.ts:324`의 검수용 문구와 일치했다.
- `seed-samples.ts:605–610`은 표본 업체도 `source='public_data'`로 저장해 공공기관 배지를 켠다고 명시한다. 표본 표식은 별도 출처 레코드에 둔다.
- 일부 ‘표본’ 안내만으로는 배지·통계·후기 전체가 검수용인지 분명하지 않다. 테스트 데이터 작성의 정당성과 별개로, 실제 정보처럼 해석될 수 있는 표시 문제다. 운영 공개 전에 표본 표시·분리 정책을 정해야 한다. 이번 검수에서 데이터를 삭제하거나 변경하지 않았다.

## 4. 느림을 유발할 수 있는 코드 경로 — 추가 측정 필요

- 앱 `api/client.ts:209,303`: 기본 요청 타임아웃 45초.
- 진입 `app/_layout.tsx:214–229`: 사용자 조회와 bootstrap을 `Promise.all`로 기다리고, 사용자 조회가 실패하면 가입 상태 요청을 추가로 기다린다. 모든 요청이 지연·타임아웃되는 조건에서는 경로 결정이 약 90초까지 늦어질 수 있는 구조다. **실제 90초를 측정했다는 뜻은 아니다.**
- 사용자 조회의 네트워크 오류를 `null`로 바꿔 인증 없음과 섞는다. 일시 장애 때도 로그인 경로로 이동할 수 있다.
- 관리자 `_api.ts:25`와 로그인 직접 fetch에는 명시적 요청 타임아웃이 없다.

**조치:** 인증 판단과 홈 선조회 대기를 분리하고, 인증 실패와 네트워크 실패를 구분한다. 관리자 요청에 타임아웃·취소·재시도·오류 표시를 넣는다. 이후 실측으로 병목을 확정한다.

정밀 성능 측정용 DevTools 도구가 없어 LCP·INP·네트워크 waterfall을 수집하지 못했다. 적용한 웹 성능 스킬의 도구 부재 시 중지 지침에 따라 추적 측정만 보류했고 코드 검수는 진행했다. 숫자로 속도 개선을 주장하지 않는다.

## 5. 계속 틀어지는 운영·배포 구조 — P1

### 기준 문서가 서로 다른 우선순위를 제공

`AI_START_HERE.md:26–29`는 기존 상태·구현을 신규 사용자 지시보다 앞에 두고, `CLAUDE.md:9–17`과 `docs/README.md:28–30`은 최신 전달본을 우선한다. 새 사용자 지시가 실제 최우선이며, 문서의 상반된 안내가 오래된 사양을 되살리는 원인이 될 수 있다.

카카오 단일 로그인은 현재 구현에서 준수하지만 `tokens.json:363–373`에는 소셜 4종, `PROJECT_STATUS.md:43`에는 카카오+이메일 완료 설명이 남아 있다. 이를 현재 앱에 소셜 4개가 노출된 버그로 해석하면 안 된다. 변경 이력·명세·토큰·상태 문서 간 동기화 문제다.

### CI·승인·운영 배포 순서가 하나로 연결되지 않음

- `.github/workflows/main.yml:11`은 Render main 자동배포가 Actions와 독립임을 명시한다. `:105,114,141`의 CI·승인 의존성은 마이그레이션을 제어하지만 Render의 자동배포를 막지 않는다.
- 초기 SHA `e5f3b581` 검수에서 Actions 실행 `34474697265`는 staging 대기였으나 Render 상태 실행 `34474995900`의 로그는 API `autoDeploy=yes`, 같은 SHA 배포 완료를 보여줬다. 이는 당시 확인한 증거이며, 최신 SHA 배포 완료를 주장하는 자료가 아니다.
- `apps/api/src/server.ts:145–158`은 `schema.ok=false`여도 HTTP 200·`ok:true`를 반환한다. `main.yml:183,233`은 본문을 버리고 HTTP 200만 검사하므로 스키마 미적용도 성공으로 통과할 수 있다. 배포 SHA도 검증하지 않는다.
- `scripts/render-trigger-deploy.py:60–63`은 검증된 SHA를 지정하지 않고 최신 main을 배포한다. 다른 재배포 경로까지 함께 통제해야 한다.

**조치:** 검증 SHA 고정 → CI → 승인 → 마이그레이션 → 해당 SHA 배포 → 스키마·버전·로그인 후 핵심 화면 확인 순서로 묶는다. 프로세스 생존과 배포 준비 완료를 별도로 검사한다.

## 수정 순서와 완료 판정

1. 관리자 8개 응답 계약과 렌더링 오류 수정. 실제 서버 응답, 빈 응답, 실패 응답으로 검증.
2. FAQ·재계산·이미지 메서드 수정. 저장 후 재조회와 작업 완료 증거 확인.
3. 샘플 표시와 정상/미연결/미집계 구분. 0건·100%를 근거 없이 정상으로 표시하지 않기.
4. 최신 정책을 기준으로 별점·수동 제보·개인정보 문구·뒤로 이동·지역 중복 정리.
5. 인증 진입 대기 개선 및 실측. 앱·관리자 각각 주요 사용자 흐름 확인.
6. 동일 SHA와 동일 상태의 원본/실제 화면을 390×844 기준으로 대조하고, API·DB·UI 증거를 화면 ID에 연결. 네이티브 검증은 별도 수행.
7. 완료 상태와 배포를 위 증거에 연결. 파일 존재·타입 검사·HTTP 200만으로 완료 처리하지 않기.

이번 결과는 **결함 진단 보고서**다. 제품 수정 완료나 전체 검수 통과 보고가 아니다.
